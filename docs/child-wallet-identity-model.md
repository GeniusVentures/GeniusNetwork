# Child-Wallet Identity Model

**Version:** 1.0
**Status:** Draft — Phase 01, Plan 01-01
**Date:** 2026-07-13

## 1. Overview

A child wallet is a fully independent SuperGenius account — a `GeniusNode` backed by a `GeniusAccount` — created identically to any other wallet in the system. It holds its own independent secp256k1 keypair, tracks its own nonce counter, and need not know about any main wallet at creation time.

### Emergent Identity

Child-ness is emergent, not intrinsic. An account **is** a child wallet if and only if a valid registration record naming a main wallet exists in consensus-visible state. There is no account-type field, no creation-time flag, and no `is_child` boolean anywhere in `GeniusAccount` or `GeniusNode`. This property is the central design decision (D-01) of the identity model:

- A standalone, never-registered wallet is a plain SuperGenius account — it can receive, hold, and transfer GNUS tokens and other assets.
- Once the wallet creates a `RegistrationTx` naming a main wallet and that transaction is accepted by consensus, the account becomes a child wallet relative to that main.
- If the registration is later detached or revoked, the account returns to standalone status.

### No Source Changes Required

No SuperGenius header or source file is modified for child-wallet identity purposes:

| File | Disposition |
|------|-------------|
| `SuperGenius/src/account/GeniusAccount.hpp` | Unchanged — `eth_keypair_`, `GetProposedNonce`/`ReserveNextNonce`, `Sign`/`VerifySignature`, `IsValidPublicKey`/`NormalizeAddress` all used as-is |
| `SuperGenius/src/account/GeniusNode.hpp` | Unchanged — `AccountSource` variant and `GeniusNode::New` factory used without new arms |
| `SuperGenius/src/account/GeniusUTXO.hpp` | Unchanged — UTXO ownership via `owner_address` (see §5) |
| `SuperGenius/src/account/UTXOStructs.hpp` | Unchanged — no new structs needed for identity |

## Keypair & Address

Every child wallet holds an independent secp256k1 keypair generated by the same `EthereumKeyGenerator` used by any wallet in the SuperGenius system. The keypair is stored in the `eth_keypair_` member of `GeniusAccount` (`GeniusAccount.hpp:391`), which is typed as `std::shared_ptr<ethereum::EthereumKeyGenerator>`.

### Key Generation

The child keypair is created through one of the standard `GeniusAccount` factory methods:

| Factory | `AccountSource` Variant | Usage |
|---------|------------------------|-------|
| `GeniusAccount::New()` | `NewAccount{}` | Generate fresh secp256k1 keypair via `EthereumKeyGenerator` |
| `GeniusAccount::NewFromPrivateKey()` | `FromPrivateKey{eth_private_key}` | Restore from an Ethereum hex private key |
| `GeniusAccount::NewFromMnemonic()` | `FromMnemonic{mnemonic}` | Restore from a BIP39 mnemonic phrase |
| `GeniusAccount::NewFromPublicKey()` | `FromPublicKey{public_address}` | Load from storage (read-only, no signing) |

The EthereumKeyGenerator (`ProofSystem/EthereumKeyGenerator.hpp`, included at `GeniusAccount.hpp:28`) handles the underlying secp256k1 key generation. This is the same generator used by main wallets, developer wallets, and any other SuperGenius account — there is no special "child" key generator.

### Address Derivation

The child's address is derived from its secp256k1 public key using the standard SuperGenius address scheme:

1. The public key is serialized as a 512-bit value (uncompressed form).
2. The hex representation is a 128-character string with **no "0x" prefix**.
3. Validation uses `GeniusAccount::IsValidPublicKey()` (`GeniusAccount.hpp:152`), which confirms the string is exactly 128 hex characters.
4. Input normalization uses `GeniusAccount::NormalizeAddress()` (`GeniusAccount.hpp:144`), which strips any leading "0x" prefix for storage consistency.

The child address format is indistinguishable from any other wallet address. The UTXO subsystem, transaction validation, and CRDT storage all use this address for ownership and routing — none of them know or care whether the address belongs to a child.

### Cryptographic Independence

> **The child keypair is NOT HD-derived from any main wallet seed.** There is no cryptographic parent-child relationship between the child keypair and the main keypair.

This is a deliberate design property (from `GNUS_Subwallet_Architecture_Proposal.md` §Core Properties):

- Compromise of the child keypair reveals **nothing** about the main wallet keypair.
- The main wallet private key **never** enters the game or child process.
- The child wallet can be created entirely offline, in a sandboxed environment, without any main wallet present.

### Signing and Verification

A child wallet signs transactions using the standard `GeniusAccount::Sign()` method (`GeniusAccount.hpp:216`):

```
std::vector<uint8_t> Sign(const std::vector<uint8_t> &data) const;
```

This produces a 64-byte ECDSA signature over the hashed transaction data. Verification uses the static method (`GeniusAccount.hpp:207`):

```
static bool VerifySignature(const std::string &address, std::string_view sig,
                            const std::vector<uint8_t> &data);
```

The child's signature authenticates the child's own transactions (transfers, registrations, escrow holds) — exactly as any wallet's signature authenticates its own transactions. A child keypair cannot produce a valid signature over a main wallet's address, and vice versa.

### Design Rule: GeniusAccount.hpp Untouched

`GeniusAccount.hpp` is **not modified** for child-wallet identity. The identity model uses the existing fields and methods (`eth_keypair_`, `Sign`, `VerifySignature`, `IsValidPublicKey`, `NormalizeAddress`) without adding new member variables, new factory methods, or new validation logic. Child-ness is tracked elsewhere — in the consensus-visible registration record (see the registration protocol design document, Plan 01-02).

## Wallet Creation & Lifecycle

A child wallet is created via the same `GeniusNode::New()` factory used for every wallet:

```
GeniusNode::New(dev_config, AccountSource{NewAccount{}})
```

See `GeniusNode.hpp:126` for the factory signature and `GeniusNode.hpp:88-107` for the `AccountSource` variant definition.

### Creation Paths

The `AccountSource` variant (`GeniusNode.hpp:107`) supports four creation modes. All apply equally to child wallets:

| Source | Struct | Creates |
|--------|--------|---------|
| `NewAccount{}` | Empty struct (line 88-90) | Generates a fresh secp256k1 keypair on the spot. This is the standard creation path for a new child wallet. |
| `FromPrivateKey{eth_private_key}` | Wraps `std::string` (line 92-95) | Restores a child wallet from a known Ethereum private key. Useful for migrating a child wallet between devices. |
| `FromMnemonic{mnemonic}` | Wraps `std::string` (line 97-100) | Restores a child wallet from a BIP39 mnemonic phrase. The child mnemonic is independent of any main wallet mnemonic. |
| `FromPublicKey{public_address}` | Wraps `std::string` (line 102-105) | Loads an existing child wallet from storage in read-only mode. No signing capability — useful for balance monitoring. |

In all cases, `GeniusNode` internally delegates to `GeniusAccount` factory methods (`GeniusAccount::New`, `NewFromPrivateKey`, `NewFromMnemonic`, `NewFromPublicKey` at `GeniusAccount.hpp:83-131`) which create the `eth_keypair_` via `EthereumKeyGenerator` as described in §2.

### Design Rule: GeniusNode.hpp Untouched

`GeniusNode.hpp` is **not modified** for child-wallet identity. No new `AccountSource` variant is needed — the existing `NewAccount`, `FromPrivateKey`, `FromMnemonic`, and `FromPublicKey` arms cover all child-wallet creation and restoration scenarios. The `GeniusNode::New()` factory does not receive a child/main discriminator — it simply creates a wallet.

### Standalone Operation

A child wallet is **initially standalone**. Immediately after creation, it can:

- Receive GNUS tokens and other assets from any source
- Hold NFTs and any other token type supported by the SuperGenius UTXO model
- Transfer its own assets to arbitrary addresses by signing transactions with its own keypair
- Submit and earn rewards from background AI inference processing (if configured)

No registration is required for any of these operations. Registration is an **optional subsequent step** that establishes a parent-child relationship with a main wallet, enabling:

- Main-wallet discovery and balance monitoring (Phase 2)
- Main-to-child funding (Phase 2)
- Main recovery of child assets (Phase 2)

These Phase 2 and Phase 3 capabilities are documented in the registration protocol design document (Plan 01-02) and subsequent design documents. The identity model presented here defines what a child wallet **is** in isolation — a standalone SuperGenius account with an independent keypair.

### Lifecycle Overview

The child wallet life cycle follows these high-level states (detailed design in Phase 3, LIFE-01..04):

```
[Created] → Standalone → (register) → Pending → Registered → (detach) → Standalone
                                                         → (revoke) → Closed
```

- **Standalone:** The child wallet operates independently. It can earn, hold, and transfer assets.
- **Registered:** A valid `RegistrationTx` names a main wallet. The main can discover and manage the child (Phase 2).
- **Detached/Closed:** Registration is removed. The child returns to standalone status and retains all assets.

The identity model does **not** define the state machine transitions or consensus rules for these states — those are Phase 2 (consensus) and Phase 3 (lifecycle) concerns. What matters for identity is that:

1. A child wallet is born standalone — no parent relationship at creation.
2. Registration is an additive event that augments the account's visible state.
3. De-registration removes the parent relationship but leaves the wallet intact.
