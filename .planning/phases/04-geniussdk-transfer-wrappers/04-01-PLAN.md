<objective>
Add 4 new public GeniusSDK C API functions — `GeniusSDKFundChild`, `GeniusSDKFundChildGNUS`, `GeniusSDKRecoverFromChild`, `GeniusSDKRecoverFromChildGNUS` — that let external callers fund a registered child wallet (SDKT-01) and recover funds from one (SDKT-02) without linking SuperGenius directly, both returning the existing `GeniusNodeReturnValue_t` status codes (SDKT-03).

Purpose: Phase 3 already delivered every piece of underlying machinery this phase wraps — `GeniusNode::TransferFunds` (ordinary transfer, D-61) and the new `GeniusNode::RecoverFromChild` (D-62) — so this phase is a pure C-API exposure layer, adding zero new business logic to SuperGenius.
Output: `GeniusSDK.h`/`GeniusSDK.cpp` gain 4 new thin wrapper functions, each following an exact existing analog (`GeniusSDKTransfer`/`GeniusSDKTransferGNUS` for the core shape, `GeniusSDKRegisterChild` for the `const char*` child-address validation idiom).
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| External caller (game/app process) → GeniusSDK C API | Untrusted caller-supplied `amount`, `child_address` (`const char*`), and `GeniusTokenValue*` cross into `GeniusNodeInstance` here — the same boundary every existing GeniusSDK wrapper already crosses |
| GeniusSDK wrapper → GeniusNode/TransactionManager/consensus pipeline | Submission-time result from `TransferFunds`/`RecoverFromChild` is visible to the wrapper; consensus-level acceptance/rejection (`CheckParentChildAuthority`, D-21) happens later, out of this wrapper's observability |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-01 | Tampering | `child_address` (`const char*`, unbounded, caller-supplied, no length parameter) | medium | accept | Matches the existing `GeniusSDKRegisterChild`/`GeniusSDKGetChildBalance` `const char*` convention used throughout `GeniusSDK.h` — no existing wrapper in this file validates buffer length; introducing a length check only for these 2 new functions would create an inconsistent input contract. Null/empty check (`child_address == nullptr \|\| child_address[0] == '\0'`) mirrors `GeniusSDKRegisterChild` exactly. |
| T-04-02 | Repudiation | `GeniusSDKRecoverFromChild`/`GeniusSDKRecoverFromChildGNUS` fire-and-forget submission | medium | accept | Per D-67, the caller cannot distinguish "gate rejected the recovery" (`CheckParentChildAuthority`'s D-21 destination-mismatch check, evaluated only at consensus finalization) from "submitted, outcome pending" — `GENIUS_NODE_RET_OK` means submitted, not confirmed. Explicitly accepted by user decision in `04-CONTEXT.md`; documented via a mandatory `@note` doc comment on both `GeniusSDKRecoverFromChild` and `GeniusSDKRecoverFromChildGNUS` (Task 1). |
| T-04-03 | Denial of Service | `amount` (`uint64_t`, unbounded, caller-supplied) passed to `TransferFunds`/`RecoverFromChild` | low | mitigate | The underlying `GeniusNode::TransferFunds`/`RecoverFromChild` already perform readiness/balance checks and return `outcome::failure` on insufficient funds or a not-ready transaction manager; the wrapper propagates this as `GENIUS_NODE_ERROR_TRANSFER` via the existing `result.has_value()` check — no unchecked arithmetic or unbounded allocation occurs in the wrapper itself. |
| T-04-04 | Elevation of Privilege | `GeniusSDKRecoverFromChild` used to attempt redirecting a child's funds to an address other than its registered main | high | mitigate | Enforced entirely by Phase 3's `CheckParentChildAuthority` consensus gate (D-21 destination restriction) at finalization time — this SDK wrapper adds no new authority path and cannot bypass the gate; the wrapper layer performs no additional access control of its own, identical to every other transfer wrapper in this file. |
| T-04-SC | Tampering | npm/pip/cargo installs | low | accept | No new package-manager dependencies — this plan only adds C/C++ function declarations and definitions to two existing files, zero new external dependencies introduced. |

</threat_model>
