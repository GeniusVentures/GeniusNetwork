**Section 1: Overview**
- State the architecture: "Discovery is push-primary, poll-fallback. The primary path is pubsub broadcast (Phase 2 D-15/D-16) — the child publishes the RegistrationTx CID to the main's address topic on `AddBroadcastTopic(main_address)`, and the main receives the CID notification via `AddListenTopic(main_address)`. **Section 2: Push Path — PubSub CID Notification (DISC-01 primary)**

**Section 6: Main-Wallet Actions (DISC-03)**
- Per D-29: "Every main-wallet action reuses an existing Phase 2 or Phase 3 mechanic. No new consensus rules are introduced for discovery — the discovery layer provides the UI/API that invokes existing mechanics."
- Document each action as a subsection:

**6.1 Fund (main→child transfer)**
- Mechanic: CONS-01 (Phase 2). Main-signed transfer transaction with child as destination.
- Validation: `CheckParentChildAuthority` (gate 2.5) validates that a certified `reg/{child_addr}` record exists linking the child to the sending main.
- Anchor: `TransactionManager.cpp:4234-4304` (ValidateTransactionForConsensus pipeline), Phase 2 `docs/02-consensus-parent-child-authority.md` §CONS-01.
- RESTRICTION: Main must have sufficient UTXOs owned by `main_address` (standard transfer validation).

**6.2 Recover (main-recover-from-child)**
- Mechanic: CONS-02 (Phase 2). Main-signed transfer FROM child address.
- Validation: Destination is HARD-RESTRICTED to the registered `main_address` from `reg/{child_addr}` CRDT record (D-21). `CheckParentChildAuthority` gate validates `dst == reg/{child_addr}.main_address` — any other destination is REJECTED.
- Anchor: Phase 2 `docs/02-consensus-parent-child-authority.md` §CONS-02, TransactionManager.cpp `ValidateTransactionForConsensus`.
- Note: Recovery requires the main's private key to sign → recovery flow must happen in the main wallet process (out-of-process from the child — same security boundary as REG-04).

**6.3 Inspect History / View Assets**
- Mechanic: SYNC-04 (Phase 2 D-17). Main reads child's CRDT state via subscribed pubsub channel (`AddListenTopic(child_address)`).
- Validation: Read-only — CRDT state is public, no signature needed. The main subscribes to the child's address topic and receives CRDT deltas for UTXO changes, transaction history, and balance updates.
- Anchor: `pubsub_broadcaster_ext.hpp:74` (`AddListenTopic`), Phase 2 `docs/02-crdt-registry-pubsub.md` §SYNC-04.
- Data: Child balance (sum of UTXO amounts), UTXO list (`UTXOEntryRecord` entries where `owner_address == child_address`), transaction history (CRDT deltas from child's topic).

**6.4 Revoke**
- Mechanic: LIFE-01 (Phase 3 D-36). Main-signed `RevokeTx` consensus transaction.
- Validation flow (research-recommended first-class `RevokeTx` approach):
  1. Gate 2 (CheckTransactionAuthorization, TransactionManager.cpp:4361-4383): validates main's signature.
  2. Gate 2.5 (CheckParentChildAuthority, Phase 2 D-19): validates `reg/{child_addr}.main_address == signer` AND reg/ record is in Registered state (detach_flag == false, main_address != empty).
  3. Gate 4 (EvaluateTransactionReplayProtection): nonce chain (`sgns.nonce.v1`, Consensus.hpp:37) prevents double-revoke.
  4. Post-validation: sets `detach_flag = true` on the `reg/{child_addr}` CRDT record. Main has zero recovery authority thereafter.
- RevokeTx proto: new message in `SGTransaction.proto` with `DAGStruct dag_struct = 1`, `bytes child_address = 2`, `uint64 registration_sequence = 3`. New `EmbeddedTransaction` oneof arm `revoke = 9` in `Consensus.proto`.
- PER RESEARCHER OPEN QUESTION #3: Recommend first-class `RevokeTx` as a new `GeniusTransaction` subclass (following `RegistrationTx` Phase 1 D-06 pattern), NOT a flagged transfer. Rationale: keeps authority actions separate from value transfers; cleaner audit trail; no overloading of the transfer type.
- Cross-reference: The RevokeTx is fully specified in `docs/03-02-reward-policy-lifecycle.md` §Lifecycle Change-Flows. This section cross-references it as a discoverable action.

**6.5 Detach**
- Mechanic: LIFE-01 (Phase 3 D-35). Child-signed `RegistrationTx` with `detach_flag = true` at higher `sequence`.
- Validation: `FilterRegistration` (Phase 2 D-13) validates child signature + `sequence > current.sequence` + `supersedes_sequence == current.sequence` (D-38). Nonce chain prevents double-detach.
- Note: This is a CHILD-initiated action. The main wallet displays "Detach" as a discoverable status, but the main cannot trigger it — only the child can detach (per D-35). The main's equivalent is Revoke.
- Cross-reference: `docs/03-02-reward-policy-lifecycle.md` §Detach Flow.

|----------|-------------|
| Pubsub network → Main wallet (push) | CID notification arrives from untrusted pubsub network; main must resolve CID content-addressed and check certified status before acting |
| Responder node → Main wallet (poll) | `ChildDiscoveryResponse` arrives from any peer on the pubsub network; responder may be malicious — main validates signature + CID content-addressing + certified status |
| Main wallet → CRDT state (inspect) | Read-only access to child's public CRDT state; no signature needed, but attacker could inject false CRDT deltas — CRDT validation handles this at the filter level |
