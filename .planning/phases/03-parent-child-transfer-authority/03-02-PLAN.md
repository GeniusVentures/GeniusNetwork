<objective>
Implement the core CONS-01/CONS-02/CONS-06 consensus gate: extend the whole-tx signature check (`CheckTransactionAuthorization`) and the per-input signature check (`GeniusInputValidator::ValidateWitness`) with the narrow D-60 certified-main OR-branch, and add the new `CheckParentChildAuthority` gate that enforces D-21's destination restriction for delegated-authority (main-recovers-from-child) transactions while leaving ordinary child-signed transfers (REGR-01/02) and ordinary main-signed transfers (CONS-01) untouched.

Purpose: This is the phase's central security-critical change. D-60 requires accepting a main-signed transaction where `src = certified_child_addr` — today's code only ever verifies a signature against the transaction's own declared source address, so without this plan's changes, `RecoverFromChild` (Plan 03) would build transactions no gate can ever approve.
Output: The complete, correctly-scoped D-60 signature-acceptance extension plus the new gate, wired into the exact verified pipeline insertion point.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Network-supplied transaction → `ValidateTransactionForConsensus` | Every peer (including the local node on its own submissions) re-validates every transaction through this exact pipeline before accepting it |
| Network-supplied per-input signatures → `GeniusInputValidator::ValidateWitness` | Each UTXO input's signature is independently re-verified, regardless of whole-tx signature outcome |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-04 | Elevation of Privilege | `CheckTransactionAuthorization` / `ValidateWitness` D-60 branch | critical | mitigate | The delegated branch only accepts a signature verifying against the certified main address returned by `Blockchain::CheckCertifiedParent` — an address resolved from a consensus-certified `reg/` record (D-26), never from client-supplied data. A child never holds the certified main's private key, so it cannot forge this signature. |
| T-03-05 | Elevation of Privilege | `CheckParentChildAuthority` destination restriction | high | mitigate | D-21 hard equality (`params->second.front().dest_address == *certified_main`) rejects any certified-main-delegated transaction whose primary output is not the certified main's own address — a compromised or malicious relayer cannot redirect recovered funds |
| T-03-06 | Tampering | Output-list reordering post-signature | high | mitigate | The whole-tx signature (`MakeSignature`/`CheckSignature`/`CheckSignatureAgainst`) covers the full serialized `DAGStruct` including UTXO inputs/outputs (verified: `TransferTransaction::SerializeByteVector` embeds `outputs_` into the signed payload) — any post-signature tampering with the output list invalidates the signature, so `.front()` cannot be spoofed without breaking authorization first |
| T-03-07 | Elevation of Privilege | REGR-03 — child claims `src = main_addr` to spend main's UTXOs | critical | mitigate | Unaffected by this plan's changes: `CheckParentChildAuthority` only fires its delegated-authority logic when `blockchain_->CheckCertifiedParent(tx.GetSrcAddress())` finds a certified registration for that src address; `main_addr` is never itself registered as anyone's child, so this gate never even reaches its delegated branch for such a tx — and `CheckTransactionAuthorization`/`ValidateWitness`'s signature checks reject it upstream regardless, since a child never holds main's private key. Reconfirmed by a dedicated regression test in Plan 04. |
| T-03-SC | Tampering | npm/pip/cargo installs | low | accept | No new package-manager dependencies in this plan |
</threat_model>
