# Deferred Items — Phase 06 (SuperGenius Merge & Regression Verification)

## DI-06-01: Real-networked E2E test fixtures crash on startup (thirdparty submodule drift, unrelated to origin/develop merge)

**Discovered during:** 06-04 Task 1 (full regression suite execution)

**Symptom:** Both `registration_transaction_test.exe` and `child_registration_test.exe` (freshly rebuilt in Plan 03 against the merged tree) crash deterministically with:
```
Assertion failed: config_.storageRecordTTL > config_.storageWipingInterval, file W:\gnus\GeniusNetwork\thirdparty\libp2p\src\protocol\kademlia\impl\storage_impl.cpp, line 26
```
This fires during `libp2p::protocol::kademlia::StorageImpl`'s constructor, the very first time a real `GossipPubSub`/Kademlia-backed node is brought up — i.e. inside every `RegistrationTransactionE2ETest`/`ChildRegistrationIntegrationTest` fixture's `SetUp()`. Since it is a process-level `BOOST_ASSERT` (not a GTest failure), the whole test process aborts (exit code 3) the instant it fires, taking down every remaining test in that run with it.

**Scope of impact:**
- `registration_transaction_test.exe`: the 5 non-E2E `RegistrationTransactionTest` cases (serialization, signature-tamper rejection) pass cleanly; all 32 `RegistrationTransactionE2ETest` cases never execute (process dies on the first one, reproduced individually via `--gtest_filter` too — confirmed not order-dependent).
- `child_registration_test.exe`: crashes on its very first (`ChildRegistrationIntegrationTest`) case; 0/4 execute.

**Root-cause investigation (why this is NOT a regression from the origin/develop merge under verification):**
- `libp2p::protocol::kademlia::Config`'s defaults are `storageRecordTTL = 24h`, `storageWipingInterval = 1h` (`thirdparty/libp2p/include/libp2p/protocol/kademlia/config.hpp`) — the assertion trivially holds for an untouched default-constructed `Config`. No code path in SuperGenius (grepped across `src/`) or in `thirdparty/ipfs-pubsub`'s `MakeCustomHostInjector` (`gossip_pubsub.cpp:148`) sets these fields to anything else. The only way the assertion can fail with these defaults is if the `Config` object's memory is corrupted, stale, or dangling by the time `StorageImpl`'s constructor reads it.
- None of the files touched by the SuperGenius merge (`TransactionManager.cpp`, `GeniusNode.hpp/.cpp`, `Blockchain.cpp`, `CMakeLists.txt`, `Consensus.proto`) reference Kademlia's `Config`/`StorageImpl` at all.
- A pre-existing, **not rebuilt in this session** binary (`build/Windows/Debug/test_bin/Debug/blockchain_genesis_test.exe`, timestamped Jul 22 17:13, predating any Plan 01-03 merge work) exercises the exact same `MakeCustomHostInjector`/Kademlia bring-up path and does **not** hit this assertion — it proceeds past node/PubSub construction into blockchain-sync retry logic. This rules out "the environment/network is always broken" and confirms the crash is specific to binaries rebuilt in this session.
- `git status`/`git diff` in the outer `GeniusNetwork` repo shows the **sibling** `thirdparty` submodule (not `SuperGenius`) is dirty: its checked-out commit (`eb5bc656...`) is 5 commits ahead of what the outer repo's index records (`13ef282e...`). `git reflog` inside `thirdparty/` shows `eb5bc65 HEAD@{2026-07-23 14:38:17 -0400}: pull: Fast-forward` — a same-day fast-forward pull (through commits titled "Thread safety changes", "Fixes for Windows" x2, "Pin to windows 2022", "Handles appleclang 21+ issues"), almost certainly pulled automatically as part of this session's Plan 03 build-troubleshooting, entirely independent of the SuperGenius/origin-develop merge this phase is verifying.
- Between the recorded and currently-checked-out `thirdparty/ipfs-pubsub` commits, `gossip_pubsub.cpp`'s `MakeCustomHostInjector` changed `libp2p::injector::makeKademliaInjector(...)` to `libp2p::injector::makeKademliaInjector<di::extension::shared_config>(...)` — a change to boost::di config-lifetime/sharing semantics across the combined host+kademlia injector graph. This is the most plausible single-line candidate for the observed corruption (a DI config-lifetime bug), though it was not proven with a live debugger given the scope of this plan.

**Why deferred rather than fixed here:** Per this plan's scope boundary, this is a pre-existing/unrelated-file issue — it lives entirely in the `thirdparty` sibling submodule (`ipfs-pubsub`/`libp2p`), which is under active, unrelated WIP development (commit history includes many "Trial"/"Revert"/"Checkpoint" commits) and was not touched by any 06-01/02/03 conflict resolution. Fixing it would require either (a) pinning `thirdparty` back to the outer repo's recorded commit and re-verifying the Windows build still succeeds (risking reintroducing whatever Windows build issue motivated the original pull), or (b) live-debugging a third-party DI library's config lifetime — both out of scope for a merge-regression-verification plan.

**Recommendation:** Track as a candidate for the same future "test-infra/node-shutdown-hygiene" phase already flagged in STATE.md for the related GossipPubSub lifecycle flakiness (teardown segfault, 10+ minute bring-up idling). Whoever picks it up should start by reproducing with `thirdparty` pinned back to `13ef282e...` (recorded commit) to confirm/deny the correlation identified above before deciding whether to fix forward (patch the DI config lifetime) or pin back.

**Impact on this phase's verification:** MVER-03 (full regression suite, zero regressions) could not be fully confirmed by direct test execution — only the 5 non-E2E `RegistrationTransactionTest` cases ran and passed. MVER-04's consensus-gate compatibility was instead fully confirmed via static verification (symbol grep + byte-identical function-body diff, see 06-04-SUMMARY.md), which does not depend on the crashing test fixtures.
