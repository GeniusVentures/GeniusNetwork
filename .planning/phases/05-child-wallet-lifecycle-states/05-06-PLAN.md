<objective>
Fix the single production-code defect verification found in Phase 5: `TransactionManager::ParseRevokeTransaction`'s write of the updated `reg/{child_addr}` record (`detach_flag=true`) currently goes through `GlobalDB::Put` — the full CRDT broadcast path (`CrdtDatastore::PutKey` -> `Publish` -> `CreateDAGNode` -> `AddDAGNode` -> `WaitForJob`) — which deadlocks when invoked during confirmed-transaction processing. Add a new, narrowly-scoped **local-only** write path that applies the same update directly into the CRDT set's own storage (the exact storage `globaldb_m->Get`/`FilterRegistration`/`CheckParentChildAuthority` already read from) without creating a DAG node, without broadcasting, and without calling `AddDAGNode`/`WaitForJob` — eliminating the deadlock at its source rather than working around it.

Purpose: this is the sole remaining gap from `05-VERIFICATION.md` (score 13/18) blocking LIFE-01 (Revoke transition) and the Revoke half of LIFE-04 (post-transition invariants). Everything else the phase goal names — proto schema, dispatch wiring, `FilterRegistration` gate 3b, `CheckParentChildAuthority`'s revoke branch, Detach, Replace-Main, and Revoke's own authority-rejection paths — is already verified working. This plan closes the one remaining defect: Revoke's state-mutation effect never actually lands.

Root cause, grounded in this plan's own source read (not merely repeated from 05-05-SUMMARY.md's candidate hypothesis): `globaldb_m->Get(reg_key)` reads via `CrdtDatastore::GetKey` -> `set_->GetElement(key)`, a synchronous local lookup with zero DAG/broadcast involvement. `globaldb_m->Put(reg_key, ...)`, however, is the ONLY public write path on `GlobalDB`/`CrdtDatastore`, and it unconditionally goes through `Publish` -> `CreateDAGNode` (reads current DAG heads, assigns a height-based priority) -> `AddDAGNode` (enqueues a self-created job, calls `WaitForJob`) -> `WaitForJob` (blocks the calling thread on a condition variable until a DAG worker thread marks the job COMPLETED, with a 20-minute internal timeout — consistent with the `WaitForJob: Still waiting for CID ... (elapsed: 90s)` log line both 05-05-SUMMARY.md and 05-VERIFICATION.md observed). `TransactionManager::PutProducedUTXOs` (the precedent 05-05-SUMMARY.md correctly identified as "the established local, non-broadcast pattern for a per-node-derived side effect") in fact writes through `UTXOManager::PutUTXO` -> `StoreUTXOs`, which persists directly to raw RocksDB via `batch->put(...)` — a *completely separate keyspace* from the CRDT `reg/` records that `globaldb_m->Get`/`FilterRegistration`/`CheckParentChildAuthority` read. Literally reusing that UTXO storage mechanism for `reg/` would silently break every reader of `reg/{child_addr}`. The correct analog is instead `CrdtDatastore::MergeDataFromDelta` (already used internally whenever a peer's already-fetched delta is merged into this node's local CRDT set) — it calls `set_->Merge(delta, id)` directly, which locks only `CrdtSet`'s own private `mutex_` (a plain, non-reentrant `std::mutex`, entirely distinct from `CrdtDatastore::dagWorkerMutex_`), performs a synchronous RocksDB batch put, and returns — never touching the DAG job queue, the DAG worker thread pool, or any condition-variable wait. This plan exposes that exact mechanism as one new minimal, reusable method rather than duplicating `CrdtSet`'s internal key-encoding inside `TransactionManager` (which CLAUDE.md's minimal-change philosophy and duplication rules both forbid).

Output: `ParseRevokeTransaction`'s `reg/{child_addr}` write completes synchronously and deterministically, with the four currently-blocked tests (`RevokeChildEndToEnd`, `RevokeRejectedForAlreadyDetachedChild`, `ReRegistrationAfterRevoke`, `RevokePreservesChildUTXOsKeypairNonce`) passing when re-run in isolation.
</objective>
