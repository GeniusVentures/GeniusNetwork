**Section 3 — Rule Dispatch Logic (~60-80 lines):**
- State D-20: rule dispatch reuses the existing `"transfer"` tx type — no new tx types are needed. The gate deterministically checks three things to classify the transaction:
  1. **Who signed the tx?** — `tx.GetSrcAddress()` is the signer. `CheckTransactionAuthorization` already verified the signature matches this address.
  2. **Is there a `reg/` record linking the addresses?** — Read `reg/{child_addr}` from CRDT. If `src` is a child (`FetchedRegisteredMain(src)` returns a main address), the relationship exists. If `dst` is a child, the reg/ record links it to a main.
  3. **Is the registration certified?** — Call `IsRegistrationCertified(child_addr)`. Per D-26, uncertified registrations are treated as no relationship → gate returns `Approve()` and lets downstream checks handle the tx (which will fail if authority is required).
- Document the signer classification logic (PATTERNS.md lines 527-536):
  - Main-signed tx: `src_address == registered_main_address` AND the signature is valid (already verified by gate 2)
  - Child-signed tx: `src_address` is a child address found in `reg/{child_addr}` AND the signature is valid
  - Ordinary tx (no registration): neither src nor dst has a reg/ record → no parent-child authority applies → `Approve()`
- Document the direction classification for main-signed txs:
  - **Main→Child fund (CONS-01):** main signed, src is main address, dst is a child registered to that main → allow

- **CONS-01 — Main→Child Fund:**

- **CONS-02 — Main-Recover-from-Child (D-21):**
  - Rule: Main can recover funds from a registered child. Explicit destination restriction: `dst` MUST be the registered main address.
  - Gate action: (a) main signed, (b) src is a child registered to that main (reg/ lookup confirms `reg/{src_child}.main_address == signer`), (c) registration certified, (d) **dst == main_address** (from reg/ record).
  - D-21 hard restriction: if `dst != main_address` → `Reject()`. Recovery IS NOT seizure — the main cannot redirect child funds to an arbitrary third-party address. This implements Pitfall 3 protection (recovery-as-seizure from RESEARCH.md lines 481-483).
  - Reuses `"transfer"` tx type — the main constructs a normal transfer with `src = child_address, dst = main_address` and signs with main key.

  - Anchor points: `CheckParentChildAuthority` does NOT read CRDT for child-signed txs; `CheckTransactionAuthorization` at `TransactionManager.cpp:4361` (signature); `ValidateWitness` at `GeniusInputValidator.cpp:419` (ownership).

  - The existing `GeniusNode::PayDev` path handles developer payments — the child's SDK constructs a normal transfer to `dev_wallet` address and signs it.
  - No reg/ lookup needed — no special authority rule applies. Child controls its own funds.
  - Anchor points: `GeniusNode::PayDev` (existing transfer-to-developer path); developer wallet address from `DevConfig_st`.

**Section 6 — RegistrationTx Field Validation in Consensus Pipeline (~60-80 lines):**
- State the problem (RESEARCH.md Pitfall 5, lines 481-488): RegistrationTx passes through `CheckTransactionWellFormed` (type exists in `transaction_parsers`) and `CheckTransactionTypeRules` (no UTXO params → passes by default at line 4592). Its semantic fields — `main_address` validity and `sequence > 0` — are validated only in `FilterRegistration` (CRDT level, Plan 02-01 §3) but NOT in the consensus pipeline.
- This creates a gap: the CRDT filter runs on a peer's local (possibly stale) state. Consensus validators independently validate the tx and should not rely solely on the CRDT filter's validation.
- State the **recommendation** (RESEARCH.md open question 2): Add a RegistrationTx validation branch to `CheckTransactionTypeRules` at `TransactionManager.cpp:4558-4593` for defense-in-depth:
  - After the existing `HasUTXOParameters()` check (line 4594) and before the default `return true` (line 4592), add:
    - If `tx.GetType() == "registration"`: validate `main_address` is a valid 128-hex public key via `GeniusAccount::IsValidPublicKey` at `GeniusAccount.hpp:152`; validate `sequence > 0`
    - FAIL → `return false` (Reject)

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Main wallet → Consensus validator | Main submits a transfer tx claiming delegated authority over a child's UTXOs. The validator MUST independently verify the parent-child relationship from certified CRDT state — it cannot trust the tx metadata. |
| Child wallet → Consensus validator | Child submits ordinary transfer tx. Validator verifies child signature + UTXO ownership via existing `CheckTransactionAuthorization` + `ValidateWitness`. No reg/ lookup needed. |
| CRDT reg/ record → CheckParentChildAuthority | The authority gate reads `reg/{child_addr}` from local CRDT. CRDT state may be stale (eventual consistency). The gate MUST check the certified status flag before applying authority rules. |
| CheckParentChildAuthority → ValidateWitness | The authority gate approves a delegated tx where the signer is NOT the UTXO owner (main-recover-from-child). The design must specify how this approval signals to `ValidateWitness` to bypass the owner check — without weakening the check for non-delegated txs. |
