<objective>
Add `GeniusNode::GetChildBalance` — a thin two-overload alias over the existing `GetBalance` family — that reads a child wallet's balance from the main node's locally-synced CRDT UTXO view, with no registration gate and no new failure path.

Purpose: This is the sole production-code artifact for BALT-01. It gives the main wallet a node-internal way to read any address's (including a registered child's) token balance, computed purely from data already syncing via the existing D-49 CRDT/pubsub follow mechanism. Phase 01-02 depends on these two overloads existing and compiling before it can write and run the multi-node proof.
Output: `GeniusNode::GetChildBalance(const std::string&, TokenID)` and `GeniusNode::GetChildBalance(const std::string&)`, declared in GeniusNode.hpp and implemented in GeniusNode.cpp, both compiling as part of `genius_node_test`.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Any in-process caller → `GeniusNode::GetChildBalance` | No registration/authorization check is performed (D-54) — the method is a node-internal read with no network-facing entry point this milestone (no gRPC/SDK exposure per REQUIREMENTS.md Out of Scope). |
| `child_address` string → `UTXOManager::address_outpoints_` map lookup | Untrusted/arbitrary address strings are used purely as map keys, never interpreted as code, paths, or query fragments. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-01 | Information Disclosure | `GeniusNode::GetChildBalance` (no registration gate, D-54) | low | accept | Node-internal only this milestone — no gRPC/SDK caller exists yet (REQUIREMENTS.md Out of Scope confirms API layer is deferred). The trust boundary is the process boundary, not a network boundary; anyone with in-process access to a `GeniusNode` instance already has equivalent or greater access. UTXO ownership is already consensus-visible via CRDT, so balance is not a secret. Authorization gating is explicitly deferred to the future API-layer milestone per 01-CONTEXT.md deferred ideas. |
| T-01-02 | Tampering | `child_address` used as `address_outpoints_` map key | low | accept | The address is used strictly as a `std::string` key into an in-memory map — no pointer arithmetic, no SQL/format-string interpolation, no filesystem path construction. Unknown or malformed addresses simply miss the map and return 0, identical to the existing (already-shipped) `GetBalance(address)` behavior. |
| T-01-03 | Repudiation | N/A — read-only query | low | accept | GetChildBalance performs no state mutation and produces no audit trail requirement; it mirrors the existing unaudited `GetBalance` family, which has shipped without an audit log. |
| T-01-SC | Tampering | npm/pip/cargo installs | n/a | accept | No package-manager installs in this plan — pure additive C++ source change, zero new dependencies. |

## Security Summary

GetChildBalance introduces no new trust boundary beyond the existing `GetBalance` family it mirrors exactly (same delegation path, same lack of registration/authorization gate, same 0-ambiguity limitation). The only material difference is that the queried address need not be the node's own account — a capability `UTXOManager::GetBalance` already supports today per the D-17 foreign-address guard removal noted in 01-CONTEXT.md.
</threat_model>
