<objective>
Close Gap 2 (Error Message Propagation Loss, major, UAT test 2), Gap 4 (Model Format Validation Missing, major, UAT test 11), and Gap 5 (Unknown Pass Type Error Handling, major, UAT test 12) — all three are rooted in the same file (`ProcessingManager.cpp`'s `CheckProcessValidity()` and the `Init()` parse path) and are fixed together: (a) `CheckProcessValidity()` currently logs field-specific messages but returns generic `Error::PROCESS_INFO_MISSING`/`Error::INVALID_JSON`, losing the field context before it reaches the caller; (b) it never validates the `model.format` value beyond presence, so an `ONNX`-format model passes `CanExecute()` unrejected; (c) quicktype-generated `from_json(PassType&)` throws a plain `std::runtime_error` for unrecognized enum values, caught generically as `Error::INVALID_JSON` with no reference to the offending type.

Purpose: without touching generated/ code (the project convention forbids hand-editing `generated/`), add 4 granular `Error` enum values with distinct, field-referencing messages, and intercept unrecognized `type`/`model.format` raw strings in `Init()` *before* calling the quicktype `from_json()` that would otherwise throw and discard the context.

Output: 4 new `ProcessingManager::Error` values with distinct category messages; pre-parse validation in `Init()`; a new model-format-executability check in `CheckProcessValidity()`.
</objective>

<task type="auto">
  <name>Task 2: Wire granular errors into CheckProcessValidity() and pre-parse validation into Init()</name>
  <files>SuperGenius/SGProcessingManager/src/processingbase/ProcessingManager.cpp</files>
  <action>
Three changes, all in `ProcessingManager.cpp`:

**1. `CheckProcessValidity()`, `case PassType::INFERENCE:` block** — change the existing `if ( !pass.get_model() )` branch's `return outcome::failure( Error::PROCESS_INFO_MISSING )` to `return outcome::failure( Error::MODEL_MISSING )` (keep the existing logger call unchanged). Immediately after that check (model now confirmed present), add a new check: if `pass.get_model().value().get_format() != ModelFormat::MNN`, log an error naming the actual format (e.g. via `m_logger->error(...)` including `pass.get_model().value().get_format()` or the pass name) and `return outcome::failure( Error::MODEL_FORMAT_UNSUPPORTED )`. This is the fix for Gap 4 (`RejectUnsupportedModelFormat`, which submits `format: "ONNX"` — a value that *parses successfully* into `ModelFormat::ONNX` since ONNX is a recognized enum value, so it can only be rejected by this explicit business-rule check, not by JSON parsing).

**2. `CheckProcessValidity()`, `case PassType::RENDER:` block** — change only the `if ( !pass.get_render_shader() )` branch's `return outcome::failure( Error::PROCESS_INFO_MISSING )` to `return outcome::failure( Error::RENDER_SHADER_MISSING )` (keep the existing logger call and the other RENDER-case checks — `render_target`, `vertex_buffer`, `vertex_layout` — unchanged; no test currently requires those to be granular).

**3. `Init()`'s parse `try` block** — insert new validation logic immediately after `auto data = nlohmann::json::parse( jsondata );` and *before* `sgns::from_json( data, processing_ );` (both currently on adjacent lines). This must run before `sgns::from_json` because that call is what throws (as a plain `std::runtime_error`, not a `nlohmann::json::exception`, losing all context) when it encounters a `passes[].type` or `passes[].model.format` string outside the schema's recognized enum values — the goal is to catch these specific cases first, with a message that names the failure category, before the generic parse exception handler discards the context entirely. Logic:
   - If `data` contains a key `passes` and that value `is_array()`: for each entry in that array that `is_object()` and contains a `type` key whose value `is_string()`, read that string. If it is not one of the 5 recognized `PassType` strings (`compute`, `data_transform`, `inference`, `render`, `retrain` — verified against `Generators.hpp`'s `from_json(PassType&)`), log an error naming the actual unrecognized string and `return outcome::failure( Error::UNKNOWN_PASS_TYPE )` immediately (do not continue to `sgns::from_json`).
   - For that same pass entry, if its recognized `type` string is `inference` or `retrain`, and it contains a `model` key whose value `is_object()`, and that object contains a `format` key whose value `is_string()`: read that string. If it is not one of the 4 recognized `ModelFormat` strings (`MNN`, `ONNX`, `PyTorch`, `TensorFlow` — verified against `Generators.hpp`'s `from_json(ModelFormat&)`), log an error naming the actual unrecognized string and `return outcome::failure( Error::MODEL_FORMAT_UNSUPPORTED )` immediately. (Recognized-but-non-MNN formats like `ONNX` are intentionally NOT rejected here — they parse successfully and are instead rejected by Task 2's change #1 in `CheckProcessValidity()`, which runs after the normal parse succeeds.)
   - If `data` has no `passes` array, or a given pass entry lacks a `type` string, skip validation for that entry and fall through unchanged to the existing `sgns::from_json( data, processing_ )` call and its existing catch blocks — this preserves current behavior for `EmptyJobDefinition` (`{}`) and `MissingPassesArray` (no `passes` key), which must continue to fail via the existing generic `Error::INVALID_JSON` path exactly as before.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Raw job-definition JSON → ProcessingManager::Init() | Untrusted caller-submitted JSON; the new pre-parse scan reads raw string fields defensively (type/is_object/is_string guarded) before any typed parsing occurs |
| Error message strings → outcome::result caller | Error text is surfaced to whatever submitted the job; must name the problem field without leaking internal state |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-09-21 | Denial of Service | Init() pre-parse raw-JSON scan | medium | mitigate | All new nlohmann::json accesses are guarded with `.is_object()`/`.is_array()`/`.is_string()`/`.contains()` checks before dereferencing, so a malformed/adversarial `passes` array cannot throw an unhandled exception or infinite-loop; malformed entries fall through unchanged to the existing try/catch |
| T-09-22 | Information Disclosure | New granular error messages | low | accept | Messages name only schema field categories (`model`, `format`, `shader`, `type`) already present in the caller's own submitted JSON — no internal server state, paths, or stack traces are exposed |
| T-09-23 | Elevation of Privilege | Model-format executability bypass (Gap 4) | high | mitigate | Explicit `ModelFormat::MNN` equality check in `CheckProcessValidity()` closes the path where a recognized-but-unsupported format (ONNX/PyTorch/TensorFlow) would otherwise reach `CanExecute()`/`Process()` unrejected |
