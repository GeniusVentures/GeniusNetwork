<objective>
Close Gap 2 (confirmed cross-phase production gap, TEST-07): `ProcessingManager::Process()` has exactly one public signature and it constructs its own local, stack-scoped `ExecutionContext` — no caller can ever obtain a handle to that object, so no test (or future real caller) can call `.cancelToken.Cancel()` on it, or pre-set a deadline/budget before the call. Phase 07's `07-03` plan already wired every processor (`MNN_Buffer`, `RenderProcessor`, and others) to check `execCtx.cancelToken.IsCancelled()`, call `execCtx.progressCallback`, and enforce `execCtx.maxOutputArtifactBytes` — that machinery works correctly today. The only missing link is the entry point: `Process()` needs an overload that accepts a caller-owned `ExecutionContext`.

Purpose: let `SuperGenius/test/src/processing_conformance_cancellation/cancellation_conformance_test.cpp` (and any future real caller needing cooperative cancellation) actually exercise cancellation, budget enforcement, and progress callbacks through the real pipeline for at least one MNN processor and the Vulkan RenderProcessor — the plan's own original must-have that 09-VERIFICATION.md found was never met.

Output: a new `ProcessingManager::Process()` overload accepting `ExecutionContext&`, delegating (alongside the unchanged legacy overload) to a shared private `ProcessInternal()`; a rewritten `cancellation_conformance_test.cpp` with 6 cases that genuinely exercise cancellation/budget/progress for MNN and Vulkan; an honest cross-reference update to `SGProcessingManager/test/execution/cancellation_test.cpp`'s remaining `GTEST_SKIP()`'d cases.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Caller-supplied ExecutionContext → ProcessingManager::Process() (new 5-arg overload) | A new public API surface; the caller now controls cancellation/budget/deadline fields directly rather than ProcessingManager owning them exclusively |
| execCtx.cancelToken.IsCancelled() → processor StartProcessing() | Already-established Phase 07 boundary; this plan does not change it, only exposes a way to trigger it externally |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-09-29 | Tampering | New 5-arg `Process()` overload could let a caller silently bypass schema-derived budgets by pre-setting nonzero values | medium | mitigate | Documented, intentional design: `0` is the existing "unset" sentinel per `execution_context.hpp`; a caller setting a nonzero value is an explicit, visible choice (not a bypass — the caller owns their own execution and cannot affect any OTHER job's budget), and the schema-derived default is still applied whenever the caller leaves the field at `0` |
| T-09-30 | Denial of Service | A caller could supply an `ExecutionContext` whose `cancelToken` is never checked/cancelled, but that is identical to today's existing behavior for the legacy 4-arg overload (no new exposure) | low | accept | No new DoS surface — the legacy path already has this property; the new overload does not remove any existing check |
| T-09-31 | Repudiation | If a future caller re-uses the same `ExecutionContext` object across multiple `Process()` calls, a stale `cancelToken.IsCancelled()==true` from a prior cancelled run could silently cancel a later, unrelated run | medium | mitigate | This task's own test cases (`ResourcesCleanedUpAfterCancelledRun`) always construct a fresh `ExecutionContext` per `Process()` call, demonstrating and documenting the correct usage pattern; `CancellationToken` has no reset method by design (D-02), reinforcing one-context-per-job |

</threat_model>
