Per D-06, D-07(a)(b)(d): create `SuperGenius/test/src/processing_conformance_cancellation/` with:

**CMakeLists.txt** — `addtest()` macro, link `nlohmann_json` + `ProcessingBase` + `SGExecution`. Reuse fixtures from `processing_datatypes/`.

**cancellation_conformance_test.cpp** — inherits `ProcessorConformanceFixture`. Test suite `CancellationConformanceTest`.

Test cases (TEST-07, minimum coverage: 1 MNN + 1 Vulkan processor):

1. `CancelMnnMidExecution` — Create ProcessingManager with a known MNN fixture (reuse `buffer-processing-definition.json`). Create `ExecutionContext` with a `CancellationToken`. Start `Process()` in a separate thread. Cancel the token after a short delay (50ms). Join the thread. Assert: (a) `Process()` returns a terminal result (not success), (b) the result indicates cancellation, (c) progress events were emitted before cancellation (at least one progress callback invoked). Per D-07(a): "StartProcessing accepts ExecutionContext and respects cancel callback."

2. `CancelVulkanMidExecution` — Same pattern for RenderProcessor. Requires GPU — use `GTEST_SKIP()` if `!HasUsableVulkanDevice()` (per D-05). Otherwise identical assertions to CancelMnnMidExecution.

3. `ResourcesCleanedUpAfterCancel` — After cancellation, verify no dangling resources. This is verified by running the same job again immediately after cancellation — if resources leaked, the second run would fail or produce corrupted output. A successful second run implies cleanup. Also verify `RunTeardown()` was called (per D-07(d)) — if the ProcessingManager exposes a teardown-invoked flag or can be queried for active processor count, assert it's zero.

4. `ProgressEventsEmitted` — Run a job with a progress callback that records events. Assert: at least 2 progress events were emitted, each has `pass_id`, `stage_name` (non-empty), `percent` (0.0–100.0), and the sequence is monotonic (each percent >= previous). Per D-07(b): "progress events at stage boundaries."

5. `DeadlineExpiryProducesTimeout` — Create ExecutionContext with a 1ms deadline. Run Process(). Assert: result indicates timeout (not cancellation, not budget-exceeded). Per TEST-07: "deadline expiry produces distinct typed timeout failure."

6. `BudgetExceededProducesBudgetFailure` — Create ExecutionContext with a tiny output-size budget (e.g., 1 byte). Run Process(). Assert: result indicates budget-exceeded. Per TEST-07: "budget exceeded produces distinct failure."

7. `NoSuccessfulResultAfterCancel` — The critical assertion from TEST-07: cancel mid-execution → verify `Process()` result is NOT a success. The result must carry a terminal state of CANCELLED, not COMPLETED.

For the MNN cancellation test, use `buffer_tiny.mnn` (fast, deterministic). For Vulkan, use a render pass with the pass-through shaders from Plan 09-01 (also fast). The separate-thread pattern uses `std::thread` + `std::atomic<bool>` for coordination.

Test cases (TEST-08):

1. `AcceptValidInferenceJob` — Create ProcessingManager with valid MNN fixture → call `CanExecute()` → assert `is_executable == true`, rejection reasons list is empty.

2. `AcceptValidRenderJob` — Create with valid render pass → `CanExecute()` → `is_executable == true`. Requires GPU — `GTEST_SKIP()` if no device (D-05).

3. `RejectUnsupportedVulkanFeature` — Render pass requiring a Vulkan feature the device doesn't have (e.g., `tessellationShader: true` or `geometryShader: true` when unavailable) → `CanExecute()` → `is_executable == false`, rejection reason mentions the specific feature "tessellation" or "geometry". Distinct, human-readable. Per TEST-08.

4. `RejectUnsupportedModelFormat` — Pass with `model.format: "ONNX"` (not MNN) → `CanExecute()` → `is_executable == false`, reason mentions "ONNX" or "model format". Per TEST-08.

5. `RejectUnsupportedPassType` — Pass with an unregistered `PassType` → either `ProcessingManager::Create()` fails (schema validation) or `CanExecute()` rejects. Assert rejection reason names the pass type. Per TEST-08.

6. `RejectMissingExecutor` — Valid PassType but no executor factory registered for it → `CanExecute()` → rejection reason mentions "executor" or "not found". Per TEST-08.

7. `RejectionReasonsAreDistinct` — Run capability checks for 4 different rejection scenarios (Vulkan feature, model format, pass type, missing executor) → verify all 4 rejection messages are different strings (not identical generic messages). Per TEST-08: "each produces a distinct, human-readable rejection reason."

For test cases that need specific Vulkan features: construct `CapabilitySnapshot` mocks following the pattern from `capability_validator_test.cpp` (`MakeMockSnapshot()`). The CapabilityValidator's `CanExecute()` method should accept a snapshot override for testing.
