<objective>
Close Gaps 2 and 3 (TEST-01, both pre-existing, unrelated-to-Phase-09 bugs found while investigating `processing_dispatch_test`, root-caused in `.planning/debug/processing-dispatch-test-failure.md`):

- Gap 2 ("Bug A"): under `ctest`, `processing_dispatch_test`'s working directory does not match where its GLSL/JSON fixtures are actually copied (`$<TARGET_FILE_DIR:processing_dispatch_test>/processing_dispatch/`), because `addtest()`'s `add_test()` call has no explicit `WORKING_DIRECTORY`. This makes 4 render-pass sub-tests fail with a spurious "#version: Desktop shaders... require version 140" error (an empty shader-source buffer reaching shaderc, not a real GLSL problem) -- but only under `ctest`, not under direct `.exe` invocation, which is why this was never caught before.
- Gap 3 ("Bug B"): `RenderPassEndToEndProducesVerifiedOutputHash` asserts a populated 32-byte `combinedHash`, but `render-pass-happy-path-definition.json` (authored in Phase 03, before the Phase-08 artifact/manifest/`combinedHash` mechanism existed) declares `"outputs": []`, so `ProcessingManager::Process()`'s `!outputs.empty()`-gated artifact/manifest assembly block never fires for this fixture and `combinedHash` stays empty even though the render pipeline genuinely succeeds. The sibling test `RenderPassSameNodeRepeatedExecutionProducesBitExactHash` only compares iterations to each other, so it passes vacuously on 10 empty hashes and silently masks this bug.

Purpose: fix the CTest working-directory mismatch narrowly (scoped to this one target, not the ~60 other SuperGenius ctest targets sharing the same `addtest()` helper), and give the happy-path render fixture a real declared output so the existing, already-correct Phase-08 artifact/manifest pipeline can do what it was built to do -- produce a genuine content-derived hash of the render pass's actual output, using the exact same fixture pattern already proven to work in `processing_conformance_regression`'s `regression-b-parseblocksize-model-only.json`.

Output: `processing_dispatch_test`'s full 11-case suite passes under `ctest` in the SuperGenius submodule-consumption build; the "bit-exact repeat run" test can no longer pass vacuously.
</objective>

  <action>
Root cause (per the referenced debug session): `addtest()` in `cmake/functions.cmake` calls `add_test()` with no explicit `WORKING_DIRECTORY`, so CTest defaults `processing_dispatch_test`'s working directory to the source-tree-mirrored build path (`build/Windows/Release/test/src/processing_dispatch`), which has no `processing_dispatch/` fixture subfolder. The fixtures are actually copied by this file's own POST_BUILD command to `$<TARGET_FILE_DIR:processing_dispatch_test>/processing_dispatch/` -- the binary's own output directory. Under the wrong ctest-default cwd, the shader-source `file://processing_dispatch/*.glsl` fetches fail, an empty buffer reaches shaderc, and shaderc reports a spurious `#version` error instead of loading the real fixture GLSL.

Fix, entirely inside this one file: immediately after the existing `addtest(processing_dispatch_test\n    processing_dispatch_test.cpp\n)` call (before `target_include_directories`), add:

`set_tests_properties( processing_dispatch_test PROPERTIES WORKING_DIRECTORY "$<TARGET_FILE_DIR:processing_dispatch_test>" )`

This targets ONLY the `processing_dispatch_test` CTest target by name -- it does not touch `cmake/functions.cmake`'s shared `addtest()` helper, so none of the other ~60 SuperGenius ctest targets built through that helper have their working directory changed by this fix. The chosen directory is exactly `$<TARGET_FILE_DIR:processing_dispatch_test>`, the same generator expression this file's own POST_BUILD copy command already uses as its fixture-copy destination -- guaranteeing the working directory always matches wherever the fixtures actually land, including across platforms/configs.

Do not modify `cmake/functions.cmake`. Do not add a `test_name` parameter or new option to `addtest()`/`addtest_part()` -- this is a single-target property override, not a reusable helper change.
  </action>

Root cause (per the referenced debug session): `render-pass-happy-path-definition.json` was authored in Phase 03, before the Phase-08 `ProcessOutput`/`Artifact`/`ExecutionManifest`/`combinedHash` mechanism existed, so it has always declared `"outputs": []`. `ProcessingManager::Process()`'s entire artifact/manifest/`combinedHash`-assembly block is correctly gated behind `!outputs.empty()` -- a job that genuinely declares no outputs has nothing to build typed artifact records from. The render pass itself already succeeds end-to-end and already produces a real, content-based `sha256` of its rendered pixels internally (`RenderProcessor::StartProcessing()`'s `result.hash` and `result.output_buffers`), but nothing routes that into `combinedHash` while `outputs` stays empty. The fixture's declaration simply never caught up to what the render pass actually produces.

Fix, in two files:

1. In `render-pass-happy-path-definition.json`, replace the empty `"outputs": []` array with one entry describing the render pass's actual rendered image, mirroring `regression-b-parseblocksize-model-only.json`'s already-proven pattern exactly:
   `"outputs": [ { "name": "renderOutput", "source_uri_param": "file://processing_dispatch/happy-path-render-output.raw", "type": "image" } ]`
   Do not add a `dimensions` or `format` field to this entry -- the reference fixture doesn't either, and `ProcessingManager.cpp`'s artifact-building loop derives `art.width`/`art.height`/`art.format` from the render pass's INPUT node metadata, not from the output entry itself. Leave every other field in this JSON file (inputs, passes, render_target, vertex_buffer, vertex_layout, pipeline_state) exactly as-is.
2. In `processing_dispatch_test.cpp`'s `RenderPassSameNodeRepeatedExecutionProducesBitExactHash` (currently around line 304, `allHashes.push_back( process_result.value().combinedHash );`), capture the per-iteration hash into a named local first and assert its size before pushing it: bind `process_result.value().combinedHash` to a local named `iterHash`, add an `ASSERT_EQ( iterHash.size(), 32u )` immediately before the `push_back`, with a failure message referencing the iteration index and explaining that a hash-equality-only comparison can pass vacuously on all-empty vectors, then push `iterHash` (not the original expression) into `allHashes`. Leave `RenderPassEndToEndProducesVerifiedOutputHash`'s existing `ASSERT_EQ( hash.size(), 32u )` check untouched -- it is already correct and will now genuinely exercise a real hash instead of failing on an empty one.

Do not modify `ProcessingManager.cpp`, `processing_processor_render.cpp`, or the `!outputs.empty()` gate itself -- both are already correct; only the fixture's declaration and the test's assertion strength change.
