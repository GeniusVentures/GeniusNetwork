<objective>
Close Gap 1 (TEST-01, confirmed pre-existing test-authoring defect, root-caused in `.planning/debug/capability-validator-reject-unregistered.md`): `CapabilityValidatorTest.RejectUnregisteredPassType` (standalone SGProcessingManager ctest build only — this test is never built into the SuperGenius submodule-consumption tree) fails because it asserts the rejection message contains either the substring "INFERENCE" or the digit "1", on the stale assumption that `PassType::INFERENCE`'s generated numeric value is 1. The actual quicktype-alphabetized enum (`generated/PassType.hpp`) makes `PassType::INFERENCE == 2`, and `CapabilityValidator::CanExecute()` never embeds the human-readable name anywhere in its message — only raw ints — so neither disjunct of the test's OR-assertion is satisfied.

Purpose: make `CanExecute()`'s PASS_TYPE rejection message genuinely self-describing (name + int, not int alone) so the test's original intent — "the rejection message should say which pass type is missing" — is actually met, and so a future reordering/addition to the generated `PassType` enum cannot silently break this assertion again the way the current numeric assumption did.

Output: `CapabilityValidatorTest.RejectUnregisteredPassType` passes deterministically in the standalone build; no other capability_validator_test case or the SuperGenius-side `capability_conformance_test` regresses.
</objective>

  <action>
Root cause (per the referenced debug session): the message-construction code in `CanExecute()`'s PASS_TYPE branch and in `ListAvailablePassTypes()` builds its text purely from `std::to_string(static_cast<int>(passType))` -- the literal pass-type name is never constructed anywhere in this code path. The test's assertion assumed `PassType::INFERENCE`'s underlying int was 1; it is actually 2 (quicktype alphabetizes the schema's enum for its C++ generator). The validator's actual rejection LOGIC is correct (category, unmet count, "Available" text, empty executorId all already pass) -- only the message's lack of a human-readable name, and the test's numeric assumption about that message, are wrong.

Fix, entirely inside these two files:

1. In `capability_validator.cpp`'s anonymous namespace, immediately before `ListAvailablePassTypes` (which currently starts at line 75), add a new helper `std::string PassTypeToString( PassType pt )` containing a `switch` over all five current generated values (`PassType::COMPUTE` -> "COMPUTE", `PassType::DATA_TRANSFORM` -> "DATA_TRANSFORM", `PassType::INFERENCE` -> "INFERENCE", `PassType::RENDER` -> "RENDER", `PassType::RETRAIN` -> "RETRAIN"), with no `default:` case inside the switch (so a future sixth enum value not yet handled here produces a compiler `-Wswitch` warning) but a fallback `return std::to_string( static_cast<int>( pt ) );` statement placed after the switch block for any value that falls through.
2. Change `ListAvailablePassTypes()`'s per-capability formatting (currently just `std::to_string(static_cast<int>(cap.passType))`) to `PassTypeToString( cap.passType ) + " (" + std::to_string( static_cast<int>( cap.passType ) ) + ")"`, so the "Available" list in the rejection message names each registered pass type as well as its int.
3. Change `CanExecute()`'s PASS_TYPE rejection message (currently `"No executor registered for PassType " + std::to_string(static_cast<int>(passType)) + ". Available: [" + ListAvailablePassTypes(...) + "]"`) to insert `PassTypeToString( passType ) + " (" + std::to_string( static_cast<int>( passType ) ) + ")"` in place of the bare int -- keeping the raw int alongside the name for existing log/debug consumers, while now genuinely containing the human-readable name.
4. In `capability_validator_test.cpp`'s `RejectUnregisteredPassType` (lines 126-127), the assertion currently checks two alternatives joined by `||`: one for the pass-type name being present, and a second, narrower disjunct that only happens to hold if the enum's underlying value equals a specific single-digit literal. Since the message now reliably contains the pass-type name regardless of the enum's numeric layout, replace that two-disjunct `EXPECT_TRUE` with a single `EXPECT_TRUE( result.unmet[0].detail.find( "INFERENCE" ) != std::string::npos )` -- keep the very next line's `EXPECT_TRUE(...find("Available")...)` assertion exactly as-is.

Do not change `UnmetRequirementCategory::PASS_TYPE`'s numeric value (`capability_types.hpp`, `= 2`) or any other enum's ordering -- this fix only touches message-formatting code and one test assertion; it does not touch `CanExecute()`'s actual PASS_TYPE-registration LOGIC (already correct per the debug session).
