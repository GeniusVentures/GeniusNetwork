<objective>
Close Gap 5 (confirmed pre-existing production bug, TEST-04): `StringInputProcessingTest` (pre-existing, using the legacy `bert-tiny.mnn` model) and `StringConformanceProcessingTest` (added by Plan 09-02, using the new tiny embedding model) both fail identically with `"Reshape error: 32 -> 4"`, `"Compute Shape Error for /fc/Gemm_output_0"`, `"Can't run session because not resized"`. Root-caused to `processing_processor_mnn_string.cpp`'s per-tensor resize heuristic (`tensor->elementSize() <= 4`), which was written for the legacy multi-input BERT model's tiny default placeholder shapes and unconditionally force-resizes to a hardcoded `maxLength = 128` — breaking the new tiny embedding model's fixed-shape fully-connected layer (`Linear(seq_len(16) * embed_dim(8) = 128, 4)`, compiled for exactly 16 input tokens) whenever the resize decision or target length doesn't match what that layer expects.

Purpose: fix the resize decision to be driven by the ACTUAL number of tokens available (already clamped to the existing `maxLength=128` ceiling), not an arbitrary elementSize threshold or a hardcoded constant — generalizing correctly to both models — and harden `runSession()`'s previously-discarded return code so any remaining shape-inference failure surfaces cleanly instead of silently reading garbage tensor memory.

Output: both previously-failing string-processor tests pass; the other 17 MNN processor conformance cases in `processing_datatypes_test` are unaffected (no shared code touched).
</objective>

  <action>
Root cause (confirmed by reading the model-generation script and both fixture JSONs): the resize decision at `Process()`'s line 193 (`if ( tensor->elementSize() <= 4 )`) was written for the legacy multi-input BERT model's tiny default placeholder shapes and unconditionally resizes any matching tensor to `{1, maxLength}`, where `maxLength` is the hardcoded literal `128` from `StartProcessing()`'s line 69 — regardless of how many tokens were actually parsed. The tiny embedding model's single input tensor and its `fc = Linear(128, 4)` layer are compiled for a FIXED sequence length of 16 (`seq_len(16) * embed_dim(8) = 128` input features); resizing that tensor to anything other than 16 changes the embedding layer's flattened output size and breaks the `fc` layer's fixed-128-input-feature assumption, producing MNN's internal shape-inference failure inside `resizeSession()` (uncorrected today, since its return isn't checked) and the subsequent `runSession()` failure once the invalid session state is used.

Fix, entirely inside this one file:

1. In `MNN_String::StartProcessing()`, immediately after the `tokenIds` vector is fully populated (after the `if ( parsedTokenIds ) {...} else {...}` block ends, before the `auto procresults = Process( tokenIds, modelFile_bytes, maxLength );` call), add `const int resizeLen = std::max( 1, static_cast<int>( tokenIds.size() ) );` and change that call site to `Process( tokenIds, modelFile_bytes, resizeLen )` — passing the actual, already-clamped token count (bounded by the existing `maxLength = 128` ceiling a few lines above) instead of the raw constant.

2. In `MNN_String::Process()`, change the per-tensor resize condition at line 193 from `if ( tensor->elementSize() <= 4 )` to `if ( tensor->elementSize() != maxLength )` (the function's `maxLength` parameter is now the caller-supplied `resizeLen`) — resize whenever a tensor's CURRENT size does not already match the desired sequence length, instead of an arbitrary `<= 4` threshold. Leave the resize target itself (`interpreter->resizeTensor( tensor, { 1, maxLength } );`) textually unchanged — only the caller-supplied VALUE flowing into `maxLength` changes, via fix #1. This generalizes correctly to both models: the tiny model's single input already defaults to `elementSize() == 16` (matching `resizeLen` when `tokenIds.size() == 16`), so it now correctly SKIPS an unnecessary and harmful resize; the legacy BERT model's three inputs all still get resized uniformly to the same `resizeLen`, exactly as before, just driven by the real token count instead of a hardcoded 128.

3. Add the missing return-code check on `runSession()` at line 243: capture `MNN::ErrorCode runResult = interpreter->runSession( session );` and, if `runResult != MNN::NO_ERROR`, log via `m_logger->error( "MNN runSession failed with ErrorCode {}", static_cast<int>( runResult ) );` and `return std::make_unique<MNN::Tensor>();` — matching this function's existing early-return-on-failure style (lines 148-151, 163-166, 184-187, 247-250). This prevents any remaining or future shape-inference failure from silently reading/hashing garbage tensor memory instead of cleanly failing.

4. In `MNN_String::StartProcessing()`, immediately after the `Process()` call, add a guard before the existing unconditional `procresults->host<float>()` dereference: `if ( !procresults || procresults->elementSize() == 0 ) { m_logger->error( "MNN string processing produced no output (see prior errors)" ); ProcessingResult errResult; errResult.error = ProcessingError{ ProcessingErrorStage::UNSPECIFIED, "MNN string processing produced no output" }; return errResult; }` — hardens against the sentinel empty-`Tensor` return added by fix #3 (and any pre-existing early-return path already inside `Process()`) so a processing failure surfaces as a structured `ProcessingResult.error`, not a null-pointer/zero-size dereference.

Do not add `PushTeardown()`/`RunTeardown()` calls to this file. `MNN_String` currently has neither anywhere in this file (confirmed by read_first) — retrofitting Phase 07's teardown-stack pattern into this processor is a separate, out-of-scope hardening effort; Gap 5's authorized scope is the resize/reshape bug specifically. Note this as a discovered follow-up item in the plan's completion summary; do not fix it here.
