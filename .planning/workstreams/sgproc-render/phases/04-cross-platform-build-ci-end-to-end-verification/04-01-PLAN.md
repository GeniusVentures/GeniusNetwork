<objective>
Add a runtime GPU probe (`sgns::sgprocessing::HasUsableVulkanDevice()`) that mirrors `RenderProcessor::IsAcceptable`'s existing DISCRETE_GPU/INTEGRATED_GPU device-type filter, per 04-CONTEXT.md D-32/D-33/D-34. Use it to retrofit a clean `GTEST_SKIP()` guard onto the existing hard-failing `RenderPassSameNodeRepeatedExecutionProducesBitExactHash` test (D-34 explicitly requires this retrofit), and add a new, distinct single-run test (`RenderPassEndToEndProducesVerifiedOutputHash`) that satisfies E2E-01 -- a real render-pass job definition executed end-to-end through the actual `ProcessingManager`/`RenderProcessor` code path, producing a verified output hash -- kept conceptually separate from DETV-01's existing 10x bit-exact-repeat-run concern (04-CONTEXT.md D-35).

**Scope decision (D-35, planner's call per 04-CONTEXT.md's explicit deferral):** the new E2E-01 test reuses the existing `render-pass-happy-path-definition.json` fixture and `WriteHappyPathVertexData()` helper rather than authoring a new distinct fixture. That fixture already satisfies the project's real-job-definition-fixture convention (`processing_schema_test.cpp:210`'s `PosenetJobTest` precedent, per 04-PATTERNS.md); authoring a second, near-identical fixture file would add no additional proof value. The two tests differ in what they assert and how many times they run (single-run "did it work" vs. 10x "is it bit-exact every time"), not in which fixture they load.

Purpose: prove the render path executes end-to-end on real hardware and fails visibly (not silently, not by hard-crashing CI) when hardware is absent -- the foundation both plan 04-02 (CI-level annotation) and plan 04-03 (regression confirmation) build on.
Output: `vulkan_gpu_probe.hpp`/`.cpp` (new), `RenderProcessor::IsAcceptable` made public, `processing_dispatch_test.cpp` gains a skip-guard on the existing determinism test plus one new E2E-01 test case.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Test binary process ↔ host Vulkan driver/loader | `HasUsableVulkanDevice()` and `RenderProcessor::InitializeContext()` both create a real `VkInstance`/enumerate physical devices against whatever ICD is installed on the runner -- untrusted host environment, not attacker-controlled input |
| Concurrent test threads ↔ shared VulkanInitMutex | The probe is a new caller of the same process-wide lock CTX-02 established; a bug here could reintroduce a race the Phase 1 concurrency test already closed |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-01 | Denial of Service | `HasUsableVulkanDevice()` | low | mitigate | Function is only called once per GPU-gated `TEST_F` invocation (not in a loop/hot path), and always releases `VulkanInitMutex()` via RAII `std::lock_guard` before returning, including on every early-return failure path -- no lock leak, no unbounded contention |
| T-04-02 | Tampering | Shared `VulkanInitMutex()` invariant | medium | mitigate | The probe's `vkb::InstanceBuilder::build()` call is placed strictly inside the `std::lock_guard` scope (task's explicit acceptance criterion greps for `VulkanInitMutex` presence in the new `.cpp`), preventing a new unguarded Vulkan-init call site from being introduced that CTX-02's existing concurrency test would not know to cover |
| T-04-03 | Information Disclosure | `GTEST_SKIP()` message text | low | accept | The skip message only names a device-type filter (DISCRETE_GPU/INTEGRATED_GPU) and test intent; it discloses no host-identifying or credential information, and is only visible in this repo's own CI logs/xunit output |

</threat_model>
