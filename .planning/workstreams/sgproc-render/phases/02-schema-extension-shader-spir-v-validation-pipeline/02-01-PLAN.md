<objective>
Fix the pre-existing, currently-blocking JSON syntax bug in `gnus-processing-schema.json`, then extend the schema so a render pass can fully describe a render target, a multi-stage (vertex+fragment) shader pipeline, a vertex buffer binding + vertex attribute layout + an optional index buffer, and fixed-function pipeline state — and regenerate the quicktype C++ headers from it with zero hand-edits.

This plan's exact schema edit was verified end-to-end in a throwaway scratch spike before being written into this PLAN: a copy of the real (buggy) schema was fixed and extended exactly as specified below (including this revision's `vertex_buffer` addition), then run through this machine's actually-installed `quicktype` (v23.2.6) using the identical invocation `.github/workflows/generate-headers.yml` uses. The resulting class/enum names and optional-vs-required member shapes documented in this plan's tasks and `must_haves` are the REAL, CONFIRMED output of that spike, not a guess — reproduce the schema edit exactly as specified in Task 1 to get the identical result.

The single most important modeling decision here — recorded as **02-CONTEXT.md's "D-11 Amendment"** (read it before implementing; this paragraph is a summary, not the full record): `shader_config` is currently shared, unmodified, between `compute` and `render` pass types. During this plan's revision, THREE independent quicktype spikes were run against this machine's actual installed toolchain to find a construction that re-types the SAME property name `pass.shader` per pass type: (1) a nested `allOf`/`if`/`then` conditional `$ref` override on `pass.properties.shader` — confirmed to silently drop the `shader` member from `Pass` entirely; (2) a root-level `oneOf` on `pass` itself, discriminated by `pass.type` — confirmed to MERGE both branches into one ambiguous class rather than produce a discriminated union; (3) a fully disjoint-field `oneOf` (ruling out property-name overlap as the cause) — same merge behavior, unaffected by `--no-combine-classes`. No construction tried preserves `pass.shader` as a distinctly-typed member per pass type with this toolchain. Given that, the confirmed-working design keeps `shader` unchanged (compute-only, still `$ref: shader_config`) and adds render's new multi-stage shape under a DIFFERENT, new sibling property name, `render_shader` (`$ref: render_shader_config`), always-optional at the schema/codegen level exactly like `shader`/`model` already are today — with `CheckProcessValidity()` (plan 02-04) doing the actual pass-type-specific presence enforcement, matching the codebase's existing, only-working pattern (`pass.allOf`'s existing `required` conditionals already have zero effect on today's generated code — `Pass::shader`/`Pass::model` are `boost::optional` regardless).

A second, smaller amendment from the same revision — **02-CONTEXT.md's "D-16 Amendment"**: the original `vertex_layout_entry` (`{name, format, offset}`) named no buffer to source attribute data from, leaving SCHEMA-02's "buffer bindings" half unaddressed. This plan adds a new sibling definition, `vertex_buffer` (`{source}`, required, reusing `pass_io_binding`'s exact prefix-notation regex, mirroring `index_buffer`'s existing one-buffer-per-binding shape) — one `vertex_buffer` binding feeds every entry in `pass.vertex_layout`.

Purpose: Every other task in this phase (shader compilation/validation, ProcessingManager wiring, test fixtures) depends on these exact generated types existing.
Output: Fixed + extended `gnus-processing-schema.json`; fully regenerated `generated/*.hpp` (no hand-edits); the stale test-fixture copy of the schema kept in sync.
</objective>
