<objective>
Wire plan 02-03's `ShaderCompiler` into `ProcessingManager`, completing SHADER-01/02/03's "before any GPU call is made" guarantee at its actual integration point (`GetCidForProc`, which runs at job-load time before any processor is invoked), and extend `CheckProcessValidity()`'s render-pass branch to match plan 02-01's new schema fields (`render_shader`/`render_target`/`vertex_layout`), replacing the now-obsolete `pass.get_shader()` check used for render passes.

`GetCidForProc`'s existing "modelFile" single-URI-then-fetch lambda (`ProcessingManager.cpp:864-871` today) fetches exactly one shader source. For a render pass, this must become: fetch each `render_shader.stages[]` entry's source independently (queued together with the existing image fetch, so the single existing `ioc->run()` call still drains everything in one pass — no new synchronization primitive needed), then run each stage's fetched bytes through `ShaderCompiler::CompileAndValidate` before anything is considered usable. The validated per-stage SPIR-V is then packed into the existing `mainbuffers->first` buffer slot using a small, explicitly-documented wire format (stage count, then per stage: a stage tag, a word count, and the raw validated SPIR-V words) — Phase 3's `RenderProcessor` has not been designed yet and does not currently consume this slot for render passes at all (today it ignores both `imageData`/`modelFile` parameters entirely, per `01-04-PLAN.md`'s stub), so this format is this plan's own choice, clearly commented as provisional, not a negotiated Phase-3 contract; Phase 3's planning may revise it once `RenderProcessor`'s actual pipeline-construction needs are known.

A second, independently-necessary fix bundled here because it is a direct, immediate consequence of plan 02-01's schema-enum narrowing: `ProcessingManager::Create()`'s JSON parsing only catches `const nlohmann::json::exception &e` today. quicktype's generated enum `from_json` functions throw a plain `std::runtime_error` (not a `nlohmann::json::exception` subclass) when an enum value doesn't match — confirmed by direct inspection of `generated/Generators.hpp`'s existing `PassType`/`DataType` `from_json` bodies. Before plan 02-01, this path was never exercised for `shader_config.type`/`shader_stage.type` because `hlsl`/`metal` were valid enum values; after narrowing to `glsl`/`spirv` only, a legacy or malicious job submitting `hlsl`/`metal` would throw an uncaught `std::runtime_error` straight out of `Init()`/`Create()` — a real, newly-live crash, not merely a hypothetical one. `Create()`'s catch clause must broaden to also catch `const std::exception &e`, returning the existing `Error::INVALID_JSON`, closing this before it can ever be observed in the wild.

Purpose: Complete SHADER-01/02/03's end-to-end guarantee — validated-before-driver, wired into the actual job-processing path, not just proven in isolation.
Output: Updated `ProcessingManager.hpp`/`.cpp`; updated/new test fixtures and dispatch tests proving the full path (valid, malformed-GLSL, invalid-direct-SPIR-V) end-to-end.
</objective>
