```cpp
namespace sgns::sgprocessing {

using CanExecuteCallback = std::function<void(CanExecuteResult)>;

class CapabilityValidator {
public:
    CapabilityValidator();

    // Build the capability snapshot once at startup (D-09, D-12).
    // Called by ProcessingManager::Init() after all Register* calls.
    // Acquires VulkanInitMutex internally (D-10).
    // @param passFactories — reference to ProcessingManager's m_passFactories,
    //        used to enumerate registered PassType→executor mappings (D-11)
    // @param mnnProcessorCount — number of registered MNN processors (DataType-keyed),
    //        used for MNN backend capability declaration
    // @param ensureVulkanDevice — callable that ensures Vulkan device exists and returns
    //        the VkPhysicalDevice handle. ProcessingManager provides a lambda that calls
    //        RenderProcessor::InitializeContext() if not yet initialized (RESEARCH.md Q#1).
    void BuildSnapshot(
        const std::unordered_map<PassType,
            std::function<std::unique_ptr<ProcessingProcessor>()>,
            PassTypeHash>& passFactories,
        size_t mnnProcessorCount,
        std::function<VkPhysicalDevice()> ensureVulkanDevice);

    // Access the cached snapshot. Returns empty optional before BuildSnapshot().
    const CapabilitySnapshot* GetSnapshot() const;

    // CanExecute will be in Plan 06-02 — declared here for header completeness.
    // void CanExecute(const sgns::SgnsPass& pass, CanExecuteCallback callback);

private:
    // Fwd-declare in header; implementation details in .cpp
    struct Impl;
    std::unique_ptr<Impl> m_impl;
};

} // namespace sgns::sgprocessing
```

**A) `SuperGenius/SGProcessingManager/src/capability/capability_validator.cpp`:**

Implement `CapabilityValidator::BuildSnapshot()`:

1. Acquire `std::lock_guard<std::mutex> lock(sgns::sgprocessing::VulkanInitMutex())` (D-10).

2. **Vulkan device query (D-14):** `BuildSnapshot` receives a `VkPhysicalDevice` handle from `RenderProcessor` after ensuring its lazy initialization. The approach: call `RenderProcessor::InitializeContext()` under `VulkanInitMutex` if the device hasn't been initialized yet (RESEARCH.md Open Q#1 resolution — trigger lazy init during snapshot build). Once the device handle exists, call `vkGetPhysicalDeviceProperties(device, &props)` and `vkGetPhysicalDeviceMemoryProperties(device, &memProps)`.

   Do NOT create a temporary Vulkan instance — D-10 explicitly prohibits this ("Reuse existing VkPhysicalDevice — no temporary Vulkan instance"). The correct approach: `BuildSnapshot` takes a reference to the `RenderProcessor` (or a `std::function<VkPhysicalDevice()>` getter) that ensures `InitializeContext()` is called, then queries the existing device. The `VulkanInitMutex` serializes this against any concurrent RenderProcessor init.

3. **MNN registry query (D-11):** Iterate `passFactories` to collect registered `PassType`→executor mappings. For MNN processors (DataType-keyed), declare capabilities based on `mnnProcessorCount`: all MNN processors on Vulkan backend (D-13/MIGR-01), format ".mnn", quantizations ["FP32", "FP16", "INT8"]. For RenderProcessor (PassType::RENDER): backend "VULKAN", no model format/quantization (render passes don't use MNN models).

4. **Executor identity hash (D-08):** Serialize `vulkanProps.deviceID`, `vulkanProps.driverVersion`, `vulkanProps.vendorID`, `vulkanProps.deviceName`, `memProps.memoryHeapCount`, each heap's `size` and `flags`, and each `ExecutorCapability`'s fields into a contiguous `std::vector<uint8_t>`. Hash with `sgns::sgprocmanagersha::sha256(data.data(), data.size())`. Store in `snapshot.identityHash`.

5. **Disk space (D-16 stub):** Query available disk space for the output directory. Use `#ifdef _WIN32` / `GetDiskFreeSpaceExW` on Windows, `<sys/statvfs.h>` on POSIX. If query fails, set `availableDiskBytes = 0` (degraded mode — disk check in CanExecute will always pass). Store path: use a configurable default or `"."` (current working directory).

6. Store the completed `CapabilitySnapshot` in `m_impl->snapshot`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Vulkan driver → CapabilityValidator | Untrusted Vulkan device properties — driver could report incorrect limits |
| MNN executor registration → CapabilityValidator | Trusted (same process, registry populated by ProcessingManager::Init()) |
| File system → CapabilityValidator | Disk space query is advisory — filesystem could be exhausted between check and use |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-01 | Tampering | Vulkan driver reporting inflated limits | accept | No practical mitigation — if driver lies about limits, job will fail at runtime; capability check is pre-flight, not security boundary |
| T-06-02 | Denial of Service | Disk space exhaustion between check and use | accept | Advisory check only — D-16 explicitly acknowledges TOCTOU; caller's responsibility to have headroom |
| T-06-03 | Information Disclosure | Vulkan device properties in snapshot | accept | Device properties (vendorID, deviceName, driverVersion) are not secrets — same data visible via vulkaninfo |
| T-06-SC | Tampering | No new npm/pip/cargo packages | mitigate | Zero new external packages — all dependencies already vendored in thirdparty/ |
</threat_model>
