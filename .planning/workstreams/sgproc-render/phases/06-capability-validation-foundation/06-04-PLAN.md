<objective>
Wire the Vulkan validation layer toggle as a CMake-controlled, best-effort, debug-only feature for `RenderProcessor`'s `VkInstance`.

Purpose: Replace the hardcoded `request_validation_layers(false)` in `RenderProcessor::InitializeContext()` with a compile-time `#ifdef` gate controlled by a CMake `option(ENABLE_VULKAN_VALIDATION ...)`. Defaults ON in Debug, OFF in Release (D-24). Best-effort semantics: if the layer isn't available on the system, instance creation proceeds without it (D-20). Only RenderProcessor's instance is affected (D-22).

Output: Modified `CMakeLists.txt` with option + compile definition, modified `processing_processor_render.cpp` with conditional gate.
</objective>

```cmake
    message(STATUS "Vulkan validation layers: ENABLED (best-effort)")

endif()
```

Use `PUBLIC` for the compile definition so any downstream consumer of SGProcessors also sees the define (though only RenderProcessor checks it per D-22).


Replace `.request_validation_layers( false )` with:

```cpp
#ifdef ENABLE_VULKAN_VALIDATION
                    .request_validation_layers()           // best-effort (D-20, D-21)

#endif
```

**Why `request_validation_layers()` (no argument) instead of `request_validation_layers(true)`:**

Per vk-bootstrap API (verified in `thirdparty/vk-bootstrap/src/VkBootstrap.cpp:823`), `request_validation_layers()` with no argument defaults to `true`, but more importantly, `request_validation_layers(true)` still uses best-effort semantics — vk-bootstrap only adds `VK_LAYER_KHRONOS_validation` to the enabled layers list, and the Vulkan loader simply skips layers that aren't installed. Using the no-argument form is idiomatic vk-bootstrap and matches D-20's best-effort requirement.

Per D-21: loads `VK_LAYER_KHRONOS_validation` by name through vk-bootstrap.
Per D-22: only RenderProcessor's VkInstance is affected — MNN's Vulkan instances in other processors are not touched.
Per D-20: no vendoring — layers must be installed on the system (Vulkan SDK on desktop, NDK on Android, MoltenVK built-in on macOS/iOS).

**Logging improvement (optional):** Add a log message when validation layers are requested:
```cpp
#ifdef ENABLE_VULKAN_VALIDATION
                    .request_validation_layers()
                    // Log that we're requesting layers (best-effort — no error if missing)
#else
                    .request_validation_layers( false )
#endif
```

No other changes to InitializeContext() — the rest of the Vulkan init flow is unchanged.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| System → Vulkan loader | Validation layers loaded from system paths — if system is compromised, layers could be tampered |
| CMake option → compile definition | Build-time only — attacker cannot enable layers at runtime without rebuild (defense-in-depth) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-10 | Elevation of Privilege | Malicious validation layer on system path | accept | Validation layers are debug-only; production builds disable them entirely. If an attacker can place files on the system Vulkan layer path, the node is already compromised. |
| T-06-11 | Information Disclosure | Validation layer output in production | mitigate | Release builds compile out validation layer requests entirely (`request_validation_layers(false)`); no layer output possible in production |
| T-06-12 | Denial of Service | Missing validation layer blocking instance creation | mitigate | Best-effort semantics (D-20): vk-bootstrap's `request_validation_layers()` only adds the layer if available; missing layer → instance creation proceeds without it |
</threat_model>
