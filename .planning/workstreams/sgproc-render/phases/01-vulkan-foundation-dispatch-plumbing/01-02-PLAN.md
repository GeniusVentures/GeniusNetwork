**Decision (D-01), made here per RESEARCH.md's Decision Point with concrete trade-off data supplied**: Adopt **Option A — vk-bootstrap** (MIT, `charles-lunarg/vk-bootstrap`), not hand-rolled bootstrap. Rationale: CTX-01 mandates macOS/MoltenVK support as a hard requirement, and this project's CI has zero macOS Vulkan signal today (a documented, pre-existing gap, not fixed until Phase 4) — a hand-rolled implementation's most likely failure mode (missing the `VK_KHR_portability_enumeration`/`VK_KHR_portability_subset` dance) is silent and platform-specific in exactly the platform this project has the least test coverage for. vk-bootstrap is a thin builder returning raw `VkInstance`/`VkPhysicalDevice`/`VkDevice`/`VkQueue` handles — it does not abstract the Vulkan API surface, so it does not reopen the "no new GPU backend" concern that disqualified the archived bgfx attempt. This decision is not re-opened as a checkpoint; only the resulting vendoring action is gated below.

Purpose: Confirm vk-bootstrap's legitimacy (correct upstream repo, not a fork/typosquat; current tag; MIT license) with a live check before plan 01-03 actually runs `git submodule add`.
