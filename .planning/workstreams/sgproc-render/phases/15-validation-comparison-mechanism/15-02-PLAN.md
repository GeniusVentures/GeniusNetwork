<objective>
Fix `ProcessingValidationCore::ValidateResults`'s concatenation bug (chunk-hash bytes from different subtasks silently appended into one shared buffer instead of compared) and extend it with a bounded numeric-tolerance fallback: on a genuine hash mismatch for the same chunk, fetch the underlying chunk data (via an injected capability, not yet wired to real I/O -- that is Plan 15-03) and compare it using Plan 15-01's `sgprocmanagerdiff` functions before declaring a real divergence.

Purpose: this is the actual defect XNODE-01b/XNODE-02 exist to fix. Keeping the fetch/tolerance-derivation *capabilities* as injected parameters (rather than reaching into `FileManager`/job-schema parsing directly) keeps this plan's scope to `ValidateResults`'s own comparison algorithm, fully testable with hand-constructed byte buffers -- no real MNN jobs, no real I/O, no real P2P needed yet.
Output: a fixed, tolerance-aware `ValidateResults` with a new signature (backward-compatible via defaulted new parameters), and a new, live `processing_validation_core_test.cpp` proving ROADMAP's SC1-SC4 directly.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Subtask results from other (potentially Byzantine) nodes -> ValidateResults | `chunk_hashes`/`ipfs_results_data_id` on every `SubTaskResult` are attacker-influenced fields (a malicious node controls its own submitted result). `ValidateResults` is exactly the trust boundary that must not assume a submitted result is correct -- this plan strengthens, not weakens, that boundary. |
| jobParameters (schema-declared quantScale/byteQuantMode) -> AttemptToleranceFallback's tolerance derivation | Same attacker-influenceable schema-parameters boundary Plan 15-01 already threat-modeled; this plan is the first runtime consumer that lets an invalid/degenerate declaration actually affect a security-relevant pass/fail decision. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-15-04 | Tampering | AttemptToleranceFallback's overall pass/fail decision | high | mitigate | This is the central risk XNODE-02 introduces: a malicious node could hope a loosened tolerance fallback masks corrupted data. Mitigated by (1) Plan 15-01's "zero elements may exceed threshold" comparison policy (not percentage-based), (2) this plan's own SC4 case proving an exceeding-tolerance mismatch still fails, and (3) Plan 15-04's SECV-02 full-pipeline counter-test against a real corrupted MNN model -- the three-layer proof RESEARCH.md's methodology calls for. |
| T-15-05 | Denial of Service | AttemptToleranceFallback's fetch-on-mismatch path | medium | mitigate | Guarded at every step: no fetch attempted at all when `fetchOutputData` is unset (D-02); any `outcome::failure` from the capability, or an empty `ipfs_results_data_id`, returns false (fail closed) rather than throwing, dereferencing an empty result, or retrying indefinitely. |
| T-15-06 | Tampering | Chunk-slicing on multi-chunk subtasks | medium | mitigate | Uniform-division slicing is attempted only when the fetched blob's size divides evenly by the subtask's chunk count; anything else (including overlapping-window jobs, which this phase does not attempt to detect from the wire protocol alone, per RESEARCH.md's Pitfall 3) fails closed rather than silently comparing the wrong byte ranges -- a documented, deliberate scope limit, not a silent correctness gap. |
