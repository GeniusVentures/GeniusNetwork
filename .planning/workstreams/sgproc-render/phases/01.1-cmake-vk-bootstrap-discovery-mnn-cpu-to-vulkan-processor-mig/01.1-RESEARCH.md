# Phase 01.1: CMake vk-bootstrap discovery, MNN CPU-to-VULKAN processor migration, and coverage - Research

**Researched:** 2026-07-29
**Domain:** CMake transitive-dependency propagation (`find_package`/exported-target resolution) + MNN inference-backend selection (`MNN::ScheduleConfig.type`) + test-coverage extension for a concurrency-sensitive migration
**Confidence:** HIGH — every claim below is grounded in direct source/CMake inspection of this repo (not external docs), since the whole phase is repo-internal wiring, not a new external technology.

## Summary

This phase bundles three concrete, independently-verifiable fixes, all discovered by reading the actual post-Phase-1 codebase rather than assumption:

1. **CMake vk-bootstrap discovery gap**: Phase 1 (commit `1acc6c6`, plan 01-03) added `find_package(vk-bootstrap CONFIG REQUIRED)` **only** to `SuperGenius/SGProcessingManager/cmake/CommonBuildParameters.cmake`. `SGProcessors` (the library containing all MNN/render processors) links `vk-bootstrap::vk-bootstrap` **PUBLIC**, so this dependency is transitively baked into `SGProcessingManagerTargets.cmake`'s exported interface. Both downstream consumers — `GeniusSDK/cmake/CommonBuildParameters.cmake` and `GeniusWallet/cmake/CommonBuildParameters.cmake` — call `find_package(SGProcessingManager CONFIG REQUIRED)` but **never call `find_package(vk-bootstrap ...)` themselves**, and `SGProcessingManager`'s `config.cmake.in` does not call `find_dependency(vk-bootstrap)` either. Any CMake configure of GeniusSDK or GeniusWallet against a submodule pointer that includes Phase 1's changes will fail with a "target `vk-bootstrap::vk-bootstrap` not found" configure-time error. This is a mechanical, 2-line-per-file fix in each of the two consumer files, mirroring the existing `MNN`/`Vulkan` `find_package` pattern already present in both.
2. **MNN CPU-to-VULKAN processor migration**: 3 of 15 MNN-backed processors already run on `MNN_FORWARD_VULKAN` (Image, String, Volume — all wrapped in the shared `sgns::sgprocessing::VulkanInitMutex()` from Phase 1/CTX-02). 12 files with 13 `createSession()` call sites are still hardcoded to `MNN_FORWARD_CPU` and unguarded (they don't need the mutex today because they never touch Vulkan — but they will once migrated). 2 files (`MNN_ML`, `MNN_Audio`) are unimplemented stubs with no `MNN::Interpreter`/`ScheduleConfig` at all and are **not** migration candidates. Migration is low-risk: the CPU processors already use the same `copyFromHostTensor`/`copyToHostTensor` host-tensor pattern the Vulkan-backend processors use (this is MNN's backend-agnostic idiom, not something added for Vulkan), so the change is `MNN_FORWARD_CPU` → `MNN_FORWARD_VULKAN` plus wrapping the `createSession()` call in the established mutex-guard pattern — not a redesign.
3. **"Coverage"**: No code-coverage tool (gcov/lcov/OpenCppCoverage) exists anywhere in this workstream's CI or build config. Every phase-1 SUMMARY.md already uses a structured `coverage:` YAML block (GSD's own Nyquist-style requirement-to-verification mapping), and the project's own `CLAUDE.md` mandates "≥80% coverage on new code" as a testing-discipline rule, not a tooling target. The concrete, actionable reading — reinforced by a fully local, network-free GTest fixture (`test/src/processing_datatypes/`) that already exists for **every one of the 13 migration-candidate call sites** (bool, buffer, float, int, mat2/3/4, tensor, texture1d, texturecube, vec2/3/4) with tolerance-based (`mean_abs_diff < 1e-3`, `max_abs_diff < 1e-2`) reference-output comparison — is: **extend test/verification coverage**, specifically (a) re-run the existing per-type `ProcessingDatatypesTest.*ProcessingTest` suite after migration to confirm Vulkan-backend output stays within the already-tolerant comparison bounds, and (b) update Phase 1's concurrent-init stress test (`vulkan_init_concurrency_test.cpp`) and its hardcoded "3 MNN + RenderProcessor = 4 call sites" doc comment (`vulkan_init_guard.hpp`), since the true call-site count grows from 4 to 17 after migration.

**Primary recommendation:** Treat this as three small, independently-committable fixes — (1) a 2-line CMake addition in each of `GeniusSDK`/`GeniusWallet`'s `CommonBuildParameters.cmake`, (2) a mechanical per-file backend-flag + mutex-wrap change across 12 processor `.cpp` files, (3) an update to the existing local `ProcessingDatatypesTest` suite's expectations plus the `VulkanInitMutex`/stress-test doc comments — none require new libraries, new architecture, or refactoring beyond what Phase 1 already established.

### Pattern 1: Downstream CMake consumer must independently `find_package` every PUBLIC-linked transitive dependency of an imported target
**What:** When a CMake-exported package (`SGProcessingManagerTargets.cmake`) declares an imported target (`SGProcessors`) that `PUBLIC`-links another package's target (`vk-bootstrap::vk-bootstrap`), every downstream consumer of that exported package must call `find_package()` for that transitive dependency itself, in the same scope, before or via `find_dependency()` inside the package's own `Config.cmake`. This project's convention (seen in every other `CommonBuildParameters.cmake`) is the former: each consumer explicitly repeats `find_package(MNN CONFIG REQUIRED)`, `find_package(Vulkan)`, etc. — it does not rely on `find_dependency()` propagation inside `config.cmake.in`.
**When to use:** Any time a new PUBLIC (not PRIVATE) link dependency is added to an exported CMake target in this codebase.
**Example:**
```cmake
# Source: SuperGenius/SGProcessingManager/cmake/CommonBuildParameters.cmake:198-200 (Phase 1, 01-03)
# vk-bootstrap
set(vk-bootstrap_DIR "${_THIRDPARTY_BUILD_DIR}/vk-bootstrap/lib/cmake/vk-bootstrap")
find_package(vk-bootstrap CONFIG REQUIRED)

# THIS PHASE must add the mirrored block to GeniusSDK/cmake/CommonBuildParameters.cmake
# (note: this file uses THIRDPARTY_BUILD_DIR, no leading underscore — confirm exact
#  variable name locally, do not copy the underscore-prefixed form verbatim)
set(vk-bootstrap_DIR "${THIRDPARTY_BUILD_DIR}/vk-bootstrap/lib/cmake/vk-bootstrap")
find_package(vk-bootstrap CONFIG REQUIRED)
# ... placed before line 432's `find_package(SGProcessingManager CONFIG REQUIRED)`

# and identically in GeniusWallet/cmake/CommonBuildParameters.cmake, before line 386's
# `find_package(SGProcessingManager CONFIG REQUIRED)` (GeniusWallet also uses
# THIRDPARTY_BUILD_DIR, confirmed at GeniusWallet/cmake/CommonBuildParameters.cmake:18)
```

### Pattern 2: MNN Vulkan-backend session creation always goes through the shared process-wide mutex
**What:** Every MNN `createSession()` call using `MNN_FORWARD_VULKAN` must be wrapped in `std::lock_guard<std::mutex> lock( sgns::sgprocessing::VulkanInitMutex() )` — this is CTX-02's shared init-lock from Phase 1, and it is a **repeatable** lock (acquired once per `createSession()` call, not once per process lifetime).
**When to use:** Every migration of a CPU-backend processor to Vulkan in this codebase, with zero exceptions — the mutex has no notion of "trusted callers."
**Example:**
```cpp
// Source: SuperGenius/SGProcessingManager/src/processors/processing_processor_mnn_string.cpp:2,152-161
// (established pattern — confirmed identical in mnn_volume.cpp and mnn_image.cpp)
#include "processingbase/vulkan_init_guard.hpp"
// ...
MNN::ScheduleConfig config;
config.type = MNN_FORWARD_VULKAN;  // was: MNN_FORWARD_CPU
config.numThread = 4;

MNN::Session *session = nullptr;
{
    std::lock_guard<std::mutex> lock( sgns::sgprocessing::VulkanInitMutex() );
    session = interpreter->createSession(config);
}
if (!session) {
    m_logger->error( "Failed to create MNN session" );
    return std::make_unique<MNN::Tensor>();
}
```

### Anti-Patterns to Avoid
- **Flipping `MNN_FORWARD_CPU` → `MNN_FORWARD_VULKAN` without adding the mutex guard:** This reintroduces exactly the race Phase 1's CTX-02 closed. The mutex only protects call sites that acquire it — an unmigrated-but-forgotten wrapper leaves a real concurrent-init race against MNN's other Vulkan sessions and `RenderProcessor`.
- **Assuming `find_dependency(vk-bootstrap)` inside `SGProcessingManager`'s `config.cmake.in` is the fix:** it would work, but it is NOT this project's established convention (every other transitive dependency — MNN, Vulkan, libp2p — is independently re-`find_package`'d by each consumer, not chained via `find_dependency`). Introducing a different propagation mechanism for just this one dependency creates an inconsistent pattern; match the existing convention instead (per CLAUDE.md's minimal-change / don't-introduce-new-architecture rule).
- **Rebuilding `thirdparty` to "fix" the MNN Vulkan backend:** Not needed. `MNN_VULKAN:BOOL=ON` is already set for the shared `ExternalProject_Add(MNN ...)` block in `thirdparty/build/CommonTargets.cmake` (applies to Windows/Linux/Android and non-iPhoneOS Apple builds). Per `SuperGenius/AgentDocs/CLAUDE.md`, "the user manages thirdparty builds separately — do not attempt to build thirdparty."

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Vulkan init synchronization | A new mutex/lock scoped to the migrated processors | The existing `sgns::sgprocessing::VulkanInitMutex()` from `processingbase/vulkan_init_guard.hpp` | It is already the single process-wide guard for every Vulkan-init call site (CTX-02); a second lock would defeat its purpose and reintroduce the exact race it was built to close |

| Regression verification for the migrated processors | New model fixtures, new JSON job definitions, or a new comparison harness | The existing `test/src/processing_datatypes/*-processing-definition.json` + `*_tiny.mnn` + `*_output_pt.raw` fixtures and `ProcessingDatatypesTest.*ProcessingTest` cases | A complete, local, network-free fixture + tolerance-based comparison already exists for every one of the 13 migration-candidate types — building new fixtures would duplicate existing, working test infrastructure |

**Key insight:** Every piece of infrastructure this phase needs (mutex, CMake find_package pattern, and regression-test fixtures) was already built in Phase 1 or exists independently in `test/src/processing_datatypes/`. This phase's job is exclusively to *apply* these three existing mechanisms to the two consumers/12 files/13 call sites that don't yet use them — not to invent anything new.

## Common Pitfalls

### Pitfall 1: Migrating the CMake fix but never actually configuring GeniusSDK/GeniusWallet to prove it
**What goes wrong:** Phase 1's own `01-03-SUMMARY.md` (D5) explicitly records that the `find_package(vk-bootstrap)` addition was *never build-verified* — "this working copy does not have the full thirdparty build environment configured." If this phase's fix is applied to `GeniusSDK`/`GeniusWallet` but likewise never run through an actual `cmake` configure, the exact same category of gap (a config-time target-resolution failure) can recur undetected.
**Why it happens:** Full builds require the complete thirdparty toolchain (MSVC, full submodule checkout, `MNN`/`vk-bootstrap` actually built) which may not be present in every working copy.
**How to avoid:** At minimum, run `cmake -B <tmp> -S GeniusSDK` (or equivalent for GeniusWallet) up to the configure step and confirm no "target not found" error for `vk-bootstrap::vk-bootstrap`; if the full toolchain genuinely isn't available, record this as an explicit `human_judgment: true` coverage item (matching this project's existing SUMMARY.md convention) rather than silently claiming it's fixed.
**Warning signs:** A CMake configure error containing `Target "SGProcessors" links to target "vk-bootstrap::vk-bootstrap" but the target was not found.`

### Pitfall 2: Migrating a processor to Vulkan without the mutex guard
**What goes wrong:** Reintroduces CTX-02's exact race — concurrent `createSession(MNN_FORWARD_VULKAN)` calls across processors (or against `RenderProcessor`'s Vulkan-context creation) without serialization can crash or corrupt driver-level Vulkan instance/device state.
**Why it happens:** The mechanical part of the fix (changing the enum) is easy to do in isolation and compiles fine without the mutex — the race is invisible until concurrent load hits it, which is exactly why Phase 1 needed a dedicated stress test rather than trusting code review alone.
**How to avoid:** Treat "flip the enum" and "add the mutex wrap" as one atomic change per file, verified by grepping every migrated file for both `MNN_FORWARD_VULKAN` and `VulkanInitMutex()` before considering the file done.
**Warning signs:** A file containing `MNN_FORWARD_VULKAN` but not `#include "processingbase/vulkan_init_guard.hpp"`.

### Pitfall 3: Leaving `vulkan_init_guard.hpp`'s doc comment and the concurrent stress test's scope note stale
**What goes wrong:** `vulkan_init_guard.hpp`'s comment explicitly says "MNN's 3 existing createSession(MNN_FORWARD_VULKAN) sites plus RenderProcessor's lazy-init path" and `01-06-SUMMARY.md`/the test file's scope note says the same. After migrating 13 more call sites, this becomes actively misleading documentation — a future engineer reading it will undercount real Vulkan-init call sites by more than 3x.
**Why it happens:** Doc comments encoding a specific count are easy to forget when the underlying set of callers grows incrementally across phases.
**How to avoid:** Update the doc comment to describe the *pattern* ("every MNN Vulkan-backend `createSession()` call site, plus `RenderProcessor`") rather than a specific number, or update the number and add a note that it must be re-verified whenever a processor migrates backends.
**Warning signs:** Grep for `MNN_FORWARD_VULKAN` across `src/processors/*.cpp` returning a count that doesn't match any hardcoded number in comments/tests.

### Pitfall 4: Treating "coverage" as a code-coverage percentage target requiring new tooling
**What goes wrong:** Time is spent standing up gcov/lcov/OpenCppCoverage instrumentation and CI wiring that doesn't exist anywhere in this repo today, when the actually-actionable and already-available mechanism (the existing `ProcessingDatatypesTest` fixture set) directly verifies the thing that matters — that migrated processors still produce correct output and that concurrent Vulkan init still doesn't race.
**Why it happens:** "Coverage" is genuinely ambiguous as written in the roadmap note, and code-coverage tooling is the more common industry meaning of the bare word.
**How to avoid:** Confirm with the reading in this research (test/verification coverage of the migration, using the existing local fixtures) before proposing new coverage-tooling infrastructure; if genuine code-coverage-percentage tooling is desired, that is a larger, separate infra decision this phase's "URGENT" framing does not suggest.
**Warning signs:** Plan tasks that mention installing/configuring a coverage tool rather than running/extending `ProcessingDatatypesTest`.
