### MNN CPU→VULKAN processor migration (12 files, 13 call sites) — service, transform

**Analog (target pattern, already-migrated):** `SuperGenius/SGProcessingManager/src/processors/processing_processor_mnn_string.cpp`

**Imports pattern to add** (line 2 of the analog — every migrated file needs this include if not already present):
```cpp
#include "processingbase/vulkan_init_guard.hpp"
```
(Also confirm `#include <mutex>` is present — `mnn_string.cpp` line 4 has it explicitly.)

**Core pattern — session creation, Vulkan backend + mutex guard** (`processing_processor_mnn_string.cpp:152-165`):
```cpp
MNN::ScheduleConfig config;
config.type = MNN_FORWARD_VULKAN;  // Use Vulkan backend as requested
config.numThread = 4;

MNN::Session *session = nullptr;
{
    std::lock_guard<std::mutex> lock( sgns::sgprocessing::VulkanInitMutex() );
    session = interpreter->createSession(config);
}
if (!session) {
    m_logger->error( "Failed to create MNN session" );
    return std::make_unique<MNN::Tensor>();
}
```

**Current (pre-migration) state to replace, exemplified by `processing_processor_mnn_mat2.cpp:365-375`:**
```cpp
MNN::ScheduleConfig config;
config.type = MNN_FORWARD_CPU;
config.numThread = 4;
config.backendConfig = nullptr;

auto session = interpreter->createSession( config );
if ( !session )
{
    m_logger->error( "Failed to create MNN session" );
    return nullptr;
}
```

**Migration diff to apply per file (mechanical, identical across all 12 files / 13 call sites):**
1. Add `#include "processingbase/vulkan_init_guard.hpp"` near top of file (if missing).
2. Change `config.type = MNN_FORWARD_CPU;` → `config.type = MNN_FORWARD_VULKAN;`.
3. Wrap the `interpreter->createSession(config)` call in `{ std::lock_guard<std::mutex> lock( sgns::sgprocessing::VulkanInitMutex() ); session = interpreter->createSession(config); }`, converting the previously-inline `auto session = ...;` into a pre-declared `MNN::Session *session = nullptr;` outside the lock scope so it remains visible afterward (exact structure shown in the "Core pattern" excerpt above).
4. Leave `config.numThread = 4;` and `config.backendConfig = nullptr;` untouched — these are backend-agnostic and not part of the migration.
5. Everything downstream of `createSession` (`copyFromHostTensor`/`runSession`/`copyToHostTensor`) is unchanged — confirmed backend-agnostic in both analog and target files.

**Files this applies to verbatim** (per RESEARCH.md's confirmed file list — 12 files, 13 call sites, `texturecube` has 2):
`processing_processor_mnn_bool.cpp`, `..._buffer.cpp`, `..._float.cpp`, `..._int.cpp`, `..._mat2.cpp`, `..._mat3.cpp`, `..._mat4.cpp`, `..._tensor.cpp`, `..._texture1d.cpp`, `..._texturecube.cpp` (2 sites), `..._vec2.cpp`, `..._vec3.cpp`, `..._vec4.cpp` — all under `SuperGenius/SGProcessingManager/src/processors/`.

**Do NOT touch** (per RESEARCH.md — confirmed stubs / already migrated / non-MNN):
`processing_processor_mnn_ml.cpp`, `processing_processor_mnn_audio.cpp` (unimplemented stubs, no session), `processing_processor_mnn_image.cpp`, `processing_processor_mnn_string.cpp`, `processing_processor_mnn_volume.cpp` (already Vulkan+mutex), `processing_processor_render.cpp` (not MNN, Phase 1 RenderProcessor already has its own lazy-init path).

**Source:** `SuperGenius/SGProcessingManager/include/processingbase/vulkan_init_guard.hpp:12-16`

inline std::mutex &VulkanInitMutex()
{
    static std::mutex vulkan_init_mutex; // magic static -- thread-safe init, C++11+
