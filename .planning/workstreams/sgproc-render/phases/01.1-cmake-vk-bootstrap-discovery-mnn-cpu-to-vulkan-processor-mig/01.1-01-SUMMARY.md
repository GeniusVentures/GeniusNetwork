**Added `find_package(vk-bootstrap CONFIG REQUIRED)` to GeniusSDK and GeniusWallet's `CommonBuildParameters.cmake`, closing the transitive-dependency gap Phase 1 left open, and confirmed via CMake reconfigure that both consumers now resolve `vk-bootstrap::vk-bootstrap` cleanly.**

## Accomplishments
- `GeniusSDK/cmake/CommonBuildParameters.cmake` now calls `find_package(vk-bootstrap CONFIG REQUIRED)` (pinned to `${THIRDPARTY_BUILD_DIR}/vk-bootstrap/lib/cmake/vk-bootstrap`) immediately after its existing MNN block, before `find_package(SGProcessingManager CONFIG REQUIRED)`
- `GeniusWallet/cmake/CommonBuildParameters.cmake` gets the identical block, before its own `find_package(SGProcessingManager CONFIG REQUIRED)` call
- Reconfigured GeniusSDK's existing `build/Windows/Release` build directory end-to-end with zero errors — direct proof the fix works

## Decisions Made
- Used the plain `THIRDPARTY_BUILD_DIR` variable convention (no leading underscore) in both consumer files, matching each file's own established MNN/Vulkan `find_package` blocks — explicitly avoided the underscore-prefixed `_THIRDPARTY_BUILD_DIR` form that only exists inside `SGProcessingManager`'s own CMake file
- Did not introduce `find_dependency(vk-bootstrap)` in `config.cmake.in` — repeated the existing per-consumer `find_package` convention instead, per RESEARCH.md Pattern 1 and CLAUDE.md's minimal-change/no-new-architecture rule
- Bumped both submodule pointers in the superproject (`dev_persisprocresults`) as a follow-on commit, matching the project's existing `chore(NN-NN): bump <submodule> pointer` convention (see `4ac898f`, `11bdf01` in recent history) — without this, the submodule commits would be orphaned and not referenced by the superproject's tracked state
