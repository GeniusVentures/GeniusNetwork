**C) CancellationToken struct (per D-01, D-02, D-05)** — callback-based, no polling:

- `void Cancel()` — invokes registered callback if set, sets internal cancelled flag
- `bool IsCancelled() const` — returns true after Cancel() called
- `void SetCallback(std::function<void()> callback)` — register the cancel callback. Called by ProcessingManager before passing token to processor.

**D) ExecutionContext struct (per D-01, D-02, D-06, D-08, D-10)** — bundles everything a processor needs:

- `CancellationToken cancelToken` — per-job token (D-02), shared across all passes
- `std::function<void(ProgressEvent)> progressCallback` — processor calls at stage boundaries (D-10). Follows CanExecuteCallback pattern: void-returning callback taking a typed struct.
- `uint64_t deadlineMs` — per-pass wall-clock deadline in milliseconds (D-08). 0 means no deadline (D-09: deadline uses unified cancel path, ProcessingManager sets up timer).
- `uint64_t gpuMemoryBudget` — estimated GPU memory in bytes (D-08). 0 means no budget declared.
- `uint64_t maxOutputArtifactBytes` — maximum output artifact size in bytes (D-08). 0 means no budget declared.

Static factory `static ExecutionContext NoOp()` returns an ExecutionContext with no-op cancel callback, no-op progress callback, and all budgets/deadline set to 0. Used by the old StartProcessing() adapter (D-18) and in tests.

**Header guard:** `#ifndef SGPROCMGR_EXECUTION_CONTEXT_HPP`. Include `<atomic>`, `<cstdint>`, `<functional>`, `<string>`. No Vulkan or MNN headers needed. PascalCase types, `m_` prefix for CancellationToken's internal member, trailing underscore for struct fields per Coding Standards.

Use `#pragma once` for internal simplicity — matches `vulkan_init_guard.hpp` and `processing_processor_render.hpp` conventions.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Job schema → Processor | Budget fields from untrusted job submission cross into processor execution |
| CancellationToken::Cancel() → processor thread | Cancel invoked from timer/deadline thread, read by processing thread |
| Teardown functions → Vulkan driver | Teardown may run during stack unwinding (D-17); Vulkan objects in unknown state |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-07-01 | Tampering | Schema budget fields | mitigate | Schema declares minimum: 0, integer type — negative/invalid values rejected by JSON parser. CapabilityValidator bounds-checks budgets against node resources (Plan 07-02 D-07). |
| T-07-02 | Denial of Service | CancellationToken::Cancel() | mitigate | Atomic bool with acquire/release ordering — no data race between timer thread and processor thread. Cancel callback invoked at most once (flag check before invocation). |
| T-07-03 | Elevation of Privilege | Teardown stack exception | mitigate | RunTeardown() wraps each callback in try/catch — one failing teardown function cannot prevent others from running. Logs failure, continues. |
| T-07-04 | Information Disclosure | ProgressEvent::pass_id | accept | Pass ID is a user-assigned name from schema — not a secret. Progress events are internal callbacks, not exposed over network. |
| T-07-SC | Tampering | quicktype npm install | mitigate | slopcheck applies to quicktype package. Already in use by CI workflow (generate-headers.yml) — established dependency. |
</threat_model>
