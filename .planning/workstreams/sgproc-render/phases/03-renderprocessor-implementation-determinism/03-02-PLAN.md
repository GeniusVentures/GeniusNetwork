<objective>
Close RESEARCH.md's Pitfall 1 gap — "the only working prefix-resolution code in the repo today is the single `input:name` → index map used once per job for the model-index lookup" — for `vertex_buffer`/`index_buffer`, which RENDER-02 requires RenderProcessor to actually upload. This is the explicit early decision RESEARCH.md's Open Question 1 flags as gating RENDER-02/05/06 simultaneously; it is resolved here, before any RenderProcessor buffer-allocation code exists (plan 03-03).

**Second, load-bearing gap this plan also closes (discovered during planning, not in RESEARCH.md — documented here for traceability):** `RenderProcessor::StartProcessing()`'s fixed signature (`chunkhashes`, `proc` — an `IoDeclaration&`, `imageData`, `modelFile`, `parameters`) never gives RenderProcessor access to the `Pass` object at all — `proc` is a top-level input declaration (name/type/dimensions/format/source_uri_param), not the pass. This means `render_target`/`pipeline_state`/`vertex_layout` — all `Pass`-level fields plan 03-04 needs to build the render pass/framebuffer/pipeline — have no channel to reach `RenderProcessor` whatsoever unless this plan serializes them too. Per D-25's "no `StartProcessing()` signature change" constraint, the only available channel is the same byte-buffer wire format already carrying the vertex/index bytes (`mainbuffers->second`/`imageData`) — so this plan's wire format carries `render_target` + `pipeline_state` + `vertex_layout` alongside the vertex/index buffer bytes, all in one pass-config buffer, serialized once at `GetCidForProc()` time (where the full `Pass` object — `p` — is already in scope) and parsed once by plan 03-03's `RenderProcessor`.

**Scope decision (documented, not silently dropped):** `vertex_buffer.source`/`index_buffer.source` are schema-permitted to use `input:`/`output:`/`internal:`/`parameter:` prefixes, but this codebase has zero cross-pass dependency/execution-order infrastructure — `ProcessingManager::Process()` dispatches exactly one pass per call, with no concept of "another pass's output becoming this pass's input" (`output:`/`internal:` would require that), and no codec exists anywhere for decoding a `parameter:`-sourced JSON value into raw vertex/index bytes. Building either is a genuinely separate, much larger undertaking than "resolve a render pass's own buffer bindings" — a real dependency-conflict/missing-information constraint, not a discretionary scope cut. This plan resolves `input:` prefix sources only (extending the existing single-lookup mechanism to fetch multiple, independently-named inputs) and makes `output:`/`internal:`/`parameter:` vertex/index-buffer sources fail `CheckProcessValidity()` cleanly, with the exact reason documented in the error path.

Uniform resolution (RENDER-05) needs no new fetch plumbing at all: `RenderShaderUniform.source` values are expected to use the `parameter:` prefix, and `processing_.get_parameters()` already flows into `RenderProcessor::StartProcessing()` unchanged, via the existing `parameters` argument. This plan only adds the defensive prefix validation RESEARCH.md's Pitfall 8 flags as missing from the schema itself; the actual value lookup happens in plan 03-03, inside `RenderProcessor`, directly against the already-available `parameters` vector.

Purpose: Give plan 03-03's RenderProcessor a real, working, independently-fetched vertex/index buffer wire format to parse — not the coincidental single-input reuse the current test fixture happens to get away with — and the only channel through which render_target/pipeline_state/vertex_layout can ever reach it.
Output: `GetCidForProc()`'s render branch resolves and packs vertex/index buffer bytes plus render_target/pipeline_state/vertex_layout into one wire format; `CheckProcessValidity()` rejects unsupported source prefixes early.
</objective>
