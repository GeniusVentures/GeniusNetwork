<objective>
Build the two Vulkan object groups RENDER-01/03/04 and DETV-02 require: the offscreen render pass + framebuffer (color+depth, explicit clears, no swapchain), and the graphics pipeline itself (shader stages from plan 03-03's parsed SPIR-V, fixed — never dynamic — pipeline state from schema, and a pipeline layout branching on plan 03-03's push-constant-vs-descriptor-set decision). This plan produces Vulkan objects but does not yet record or submit a command buffer, upload buffer data, or read back — that is plan 03-05, which needs these objects to already exist.

Every `sgns::RenderTarget`/`sgns::PipelineState`/`sgns::VertexLayoutEntry` this plan's methods take as parameters comes from plan 03-03's `ParseRenderPassConfig()` — reconstructed from plan 03-02's wire format, not read from a `Pass` object (`RenderProcessor` never has one). This plan's methods are agnostic to that origin (they simply take the typed generated-schema objects as `const` references/values), but plan 03-05's `StartProcessing()` wiring is where `ParseRenderPassConfig()`'s output actually gets threaded into these methods' call sites.

**Vertex attribute component-count gap (discovered, not in RESEARCH.md — documented here for traceability):** `vertex_layout_entry.format` is `FLOAT16`/`FLOAT32`/`INT32` with no vec2/vec3/vec4 variant anywhere in the schema, and no "component count"/"location" field exists either. The only defensible, schema-literal reading is that each `vertex_layout` entry describes a single-scalar-component Vulkan format (`VK_FORMAT_R32_SFLOAT`/`VK_FORMAT_R16_SFLOAT`/`VK_FORMAT_R32_SINT`), with `location` assigned by the entry's position in the `vertex_layout` array (index 0 → `location = 0`, etc. — the only ordering information the schema provides) and the auto-computed stride being the tightly-packed sum of every entry's scalar byte size. Phase 2's existing `dummy_shader.glsl` test fixture (`layout(location=0) in vec3 inPosition;`) was authored only for Phase 2's compile-validate testing and was never pipeline-executed — it is NOT evidence that multi-component attributes are supported by this schema, and this plan does not attempt to reconcile that fixture; plan 03-06's new happy-path fixture is authored with a scalar attribute instead, consistent with this reading.

Purpose: Produce the exact Vulkan render-pass/pipeline objects plan 03-05's draw call binds against, with every determinism-relevant fixed-function choice (sample count, clear ops, baked pipeline state) locked in per DETV-02.
Output: `BuildRenderPass()`, `BuildFramebuffer()`, `BuildPipeline()` — three new private methods, plus the schema-to-Vulkan mapping helpers they need.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Job-declared `render_target.width`/`height` → `vkCreateImage` | Schema enforces only `minimum: 1`; a pathological value is a resource-exhaustion vector on a shared distributed-compute node |
| Job-declared `color_format`/`depth_format` → `vkCreateImage`/`vkCreateRenderPass` | Not guaranteed renderable on every device (Pitfall 7) |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-04-01 | Denial of Service | `BuildRenderPass()` given an unbounded `render_target.width`/`height` | medium | mitigate | New `kMaxRenderDimension` (8192) bounds check before any `VkImage`/`VkRenderPass` creation |
| T-03-04-02 | Denial of Service | `vkCreateImage`/`vkCreateRenderPass` given an unsupported color/depth format combination | medium | mitigate | `CheckFormatSupport()` (plan 03-03) queried for both formats before any image/render-pass object is created; failure returns a structured `FORMAT_UNSUPPORTED` error, never an opaque `VkResult` propagated to the caller |
| T-03-04-03 | Tampering | `DONT_CARE` load ops silently reintroduced on a hashed attachment during future maintenance | high | accept | No code-level guard beyond this plan's explicit `VK_ATTACHMENT_LOAD_OP_CLEAR` choice and the region-scoped grep acceptance criteria above — a future edit could still regress this; accepted since a stronger structural guard (e.g. a custom lint rule) is out of proportion for this phase |

</threat_model>
