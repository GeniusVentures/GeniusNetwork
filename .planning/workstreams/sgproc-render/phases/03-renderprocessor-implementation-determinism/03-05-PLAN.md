<objective>
Complete `RenderProcessor::StartProcessing()`: upload vertex/index/uniform buffers (D-20/D-21's HOST_VISIBLE|HOST_COHERENT direct-write policy), record and submit one command buffer (bind pipeline/buffers/push-constants-or-descriptor-set, draw(indexed), readback via `vkCmdCopyImageToBuffer`), compute the real output hash, apply RENDER-07's data_transform stance, and tear everything down before returning — on every path, success or failure. This is the plan where plans 03-03/03-04's helpers are finally called from the public `StartProcessing()` entry point for the first time; the method's current stub behavior (always returns a zero hash) is replaced entirely.

**RENDER-07 scope (documented, per RESEARCH.md Pitfall 9 — zero `data_transform` executor exists anywhere in this codebase):** this plan implements the schema-literal "optionally flow through" reading — absent/empty `data_transforms` is a no-op (readback bytes flow through unmodified), any non-empty `data_transforms` array fails cleanly with a structured, named error (`ProcessingErrorStage::DATA_TRANSFORM_UNSUPPORTED`) rather than silently ignoring the job's declared transform or attempting to build general transform infrastructure with no existing pattern, no fixture, and no requirement text describing which specific transform a render pass actually needs applied. This satisfies RENDER-07's literal wording without inventing scope RESEARCH.md explicitly flagged as disproportionate for this phase.

Purpose: Deliver the actual, working, bit-producing render pipeline — the literal deliverable of this entire phase.
Output: A fully-wired `StartProcessing()` that executes a schema-declared render pass end-to-end and returns a real hash or a structured error, never a crash or a silent zero-hash success.
</objective>
