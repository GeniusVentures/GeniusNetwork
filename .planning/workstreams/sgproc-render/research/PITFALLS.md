# Pitfalls Research: Cross-Hardware Hash Tolerance (Quantization Before SHA-256)

**Domain:** Adding floating-point quantization/rounding before `sha256()` hashing in SGProcessingManager's render (Vulkan framebuffer readback) and MNN inference (tensor) output paths, to make job-result hashes tolerant of cross-GPU-vendor/cross-driver/CPU-vs-GPU numeric divergence — while keeping the hash a meaningful integrity check
**Researched:** 2026-08-07
**Confidence:** HIGH for repo-grounded findings (direct source read of the current `sha256()` call sites, confirmed current as of this research date); MEDIUM for general floating-point/GPU-determinism/verification-security findings (web search, cross-checked across independent sources — see Sources). Nothing here is presented as LOW confidence.

**Scope note:** This document assumes same-node determinism is already solved (v1.0/v2.0 DETV-01/DETV-02: explicit clear ops, `VK_SAMPLE_COUNT_1_BIT`, fixed shader precision qualifiers, no unordered parallel-reduction shader math — see the prior `PITFALLS.md` for that research, not repeated here). Everything below is specific to the **new** cross-hardware problem: tolerating real numeric divergence across GPU vendors/drivers/CPU-vs-GPU while still rejecting a genuinely wrong or substituted result. Pitfalls are explicitly tagged **Capture-harness phase** (build the cross-machine capture/diff tooling) or **Quantization-implementation phase** (add the actual pre-hash rounding step), matching this milestone's two target features.

## Grounding facts (from this repo, verified 2026-08-07 — not general floating-point knowledge)

- The hashing primitive is one small shared utility: `sgns::sgprocmanagersha::sha256(const void* data, size_t dataSize)` (`SGProcessingManager/include/util/sha256.hpp`, `src/util/sha256.cpp`). It is a pure byte-hasher — it has zero awareness of what the bytes represent (image, tensor, model file, manifest struct). Today it is called from **at least four structurally distinct places**, not one:
  1. Per-processor **chunk hashes**, computed on raw pre-stitch/pre-average model output, one call per processing window (e.g. `processing_processor_mnn_float.cpp:307`: `sgprocmanagersha::sha256( data, dataSize )` on the raw `float*` output of each windowed MNN inference call, before any stitching/averaging).
  2. Each processor's own **final subtask hash** (`result.hash`), computed on that processor's fully-assembled output bytes (e.g. `processing_processor_mnn_float.cpp:330`: `sha256( stitchedStr.c_str(), stitchedStr.size() )` on the *averaged* float32 output; `processing_processor_render.cpp:2156`: `sha256( readbackBytes.data(), readbackBytes.size() )` on raw framebuffer bytes).
  3. `ComputeArtifactIdentity()` (`include/artifacts/artifact_types.hpp:76`), called from `ProcessingManager.cpp:1426`, independently re-hashes the same final output bytes (`bufferData[outIdx]`) to fill `Artifact::contentHash`/`artifactId` — a **separate** `sha256()` call over what is usually the same logical bytes as (2), but reached through a different code path (`ProcessingManager.cpp`, not the processor).
  4. `ComputeManifestHash()` (`include/artifacts/artifact_serializer.hpp:60`), called from `ProcessingManager.cpp:1508`, hashes the whole `ExecutionManifest` struct (which embeds the artifact hashes from (3), model/executor identity hashes, etc.) to produce `output.combinedHash` — this is the value the milestone's capture harness calls "the combined hash per run."
  - Model-identity hashing (`ProcessingManager.cpp:1460`) and executor-identity hashing also call the same `sha256()` on non-numeric bytes (model file contents, identity blobs) and must **never** be quantized — this is the same shared function serving both "tolerate numeric noise" and "must stay exact" callers.
- The render path's readback is **uint8 image data today, unconditionally**: `RenderProcessor::ToVkFormat(ColorFormat)` only maps to `VK_FORMAT_R8G8B8A8_UNORM` or `VK_FORMAT_R8G8B8_UNORM` (`processing_processor_render.cpp:1047-1057`) — the schema's `ColorFormat` enum has no float/HDR color option yet, and `Readback()` (`processing_processor_render.cpp:1960`) only copies the color attachment; the depth attachment (which *can* be `D32_SFLOAT`, a float format) is never read back or hashed. So today's render-path quantization problem is concretely "cross-hardware rasterization noise in uint8 RGBA/RGB channel bytes," not "cross-hardware noise in floats" — the float-quantization problem is currently MNN-only.
- MNN's float path (`MNN_Float::StartProcessing`) does its own windowed-overlap-add reconstruction: each window's raw model output is chunk-hashed *before* stitching (grounding fact 1 above), then results are summed into `stitchedOutput` and divided by `stitchedWeights` (lines 300-326) — this averaging/division is itself a floating-point operation whose rounding can differ across hardware, **on top of** whatever divergence the MNN inference kernels themselves introduce. A capture tool that only diffs the final stitched tensor cannot distinguish "inference-kernel divergence" from "stitching-math divergence."
- A pre-existing, differently-scoped tolerance convention already exists in this codebase: `ProcessingDatatypesTest` (`SuperGenius/test/src/processing_datatypes/processing_datatypes_test.cpp`) asserts `mean_abs_diff < 1e-3` and `max_abs_diff < 1e-2` between `MNN_FORWARD_CPU` and `MNN_FORWARD_VULKAN` outputs on the **same machine** (COV-01, from the Phase 01.1 CPU→Vulkan backend migration). This is a **test-time float-array comparison**, unrelated in purpose to pre-hash byte quantization, and its thresholds were derived for a different comparison (CPU vs. GPU backend on one node), not for cross-machine/cross-vendor noise.
- `ProcessingValidationCore::ValidateResults`'s concatenation bug (explicitly deferred, not fixed this milestone — see PROJECT.md) means no code path today actually diffs two subtasks' hashes for the same chunk; this milestone's capture-and-diff tooling is a **separate, standalone tool**, not integrated into that broken comparison path — don't assume fixing quantization also fixes verification end-to-end.

## Critical Pitfalls

### Pitfall 1: Naive "round to N decimal places" silently corrupts NaN, Inf, denormals, and signed zero

**What goes wrong:**
A straightforward quantization implementation — reinterpret each 4-byte (or 2-byte) chunk as a float, do `std::round(x * scale) / scale`, write the bytes back — behaves correctly on ordinary finite values but corrupts IEEE-754 special values in ways that are easy to miss in testing because they only appear on specific inputs:
- **Signed zero:** `-0.0` and `+0.0` compare equal under IEEE `==` but have different bit patterns; a decimal-rounding step that does arithmetic (multiply/round/divide) on `-0.0` can produce `+0.0` on one hardware/compiler and preserve `-0.0` on another (sign-of-zero handling in `round()`/FMA is implementation-defined at the edges), reintroducing a spurious bit-level mismatch that quantization was supposed to eliminate.
- **Denormals/subnormals:** flushing denormals to zero (FTZ) is a legitimate simplification, but whether a GPU driver or the quantization code's own float math flushes denormals to zero **depends on hardware FTZ/DAZ mode**, which differs by vendor and even by shader vs. host-CPU code path — so a denormal that survives on one machine and gets flushed on another produces a divergence at exactly the boundary the quantization step is supposed to smooth over.
- **NaN:** doing decimal-rounding arithmetic on a NaN typically propagates NaN (fine), but if the quantization step instead does bit-level truncation/masking of the mantissa (a tempting "fast" implementation for fixed-precision rounding), zeroing the wrong bits can flip a NaN into `+Inf`/`-Inf` (an exponent-all-ones, mantissa-all-zeros pattern). Separately, x86 CPUs canonicalize NaN payloads on many operations (rewriting to a fixed `0x7FC00000`-style pattern) while GPU shader cores frequently preserve or generate different NaN payload bits — so even "the same" NaN can hash differently pre-quantization, and a byte-truncation-based quantizer does nothing to normalize this unless it explicitly canonicalizes NaN/Inf as a distinct case.
- **Infinity:** multiplying `Inf` by a rounding scale factor and dividing back can produce `Inf`, `NaN` (if the scale is somehow zero/degenerate), or overflow behavior that differs across the CPU's software rounding path and a GPU's hardware rounding path.

**Why it happens:**
Decimal-place rounding is designed and tested against "normal" numeric ranges (the kind of values a render color channel or a well-trained model's activations produce); NaN/Inf/denormal/signed-zero are edge cases that only appear from specific inputs (empty regions, divide-by-zero in a shader, an untrained/adversarial model, an uninitialized buffer region) and are easy to never exercise in a first test pass.

**How to avoid:**
- Special-case NaN, +Inf, -Inf, and signed zero **explicitly and first**, before any decimal-rounding arithmetic: detect via `std::isnan`/`std::isinf`/checking the sign bit of zero, and canonicalize each to one fixed representative bit pattern (e.g. a single canonical NaN payload, `+0.0` for both zeros) rather than running them through the same rounding formula as finite values.
- Do not implement quantization as a bitmask/truncation trick on the raw mantissa bits "for speed" — reinterpret as the actual float type, use library rounding functions, and treat the special-value canonicalization as a mandatory first branch, not an assumed side effect of the rounding formula.
- Add unit tests that specifically feed NaN, +Inf, -Inf, +0.0, -0.0, and a subnormal value through the quantizer and assert canonical output bytes — this is cheap and catches the whole pitfall class in one test file, without needing multi-machine hardware.

**Warning signs:**
Two runs on the *same* machine producing different hashes only when the input/output happens to contain a NaN, Inf, or a very-small (subnormal-range) value; a quantizer that passes all "normal-looking" test fixtures but a fuzz/property test with extreme float values immediately finds mismatches; render-path uint8 data is immune to this whole pitfall (see Pitfall 4) — if this shows up on the render path at all, something is misapplying float-oriented quantization logic to non-float bytes.

**Phase to address:** Quantization-implementation phase. This is a correctness detail of the rounding function itself, testable entirely on one machine with synthetic inputs — it does not require the capture-harness's multi-machine data to catch.

### Pitfall 2: Assuming a fixed decimal-place/ULP tolerance "cancels out" non-associative reduction-order noise, when the noise magnitude is workload-shape-dependent, not a hardware constant

**What goes wrong:**
It's tempting to pick one tolerance ("round to 3 decimal places" or "8 ULP") once, based on a couple of observed cross-machine diffs, and assume it generalizes. But the magnitude of cross-hardware floating-point divergence comes from **non-associative reduction order** — different GPU vendors/drivers use different warp/wavefront scheduling, different tensor-core MMA topologies per generation, and different approximations in transcendental/special-function units — and the resulting error **accumulates with reduction depth and magnitude of intermediate values**, not just with the final value's size. A shallow, small-magnitude computation (e.g. a small render pass with few blended fragments) may diverge by only 1 ULP across vendors; a longer MNN inference chain with many accumulation steps (matmuls, softmax, normalization) can accumulate divergence far beyond a fixed small-ULP tolerance derived from a toy test case. A single fixed-precision constant chosen from one capture run risks being simultaneously too tight for the real workload's accumulated noise (causing false mismatches on legitimate cross-hardware runs) and, if loosened to compensate, too loose everywhere else (see Pitfall 3).
Architectural guards already in place for same-node determinism (DETV-02: explicit clears, `VK_SAMPLE_COUNT_1_BIT`, fixed shader precision, no unordered shader-side reductions) constrain reduction order **within one driver's execution of the render shader** — they say nothing about MNN's own internal kernel scheduling, nor about a *different* GPU vendor's driver choosing a different (but equally valid, equally deterministic-on-its-own-hardware) reduction order for the same math. Same-node determinism and cross-hardware tolerance are different problems solved by different mechanisms; DETV-02's guards do not transfer.

**Why it happens:**
"Bit-exact on my machine, N≥10 runs" (DETV-01/02's actual, already-proven guarantee) sounds like it should generalize to "close on every machine" with just a small fudge factor, but the two guarantees rest on entirely different assumptions — one relies on a single driver's deterministic scheduling being *itself* deterministic across repeat runs, the other is asking whether *two different, independently-valid* schedulings converge to similar values.

**How to avoid:**
- Derive the fixed precision constant from the capture-harness's actual empirical cross-hardware diff stats (max delta, mantissa-bit differences — exactly what the capture tool this milestone builds is meant to produce) across the real render + MNN job workloads intended for production, not from a synthetic toy case.
- Treat the render (shallow reduction depth, bounded per-fragment) and MNN tensor (potentially deep accumulation chains) paths as needing **independently derived** tolerance constants, even though both are "floating point" — see Pitfall 4.
- Document the tolerance as empirically-derived-and-fixed-for-this-milestone, explicitly flagging that a workload with materially different reduction depth (a much larger model, a much more complex shader) may need re-derivation — this is exactly why the milestone scopes out schema-configurable precision rather than pretending one constant is universally correct.

**Warning signs:**
The chosen tolerance passes the specific ≥3-machine empirical test this milestone requires but a slightly different job definition (larger render target, deeper model) run on the same 3 machines produces mismatches at the same tolerance; tolerance was chosen by looking at one capture run's diff and picking a round number ("looks like 1e-4 is enough") rather than from the diff tool's actual max-delta/mantissa-bit-diff output across the full intended workload set.

**Phase to address:** Quantization-implementation phase (the constant itself) — but structurally *depends on* the capture-harness phase running first and producing real diff statistics; sequencing matters here (see Pitfall 8).

### Pitfall 3: A tolerance loose enough to absorb real cross-hardware noise is, by construction, loose enough to also absorb a wrong or substituted result — this is the central risk of this milestone, not a side effect

**What goes wrong:**
This is the sharpest version of the stated design tension. If the quantization step rounds/tolerates aggressively enough that legitimate GPU-vendor-A vs. GPU-vendor-B noise always collapses to the same post-quantization hash, nothing in the rounding function itself distinguishes "this divergence came from vendor A vs. vendor B's floating-point unit" from "this divergence came from a subtly wrong shader," "a truncated/corrupted model," "a downgraded-precision inference run," or "a deliberately substituted result crafted to land inside the tolerance band." A flat, global "round to N decimal places" cutover is a single scalar knob controlling both false-negative rate (real cross-hardware pairs wrongly flagged as mismatched) and false-positive/security risk (wrong or adversarial results wrongly accepted as matching) — there is no way to move it to reduce one risk without moving the other. Recent verification-protocol research (TAO, arXiv 2510.16028) frames this exact tension for floating-point neural network output verification: naively-loose tolerance bands reopen the attack surface (model swaps, quantization/precision downgrades, graph rewrites) that a strict hash was meant to close, precisely because those attacks are designed to produce outputs that are numerically "close" to correct.

**Why it happens:**
The stated goal — "make the hash cross-hardware tolerant" — is trivially satisfiable by rounding away almost all precision (round every value to the nearest power of 2, say); it is easy to solve the tolerance problem while accidentally also solving away the hash's actual job (rejecting wrong results), because both failure modes look identical during "does it work on 3 machines" testing — a too-loose tolerance passes that test just as well as a correctly-tuned one, and the security regression only shows up when someone (or something) actually tries to exploit the slack, which isn't exercised by the milestone's own empirical acceptance test.

**How to avoid:**
- Explicitly test the *other side* of the tolerance, not just the cross-hardware-match side: construct a deliberately-wrong-but-plausible result (e.g. run the same job with a corrupted model file, a wrong shader constant, or a truncated/lower-precision inference run) and confirm it still produces a **different** post-quantization hash from the correct result, on top of the ≥3-machine matching test. The milestone's stated acceptance criterion (same job, ≥3 machines, matching hash) proves tolerance is loose enough — it does not by itself prove tolerance is not *too* loose. Both checks are needed and are not redundant with each other.
- Prefer the tightest tolerance that empirically satisfies the capture-harness's real cross-hardware diff data (Pitfall 2) over any looser "round number for safety margin" — every extra bit of slack purely enlarges the space of results indistinguishable from correct.
- Since schema-configurable precision is explicitly deferred, document the chosen fixed constant's derivation and the "wrong result still diverges" counter-test result together, so a future milestone tightening or per-datatype-tuning this value has the actual empirical basis, not just "it passed 3 machines."
- Do not present the quantization step's job as "verification" or "consensus" (deferred XNODE-01/`ValidateResults` fix) — it only makes the *hash comparison* tolerant; it is explicitly not building the redundant-execution/consensus plumbing that would actually catch a malicious single node. Document this boundary so no downstream consumer assumes more security than this milestone delivers.

**Warning signs:**
The chosen tolerance was validated only against the "does it match across 3 machines" test, never against a "does a wrong result still mismatch" test; the tolerance constant was chosen as a round, convenient number rather than derived from measured cross-hardware deltas; anyone describing this milestone's output as "verification" or "fixing consensus" rather than "making the existing hash comparison cross-hardware tolerant."

**Phase to address:** Quantization-implementation phase — this is the single most important thing to get right in that phase, and it needs its own explicit test category (adversarial/wrong-result divergence), not just the empirical N-machine-match test already planned.

### Pitfall 4: Treating uint8 image/texture bytes and float32 tensor bytes with the same quantization logic

**What goes wrong:**
Today, concretely in this repo, the render path's readback is unconditionally `VK_FORMAT_R8G8B8A8_UNORM`/`VK_FORMAT_R8G8B8_UNORM` — plain 8-bit-per-channel integers, already maximally quantized by the pixel format itself, with a fixed 0-255 range and no denormals/NaN/Inf/signed-zero possible. MNN's float path hashes raw `float32` tensor bytes with unbounded dynamic range and every IEEE-754 edge case in play. Applying the *same* "reinterpret as float, round to N decimal places" function to both is a category error in two directions:
- Applied to uint8 image bytes, float-decimal-rounding logic either does nothing meaningful (there's no fractional part to round away) or, worse, if the implementation is sloppy about byte-width assumptions (e.g. reinterpreting 4 uint8 RGBA bytes as one float32 instead of 4 separate uint8 values), it corrupts the image data outright rather than quantizing it. The actual cross-hardware noise source for uint8 image output is **not** decimal precision — it's ±1-2 LSB per channel from rasterization/blending/interpolation differences across GPU vendors (different subpixel sample-point conventions, different rounding in fixed-function blend units) — the right tolerance mechanism for this is a small integer-delta tolerance per channel, not a floating-point decimal-place round.
- Applied to float32 tensor bytes, a tolerance mechanism designed for "±1-2 integer LSBs on a 0-255 scale" (if someone tried to reuse image logic for tensors) is meaningless — tensor values can be large, small, negative, or span many orders of magnitude within one output, so a fixed absolute tolerance either does nothing at large magnitudes or destroys all signal at small magnitudes; tensors need magnitude-relative (percentage/ULP-style) tolerance, or decimal-place rounding scaled appropriately to the expected value range for that specific pass.

**Why it happens:**
Both are "the output bytes that get hashed," and the schema's own `InputFormat`/`ColorFormat` enums put integer and float formats in adjacent-looking lists (`RGB8`/`RGBA8` alongside `FLOAT16`/`FLOAT32`/`INT8`/etc. in `ProcessingManager.cpp`'s format-name table) — it's natural to reach for one generic "quantize this buffer" function keyed only on byte size rather than on the declared `DataType`/format.

**How to avoid:**
- Branch quantization strategy explicitly on the artifact's declared data type/format, not on byte layout alone: uint8/integer image formats get a small-integer-delta tolerance (or, if truly no cross-hardware image divergence is expected/acceptable, no quantization at all — verify empirically via the capture harness before assuming otherwise); float tensor formats get the decimal-place/ULP-style float quantization from Pitfalls 1-3.
- Do this dispatch at the point where each processor already knows its own output's type (inside `MNN_Float::StartProcessing`, `RenderProcessor::StartProcessing`, etc.) rather than trying to infer "is this float or int" generically from raw bytes downstream in `ProcessingManager.cpp`'s shared artifact-assembly code — the type information that already exists (`InputFormat`/`ColorFormat` on the schema object) should drive which quantization path runs, matching the existing type-guard pattern this codebase already uses for `PassType`-specific fields (see the prior `PITFALLS.md`'s Pitfall 8 on `.value()` guards).
- If/when a float HDR color format or depth-inclusive readback is added to the render path in a future milestone (schema currently has no such option — see Grounding facts), re-verify this dispatch: the "render path is always uint8" assumption baked into today's quantization design would silently stop covering float render output otherwise.

**Warning signs:**
One quantization function called uniformly from both `MNN_Float`/`MNN_Tensor`-style processors and `RenderProcessor`, with no branch on data type; render-path output hash still changing across GPU vendors after quantization is added (a sign the wrong noise model — decimal precision instead of integer-delta — was applied); a code review that can't point to where the type dispatch happens.

**Phase to address:** Quantization-implementation phase.

### Pitfall 5: One shared `sha256()` utility, at least four independent call sites — quantizing the wrong layer (or all of them uniformly) breaks something

**What goes wrong:**
Because `sha256()` is a single, type-agnostic byte-hasher reused everywhere (see Grounding facts), there are two opposite ways to get the integration wrong:
- **Wrapping `sha256()` itself** to auto-quantize its input "transparently" for every caller fixes the render/tensor cases but also silently reaches the same function's other callers: `MNN_Bool`/`MNN_Int`/`MNN_String`-style processors hashing exact integer/bool/string output (which must **never** be fuzzed — there is no floating-point noise there to tolerate, and doing so would make genuinely different int/bool/string outputs collapse to the same hash), the model-identity hash (`ProcessingManager.cpp:1460`, hashing model *file bytes*, not inference output), and `ComputeManifestHash()` (hashing a struct of identifiers/timestamps/other hashes, not raw sensor/render data). A global wrapper cannot distinguish these without added context the shared utility doesn't have today.
- **Adding quantization only at the most visible call site** (e.g. only where the final `result.hash`/`subTaskResultHash` is computed inside each processor) while leaving the **per-window chunk hashes** (computed earlier, pre-stitch, at `processing_processor_mnn_float.cpp:307` and equivalent lines in other MNN processors) and/or `ComputeArtifactIdentity()`'s independent re-hash of the final bytes (`ProcessingManager.cpp:1426`) un-quantized leaves real gaps: the milestone's own target feature explicitly wants the capture harness to dump "chunk hashes, and the combined hash per run, for cross-machine comparison" — if chunk hashes stay raw/un-quantized while only the final combined hash is quantized, chunk-level cross-machine comparison will still show mismatches even after the final hash matches, defeating half the stated capture-and-diff goal and producing a confusing, partially-fixed result that looks like a bug in the new quantization code rather than a coverage gap.

**Why it happens:**
`sha256()`'s simplicity (a pure function of bytes, no metadata) is exactly what made it easy to reuse everywhere in the first place — that same simplicity means "add quantization near the hash call" has no natural single insertion point; there are several, and only some of them carry float/image data.

**How to avoid:**
- Do not modify `sgprocmanagersha::sha256()`'s signature or behavior at all — keep it as the exact, context-free byte-hasher it already is. Insert quantization as an explicit pre-processing step (a new function, e.g. `QuantizeForHash(data, format)`) called by the *caller* at each site that both (a) hashes numeric render/tensor output and (b) knows the data's type/format — not inside the shared utility.
- Enumerate and cover every relevant call site explicitly, using the four-layer list in Grounding facts as the checklist: per-processor chunk hashes (pre-stitch, in each MNN processor and the render processor), each processor's final `result.hash`, and `ComputeArtifactIdentity()`'s independent re-hash in `ProcessingManager.cpp`. Skip (intentionally, and document why) the model-identity hash and `ComputeManifestHash()` — those must stay exact.
- Since `ComputeArtifactIdentity()` re-hashes the *same* final bytes a processor already hashed for its own `result.hash`, ensure both call sites quantize using the *identical* logic/constant — if a processor quantizes before computing `result.hash` but the raw (unquantized) bytes are what get passed into `ComputeArtifactIdentity()` downstream in `ProcessingManager.cpp`, the two hashes for "the same" output will diverge from each other, not just across machines. Concretely: either quantize the bytes in place before they're handed off (so both hashing layers see already-quantized bytes), or apply the identical quantization function at both of the two hashing layers independently — do not quantize only one of them.

**Warning signs:**
A code review that finds quantization logic in exactly one file/function; the capture harness's chunk-hash diff output still shows mismatches after the combined-hash diff output matches on the same machines; `Artifact::contentHash` (from `ComputeArtifactIdentity`) and a processor's own `result.hash` disagree with each other on a *single* run on a *single* machine (a sure sign quantization was applied inconsistently between the two independent re-hashes of nominally the same bytes).

**Phase to address:** Quantization-implementation phase — this is the primary implementation-sequencing risk of that phase; treat the four-call-site enumeration as a mandatory checklist item, not something to discover incrementally.

### Pitfall 6: Capture harness dumps bytes from a copy downstream of the hash, not the exact bytes that fed `sha256()`

**What goes wrong:**
The milestone's capture-and-diff tool needs to dump "raw output values, chunk hashes, and the combined hash per run" for comparison. The tempting, easy place to grab "the output" is `result.output_buffers` or the artifact's serialized bytes in `ProcessingManager.cpp` — but these are **copies made after** the bytes that actually fed the hash calls. Concretely in this repo: `RenderProcessor` computes `result.hash` from `readbackBytes` (line 2156) and only *afterward* copies those same bytes into `result.output_buffers` (line 2157-2160) via a `std::vector<char>` copy; `MNN_Float` computes `subTaskResultHash` from `stitchedStr` (a `std::string` view over `stitchedOutput`, line 330) and separately, later, copies `stitchedOutput` into `outputBytes` for `result.output_buffers` (lines 355-357). If a future change ever inserts any transformation between the hash call and the `output_buffers` copy (e.g. RENDER-07's `data_transform` post-processing step, which today hard-fails if declared for render passes but is schema-legal and could be wired up later), a capture tool reading from `output_buffers` would silently start diffing **post-transform** bytes while the actual hash was computed on **pre-transform** bytes — the capture tool's diff would then say "these match" or "these differ" about data that was never actually hashed, making its output meaningless without anyone noticing, because nothing crashes or errors.

**Why it happens:**
`output_buffers` is the field most visible/reachable from outside the processor (it's what gets saved to disk, what a test harness would naturally reach for), while the exact byte range passed into each `sha256()` call is a local variable inside the processor's `StartProcessing()`, not surfaced anywhere. Capturing "the output" and capturing "what was hashed" look like the same request until a transformation step sits between them.

**How to avoid:**
- Build the capture harness to instrument (or directly call) the exact same code path that produces the hash — ideally by adding a debug/capture hook immediately adjacent to each `sha256()` call site identified in Pitfall 5's checklist, dumping the literal argument bytes passed to that call, not a value reconstructed from `result.output_buffers` or any other downstream field.
- Capture at all relevant layers, not just the final combined hash: per-window chunk-hash inputs (pre-stitch), per-processor final-hash inputs (post-stitch/post-readback, pre-`ComputeArtifactIdentity`), and the final `combinedHash`/manifest inputs — this lets the diff tool localize *which* layer a cross-machine divergence first appears at, rather than only knowing "somewhere in this job, something differed."
- Treat "the bytes the capture tool dumped" and "the bytes `sha256()` actually saw" as a single invariant to verify once, explicitly (e.g. assert the capture hook's byte buffer's own hash equals the `result.hash`/chunk hash it's paired with) — cheap, and catches this entire pitfall class immediately rather than after a confusing multi-machine debugging session.

**Warning signs:**
The diff tool's reported byte buffer, independently hashed, does not match the chunk/combined hash it's supposedly explaining; a future `data_transform` or post-processing addition to the render or MNN path with no corresponding update to the capture tool's dump point; capture code that reads from `ProcessingResult::output_buffers`/`Artifact` fields rather than from a hook placed next to the actual `sha256()` calls.

**Phase to address:** Capture-harness phase.

### Pitfall 7: Attributing a cross-machine hash mismatch to hardware/vendor noise before ruling out a same-node nondeterminism bug on one of the machines

**What goes wrong:**
DETV-01/DETV-02's same-node determinism guarantee was proven for the render path specifically (explicit clears, `VK_SAMPLE_COUNT_1_BIT`, fixed shader precision, no unordered shader math — see prior `PITFALLS.md` Pitfall 5). It was **not** re-verified for MNN's inference path under this milestone's new cross-hardware lens, nor for the windowed overlap-add stitching arithmetic in `MNN_Float`/similar processors, nor for any nondeterministic-ordering hazards in `ProcessingManager.cpp`'s artifact/manifest assembly (e.g. iteration order over any unordered container, if one exists in that code path). If a capture run on Machine B shows a different hash from Machine A, the intuitive first hypothesis is "cross-hardware floating-point noise, exactly what this milestone is here to tolerate" — but an equally plausible cause is that Machine B (or even Machine A) has *its own* run-to-run nondeterminism unrelated to being different hardware: a different MNN thread-pool size changing internal reduction order, a race in progress-callback-adjacent state, or any RNG/unseeded randomness anywhere upstream of the hashed bytes. Tuning the quantization tolerance to absorb a same-node bug's noise magnitude both wastes the tolerance budget on a problem quantization can't actually fix reliably (an unfixed race can occasionally produce a *larger* divergence than the tolerance covers, causing an intermittent, hard-to-reproduce "mismatch" that looks like the quantization "isn't working") and masks a real bug that should be fixed at the source instead.

**Why it happens:**
This milestone's own framing ("cross-hardware is the new problem, same-node is already solved") makes it easy to assume same-node determinism transfers to the *specific* code paths now being exercised for the first time under this lens (MNN inference determinism was never part of DETV-01/02's proof, which was render-specific) — "already solved" was true for the render path's original claim, not automatically true for every code path this milestone's capture tool will now touch.

**How to avoid:**
- Before attributing any observed capture-tool divergence to cross-hardware noise, first re-run the *same* job N≥2 times on the *same* single machine for every machine in the comparison set, and confirm each machine's own repeat-run hash is stable (the same N≥10 same-node test DETV-01 already established for render, extended to cover the MNN path and the full manifest-assembly pipeline this milestone's capture tool actually exercises). Only diff *across* machines once same-node stability is confirmed independently on each one.
- If a same-node instability is found on any machine during this check, root-cause and fix it as its own issue before treating any of that machine's cross-machine diffs as "real" hardware noise data — a same-node bug's presence invalidates that machine's capture data for tuning the quantization constant (Pitfall 2).
- Keep the same-node re-verification and the cross-machine diff as two clearly separate steps/outputs in the capture harness's workflow and report — don't let a single "ran once per machine, diffed across machines" pass silently conflate the two.

**Warning signs:**
A machine's own repeat-run hash (same job, same machine, back-to-back) is unstable — this alone means any cross-machine number involving that machine is unusable until fixed; the empirically-required quantization tolerance keeps growing as more machines are added to the comparison set, suggesting at least one machine has runaway same-node variance rather than all machines contributing bounded cross-vendor noise; intermittent (not consistent) mismatches on a *repeated* cross-machine comparison between the same fixed pair of machines.

**Phase to address:** Capture-harness phase — this check must run and pass *before* any cross-machine diff data is used to derive the quantization-implementation phase's tolerance constant (see Pitfall 8 on phase sequencing).

### Pitfall 8: Deriving the quantization constant before the capture-and-diff data actually exists, or updating it informally afterward without re-running the empirical validation

**What goes wrong:**
The milestone's own two target features are sequenced: build the capture/diff tooling first, then add the quantization step "before hashing," then empirically validate on ≥3 machines. It's tempting under implementation pressure to reverse or blur this order — write a plausible-sounding quantization constant based on general floating-point knowledge ("8 decimal places should be safe" / "24-bit mantissa minus a few guard bits") and start implementing the rounding step immediately, treating the capture harness as an afterthought verification step rather than the actual source of the tuning data. This produces a constant that is either unjustified-but-happens-to-pass the final 3-machine test (no evidence it generalizes, and no evidence about the wrong-result-still-diverges property from Pitfall 3), or fails the 3-machine test and gets "fixed" by loosening the constant reactively without re-checking whether the new, looser value reintroduces Pitfall 3's security regression.

**Why it happens:**
Writing the rounding function is the more concrete, more obviously "real work" task; running a capture tool across multiple physical machines (the user's Mac + PC plus others) has real logistical friction (access to hardware, coordinating runs), so there's schedule pressure to start on the part that doesn't need that coordination first.

**How to avoid:**
- Treat the capture harness's empirical diff output (max delta, mantissa-bit differences, per data-type) as a hard prerequisite input to choosing the quantization constant, not a confirmation step run after the constant is already chosen. Structure the two phases' deliverables so the quantization-implementation phase literally cites specific captured numbers as its justification.
- If the initial 3-machine validation fails and the constant needs loosening, re-run *both* the cross-machine match test and the wrong-result-still-diverges counter-test (Pitfall 3) at the new value before accepting it — never treat "the match test now passes" alone as sufficient justification for a looser constant.

**Warning signs:**
A quantization constant with no comment/reference to actual captured diff statistics; a git history showing the constant tightened/loosened multiple times with no corresponding new capture data cited each time; the quantization-implementation phase's plan not depending on (waiting for) capture-harness phase output.

**Phase to address:** Both — this is a sequencing risk that spans capture-harness phase (produce the data) and quantization-implementation phase (consume it); the roadmap should make the dependency explicit rather than letting the two phases run in either order or in parallel.

### Pitfall 9: Reusing the pre-existing `mean_abs_diff`/`max_abs_diff` (COV-01) test tolerance as if it were already the answer to this milestone's tolerance question

**What goes wrong:**
This codebase already has a numeric tolerance convention in `ProcessingDatatypesTest` — `mean_abs_diff < 1e-3`, `max_abs_diff < 1e-2` — from validating that `MNN_FORWARD_CPU` and `MNN_FORWARD_VULKAN` produce similar-enough output *on the same machine* (Phase 01.1's COV-01 requirement). Because it's the only precedent for "how much float divergence do we tolerate" already in the repo, it's an easy, plausible-looking shortcut to reuse those exact numbers (or "the same style of check") as this milestone's cross-hardware pre-hash quantization tolerance, reasoning "it's already proven acceptable elsewhere in this codebase." But that check compares two float *arrays* with a tolerance at *test-assertion* time, on one machine, to validate a backend migration — it says nothing about what divergence appears *between different machines' GPUs*, and it operates at a completely different layer (post-hoc array comparison in a test) than pre-hash byte quantization (a production code path that runs on every job, whose output must itself be bit-identical across machines after quantization, not merely "close" per some external assertion).

**Why it happens:**
Both are "float tolerance numbers" in the same codebase, for the same broad domain (MNN Vulkan-related output), which makes them look interchangeable at a glance — but the CPU-vs-Vulkan-on-one-machine divergence this constant was tuned for and the actual GPU-vendor-A-vs-GPU-vendor-B-vs-CPU divergence this milestone must tolerate are different physical phenomena with no guaranteed relationship in magnitude.

**How to avoid:**
- Derive this milestone's quantization tolerance solely from the capture harness's actual cross-hardware/cross-driver/CPU-vs-GPU diff data (Pitfall 2, Pitfall 8) — treat COV-01's `1e-3`/`1e-2` as an unrelated, coincidentally-similar-sounding number from a different problem, not a starting point or sanity bound.
- If the two happen to end up numerically close, document that as an observation, not as evidence either one validates the other.

**Warning signs:**
A commit message or code comment justifying the new quantization constant by referencing `ProcessingDatatypesTest`'s existing thresholds rather than this milestone's own capture data; the quantization tolerance being implemented as a literal reuse of the same `1e-3`/`1e-2` constants without independent derivation.

**Phase to address:** Quantization-implementation phase.

## Technical Debt Patterns

| Shortcut | Immediate Benefit | Long-term Cost | When Acceptable |
|----------|-------------------|-----------------|-----------------|
| Pick a quantization constant "from general float knowledge" without waiting for capture-harness data | Faster start on the implementation phase, no hardware-coordination blocker | Unjustified tolerance, no evidence it generalizes or resists Pitfall 3's security regression (Pitfall 8) | Never for the constant actually shipped — a placeholder during early scaffolding is fine if explicitly replaced before empirical validation |
| Reuse COV-01's `1e-3`/`1e-2` test tolerance as this milestone's pre-hash quantization tolerance | No new number to derive/justify | Conflates two unrelated divergence sources (same-machine CPU-vs-Vulkan vs. cross-machine GPU-vendor); silently wrong magnitude either direction (Pitfall 9) | Never |
| Wrap the shared `sha256()` utility itself to auto-quantize all input | One code change instead of several call sites | Silently fuzzes int/bool/string/model-identity/manifest hashes that must stay exact (Pitfall 5) | Never |
| Only validate tolerance against the "does it match across 3 machines" empirical test | Matches the milestone's literal stated acceptance criterion, fastest to "done" | No evidence the tolerance isn't also loose enough to accept a wrong/adversarial result (Pitfall 3) | Never — this counter-test is cheap (single-machine, no extra hardware) and should always accompany the cross-machine test |
| Capture-harness reads from `result.output_buffers`/`Artifact` fields instead of hooking the literal `sha256()` call-site bytes | Simpler capture code, uses already-public fields | Silently diffs post-any-future-transform bytes instead of what was actually hashed, once anything (e.g. `data_transform`) sits between hash and output_buffers (Pitfall 6) | Acceptable only if explicitly re-verified (one-time self-hash-check) that the captured bytes' hash matches the paired result hash today, with a note to re-check if the render/MNN pipeline gains any post-hash-pre-output-buffers step |

## Integration Gotchas

| Integration | Common Mistake | Correct Approach |
|-------------|----------------|-------------------|
| Shared `sgprocmanagersha::sha256()` utility (single function, ≥4 structurally distinct call sites: per-window chunk hash, per-processor final hash, `ComputeArtifactIdentity`, `ComputeManifestHash`/model-identity) | Adding quantization inside the shared function, or at only one visible call site | Insert a separate `QuantizeForHash`-style pre-processing step, called explicitly by each numeric-output call site that needs it (chunk hash + final hash in each render/tensor processor, plus `ComputeArtifactIdentity`'s independent re-hash in `ProcessingManager.cpp`); leave `sha256()`, model-identity hashing, and `ComputeManifestHash()` untouched (Pitfall 5) |
| `ComputeArtifactIdentity()` (`ProcessingManager.cpp`) re-hashing the same bytes a processor already hashed for `result.hash` | Quantizing inside the processor only, leaving `ComputeArtifactIdentity()` to hash raw (or differently-quantized) bytes | Apply identical quantization logic/constant at both layers, or quantize the bytes in place before either hash call sees them, so the two independent re-hashes of "the same" output agree with each other, not just across machines (Pitfall 5) |
| Render path readback (`RenderProcessor::Readback`, unconditionally uint8 `RGBA8`/`RGB8`) vs. MNN float/tensor output (unconditionally float32/float16) | One generic "quantize this buffer" function applied to both by byte size alone | Dispatch quantization strategy on declared data type/format (`ColorFormat` → small-integer-delta tolerance; float `InputFormat` → decimal/ULP quantization), decided inside each processor where the type is already known (Pitfall 4) |
| Pre-existing `ProcessingDatatypesTest` `mean_abs_diff`/`max_abs_diff` (COV-01) tolerance convention | Treating it as prior art/justification for the new cross-hardware tolerance constant | Derive the new constant independently from capture-harness cross-machine data; COV-01's numbers address a different (same-machine CPU-vs-GPU) divergence source (Pitfall 9) |
| `ProcessingValidationCore::ValidateResults`'s known concatenation bug (explicitly deferred, not fixed this milestone) | Assuming quantization + this milestone's capture tool together "fix verification" | This milestone only makes the *hash* cross-hardware tolerant; the actual subtask-hash comparison mechanism remains broken and is out of scope — document this boundary explicitly wherever the quantized hash is described (Pitfall 3) |

## Performance Traps

| Trap | Symptoms | Prevention | When It Breaks |
|------|----------|------------|----------------|
| Quantization re-parses/re-copies the full output buffer as a separate pass, in addition to the existing stitching/readback copies already in the render and MNN paths | Extra full-buffer traversal added per job, on top of the copies Pitfall 6 already identifies (readback→output_buffers, stitchedOutput→outputBytes) | Fold the quantization pass into an existing traversal (e.g. quantize while assembling `stitchedOutput`/while copying `readbackBytes`) rather than adding a fourth full-buffer pass | Matters once render targets or tensor outputs are large and jobs run at meaningful throughput — not a concern for the milestone's own 3-machine empirical validation runs, but worth avoiding from the start given the existing per-job allocation/copy patterns already flagged as a concern in the prior `PITFALLS.md` |
| Per-window chunk-hash quantization (Pitfall 5) redundantly re-derives type/format dispatch logic (Pitfall 4) on every window instead of once per job | Repeated branch-on-format overhead inside a hot per-window loop (`MNN_Float`'s window loop already runs once per patch) | Resolve the quantization strategy/function pointer once per `StartProcessing()` call (outside the per-window loop), not per window | Only shows up as measurable overhead on jobs with many small windows/patches; correctness is unaffected either way |

## Security Mistakes

| Mistake | Risk | Prevention |
|---------|------|------------|
| Choosing a quantization tolerance loose enough to pass the cross-machine match test without also testing that a wrong/substituted result still diverges | A node returning a subtly wrong result (corrupted model, downgraded precision, adversarially-crafted output) produces a hash that matches the correct result's post-quantization hash, silently defeating the integrity check this hash exists to provide | Always pair the cross-machine empirical match test with an explicit wrong-result-still-diverges counter-test before accepting a tolerance value (Pitfall 3) |
| Describing this milestone's quantized hash as "verification" or "consensus-ready" | Downstream code/design (a future cross-node consensus phase, XNODE-01) could assume the quantized hash alone is sufficient proof of correctness, when `ProcessingValidationCore::ValidateResults`'s comparison-mechanism bug remains unfixed and no redundant-execution plumbing exists yet | Document explicitly, wherever the quantized hash is produced or consumed, that it only makes hash *comparison* cross-hardware tolerant — it is not a complete verification/consensus mechanism on its own (Pitfall 3, PROJECT.md's explicit deferred-scope list) |
| Applying quantization inconsistently across the ≥4 hash call sites (Pitfall 5), leaving some layers un-quantized | An attacker (or a genuine bug) could target whichever hash layer stayed un-quantized/raw, since that layer's comparison would still be strict-bitwise and thus either falsely reject legitimate cross-hardware results (availability impact) or — if that layer is ever the one actually consumed downstream — bypass the intended tolerance in an unpredictable way | Enumerate and cover every call site explicitly (chunk hash, per-processor final hash, `ComputeArtifactIdentity`, deliberately excluding model-identity/manifest hashes) as a checklist, not incrementally |

## "Looks Done But Isn't" Checklist

- [ ] **NaN/Inf/denormal/signed-zero handling:** Often the rounding formula "just runs" on these without an explicit canonicalization branch — verify a unit test feeds each special value through the quantizer and asserts canonical output bytes (Pitfall 1).
- [ ] **Image vs. tensor dispatch:** Often one quantization function is wired up generically by byte size — verify the render path (uint8 `RGBA8`/`RGB8`) and MNN float/tensor path use visibly different quantization logic, not the same decimal-rounding function (Pitfall 4).
- [ ] **All hash call sites covered:** Often only the most visible final-hash call site is patched — verify quantization is applied at chunk-hash time, final-processor-hash time, AND `ComputeArtifactIdentity()`'s independent re-hash in `ProcessingManager.cpp`, and that the two independent re-hashes of the same bytes still agree with each other (Pitfall 5).
- [ ] **Wrong-result divergence test exists:** Often only the "matches across 3 machines" empirical test is run — verify a deliberately-wrong/corrupted result still produces a different post-quantization hash from the correct one (Pitfall 3).
- [ ] **Same-node stability re-checked per machine before cross-machine diffing:** Often a single capture run per machine is treated as ground truth — verify each machine's own repeat-run hash is stable before its cross-machine diff data is used to tune the tolerance (Pitfall 7).
- [ ] **Capture harness dumps pre-hash bytes, not post-copy bytes:** Often the capture tool reads `result.output_buffers`/`Artifact` fields — verify it instead captures the literal argument bytes passed into each `sha256()` call, and self-checks that the captured bytes' own hash matches the paired result (Pitfall 6).
- [ ] **Tolerance constant traceable to real capture data:** Often the constant is chosen first, then "confirmed" by a capture run — verify the constant's value is derived from, and documented with reference to, actual captured cross-machine diff statistics (max delta, mantissa-bit diffs), not COV-01's unrelated same-machine CPU-vs-Vulkan tolerance or a round guessed number (Pitfall 2, Pitfall 8, Pitfall 9).

## Recovery Strategies

| Pitfall | Recovery Cost | Recovery Steps |
|---------|----------------|-----------------|
| Tolerance too loose, discovered via a later security review or an actual bad-result incident (Pitfall 3) | MEDIUM | Re-derive a tighter constant from the existing capture data (no new hardware needed if capture data was saved), re-run the wrong-result-still-diverges counter-test at the new value, re-run the original ≥3-machine match test to confirm it still passes; localized to the quantization function's constant, no schema/wire-format change |
| Quantization applied at only one of the ≥4 hash call sites, discovered when chunk-hash cross-machine diffs still mismatch after combined-hash diffs match (Pitfall 5) | LOW-MEDIUM | Add the same quantization call at the missed site(s) using the checklist in Grounding facts; mechanical, localized change per site, no architecture change |
| Capture harness was diffing post-copy bytes instead of pre-hash bytes, discovered when a self-consistency check fails (Pitfall 6) | LOW | Move the capture hook to sit immediately adjacent to each `sha256()` call site; re-run captures; no product code changes needed, capture-tool-only fix |
| A same-node instability on one capture machine was mistaken for cross-hardware noise, discovered when repeat-run-on-one-machine stability checks are retrofitted (Pitfall 7) | MEDIUM | Root-cause the specific same-node nondeterminism source (thread-pool sizing, an unseeded RNG, an ordering hazard) using the same mechanisms as the prior `PITFALLS.md`'s Pitfall 5 recovery steps; discard that machine's capture data until fixed, then re-capture |
| Special-value (NaN/Inf/denormal/signed-zero) corruption in the quantizer, discovered via a fuzz test or an unexplained render/inference artifact | LOW | Add the explicit canonicalization branch ahead of the rounding arithmetic; localized fix to the quantization function, covered by the unit tests from the "Looks Done But Isn't" checklist |

## Pitfall-to-Phase Mapping

| Pitfall | Prevention Phase | Verification |
|---------|-------------------|---------------|
| Naive rounding corrupts NaN/Inf/denormal/signed-zero (Pitfall 1) | Quantization-implementation phase | Unit test feeds each IEEE-754 special value through the quantizer, asserts canonical output bytes — single-machine, no hardware dependency |
| Fixed tolerance doesn't generalize across reduction depth/workload shape (Pitfall 2) | Quantization-implementation phase (constant), fed by capture-harness phase (data) | Tolerance constant documented with reference to actual captured max-delta/mantissa-bit-diff statistics across the real render + MNN workloads, not a synthetic toy case |
| Tolerance loose enough for noise is loose enough for wrong results (Pitfall 3) | Quantization-implementation phase | Explicit wrong/corrupted-result counter-test passes (still diverges) alongside the ≥3-machine match test |
| Image (uint8) vs. tensor (float) quantization treated identically (Pitfall 4) | Quantization-implementation phase | Code review confirms distinct quantization paths keyed on declared data type/format, not byte size alone |
| Wrong hash layer(s) quantized among the ≥4 `sha256()` call sites (Pitfall 5) | Quantization-implementation phase | Chunk-hash cross-machine diffs and combined-hash cross-machine diffs both pass; a processor's `result.hash` and `ComputeArtifactIdentity()`'s independent re-hash of the same bytes agree with each other |
| Capture harness dumps post-copy, not pre-hash, bytes (Pitfall 6) | Capture-harness phase | Self-check: captured buffer's independently-computed hash equals the paired chunk/combined hash from the same run |
| Cross-machine mismatch misattributed to hardware before ruling out a same-node bug (Pitfall 7) | Capture-harness phase | Each machine's own repeat-run hash confirmed stable (extending DETV-01's N≥10 same-node test to the MNN + manifest-assembly paths) before any cross-machine diff data is used |
