# Render Backend Decision: Multi-Backend Fallback Reconsideration

**Domain:** Multi-backend rendering library options (Vulkan primary + graceful CPU/OpenGL-class fallback) for SGProcessingManager's `RenderProcessor`
**Researched:** 2026-07-28
**Confidence:** MEDIUM (license claims verified via direct LICENSE-file fetches — HIGH within this section; backend/headless/maintenance capability claims are web-search-sourced and cross-referenced where possible — MEDIUM; a few single-sourced claims are explicitly flagged LOW)

> **Recommendation in one line:** Stay with the prior Vulkan-only, hand-rolled `RenderProcessor` (vk-bootstrap + VMA + shaderc) for the GPU-present path — no rendering *engine* changes this — but add **Mesa lavapipe** (preferred) or **Google SwiftShader** as a bundled software Vulkan ICD so the exact same `RenderProcessor` code path executes on the CPU when a node has no Vulkan-capable GPU. This is the only combination that is architecturally equivalent to MNN's graceful backend fallback, because the fallback happens *underneath* the Vulkan API your code already calls, not by switching to a different rendering library with a different API surface.

## The core finding (read this first)

**No C++ rendering engine or library gives you an MNN-style, application-level "if Vulkan unavailable, fall back to a CPU rasterizer" switch.** Every engine surveyed (bgfx, Diligent Engine, sokol_gfx, Ogre-Next, The Forge, Filament) treats "fallback" as **picking a different GPU API** (Vulkan → D3D11 → GL, etc.) — none of them ship or wire in a genuine software rasterizer as one of their backend choices. Their "headless"/"noop"/"dummy" modes (bgfx's `BGFX_RENDERER_TYPE_NOOP`, sokol's dummy backend) are **test stubs that discard draw calls and produce no pixels** — not a rendering fallback, a no-op.

The place a genuine CPU fallback *does* exist is one layer down, at the **Vulkan driver/ICD level**: Google's **SwiftShader** and Mesa's **lavapipe** (built on `llvmpipe`) are full software implementations of the Vulkan API itself. Install/bundle one of these as an alternate Installable Client Driver (ICD), and the **same `VkInstance`/`VkDevice`/`VkPipeline` calls your existing `RenderProcessor` already makes** get executed on the CPU instead of a GPU — selected by the Vulkan loader's ICD enumeration (`VK_ICD_FILENAMES` or system driver registration), completely transparent to your application code. This is the direct structural analog of what MNN does for inference — MNN picks a different *backend implementation* underneath one API; a software Vulkan ICD picks a different *implementation* underneath the same Vulkan API. It is not "an app picking a different graphics library" (which is what bgfx/Diligent/Ogre/The Forge/Filament all actually offer), and that distinction is the entire point of this research.

This changes the recommendation's *shape*, not its *foundation*: the prior Vulkan-only `RenderProcessor` research (vk-bootstrap + VMA + shaderc, hand-rolled on raw Vulkan) remains correct and does not need to be replaced with an engine. What needs to be added is a **deployment-time fallback ICD**, not a **code-time rendering-library swap**.

## Recommendation for THIS project

**Do not replace the Vulkan-only `RenderProcessor` architecture from the prior STACK.md.** None of the six engines evaluated here beat that decision on its own terms — every one of them is either (a) still just "pick a different GPU API," which is a real capability but not what closes the actual gap the user identified, or (b) heavier/more engine-shaped than a single schema-declared pipeline needs, echoing the prior research's rejection rationale.

**What changes: add a software-Vulkan-ICD fallback path underneath the existing Vulkan-only `RenderProcessor`, not instead of it.**

1. **Primary path (unchanged from STACK.md):** vk-bootstrap + VMA + shaderc on top of the already-vendored Vulkan-Headers/Vulkan-Loader, hand-rolled `RenderProcessor`. This runs against whatever real GPU driver the Vulkan loader finds on a node with Vulkan-capable hardware.
2. **Fallback path (new):** vendor **Mesa lavapipe** (preferred) or **Google SwiftShader** as an additional ICD. When `vk-bootstrap`'s device-selection step finds zero suitable physical devices (or the loader finds no hardware ICD at all), have node startup register the software ICD (via `VK_ICD_FILENAMES` or an equivalent programmatic ICD-path override) so the **exact same** `RenderProcessor` code executes — just on the CPU. No second code path, no second rendering API, no schema/pipeline-builder duplication.
3. **Prefer lavapipe over SwiftShader if forced to pick one**, on performance grounds (reported to outperform SwiftShader in several published benchmarks) and because it's the more "native" choice for a project already living in the Vulkan/Khronos ecosystem — but note the vendoring cost tradeoff below before committing.

**Practical vendoring note (open question, flag for a scoping decision, not resolved by this research pass):** SwiftShader is the easier of the two to vendor cleanly into `thirdparty/` as an isolated CMake-buildable git submodule scoped exactly to "give me a software Vulkan ICD," matching the existing convention. Lavapipe is a first-class, better-performing driver, but it lives inside the full Mesa tree rather than as a narrowly-scoped standalone repo — vendoring it via the existing `git submodule` + `find_package`/`include_directories` convention is more awkward (Mesa's own build system is Meson, not CMake, and it's typically consumed as a prebuilt driver artifact rather than built piecemeal as an app-level dependency). **Recommend starting with SwiftShader for the fallback ICD given the existing CMake-submodule vendoring convention, revisiting lavapipe only if SwiftShader's CPU performance proves inadequate for real render-job SLAs.**

**What this does NOT solve:** a software Vulkan ICD is still meaningfully slower than a real GPU (CPU rasterization is fundamentally more expensive per-pixel), so this is explicitly a "runs somewhere over fails outright" mechanism, matching the project's stated priority — not a performance-equivalent fallback. This mirrors MNN's own CPU-fallback tradeoff (CPU inference is also slower than GPU inference) and is the correct framing for downstream job-scheduling/SLA expectations: a render job routed to a non-Vulkan-capable node should expect to complete, not expect to complete fast.

## What NOT to Use (updated from prior STACK.md, multi-backend-specific reasoning)

| Avoid | Why (multi-backend-fallback-specific reasoning) | Use Instead |
|---|---|---|
| Treating bgfx's "noop" or sokol's "dummy" backend as a CPU fallback | Both are test/CI stubs that accept API calls and produce zero pixels — not rendering fallbacks in any functional sense | Software Vulkan ICD (SwiftShader/lavapipe) underneath the real Vulkan backend |
| Adopting bgfx/Diligent/Ogre-Next/The Forge/Filament specifically *for* multi-backend fallback | Every one of them only offers "switch to a different real GPU API" (Vulkan↔D3D↔GL↔Metal) — none solve the true no-GPU-available case; adopting a full engine for this reason pays a large architectural cost for a capability it doesn't actually deliver | Keep the existing thin hand-rolled `RenderProcessor`; add the ICD fallback layer instead |
| sokol_gfx's Vulkan backend as the primary Vulkan implementation for this milestone | Explicitly experimental as of Dec 2025: author-documented limited platform coverage (Linux/X11-tested-on-one-iGPU only), no memory allocator equivalent to VMA, single-swapchain-only — far less mature than the vendored Vulkan-Headers/Loader + vk-bootstrap + VMA combination already recommended | vk-bootstrap + VMA + shaderc on raw Vulkan (unchanged from STACK.md) |
| Assuming Mesa lavapipe vendors as easily as a typical `thirdparty/` git-submodule + CMake target | It's part of Mesa's much larger Meson-built tree and is normally consumed as a prebuilt driver artifact, not source-built piecemeal | Start with SwiftShader (standalone CMake-buildable repo) for the fallback ICD; revisit lavapipe only if performance demands it |
