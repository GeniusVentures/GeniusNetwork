<objective>
Fix the MoltenVK static-link ObjC category drop: after migrating MoltenVK to the static `libMoltenVK.a`, every SuperGenius test that runs MNN Vulkan inference dies with `doesNotRecognizeSelector: setBorderColorMVK:` because static-archive linking never pulls MoltenVK's ObjC category object files (their `__OBJC_$_CATEGORY_*` symbols are LOCAL). Adding `-Wl,-ObjC` to the linker command at all 5 `Vulkan::Vulkan` consumer sites makes the linker load all ObjC members of static archives, restoring the categories.

Purpose: The processing_conformance test suite (cancellation, hashing, migration, regression, security, capability, executor) is red on macOS after the MoltenVK static-lib migration. Root cause is already empirically validated (lldb backtrace + `nm` verification + manual relink with `-Wl,-ObjC` → 8/8 and 7/7 PASS) — this task mechanicalizes that validated fix into CMake so it survives reconfiguration.

Output: 5 one-line `set_property` appends (plus comment), one atomic commit per nested repo (4 repos), green processing_conformance tests on SuperGenius/build/OSX/Release.

Diagnosis ground truth (do NOT re-derive, no research needed):
- Backtrace: MNN `VulkanRuntime` ctor → `vkCreateSampler` → MoltenVK `MVKSampler::newMTLSamplerDescriptor` → `[MTLSamplerDescriptor setBorderColorMVK:]` → `doesNotRecognizeSelector:` → NSException.
- `libMoltenVK.a` contains ObjC category members (`MTLSamplerDescriptor+MoltenVK.m.o`, `MTLRenderPipelineDescriptor+MoltenVK.m.o`, `CAMetalLayer+MoltenVK.mm.o`, `NSString+MoltenVK.mm.o`) exporting only LOCAL `__OBJC_$_CATEGORY_*` symbols — undefined-symbol resolution can never pull them.
- Safety: `libMNN.a` and all other archives on SuperGenius link lines contain ZERO ObjC members, so `-ObjC` only pulls MoltenVK's categories. Do NOT use `-force_load` on libMoltenVK.a — its SPIRV-Tools/spirv-cross members duplicate `libshaderc_combined.a` symbols → duplicate-symbol link errors.
</objective>
