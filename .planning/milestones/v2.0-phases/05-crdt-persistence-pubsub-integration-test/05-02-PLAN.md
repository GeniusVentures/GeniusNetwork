<objective>
Give the main node the ability to discover child wallets registered to it: a `GetRegistrationsForMain` CRDT scan that returns child address, main address, sequence, and metadata for every registration naming a given main, and a CID notification handler that automatically follows newly discovered children by calling `AddListenTopic(child_addr)` when a reg/ element arrives whose `main_address` matches the local node.

Purpose: Without the discovery read path, a main node has no way to learn about children that registered with it. Without the CID handler (following behavior per D-49), the main node does not automatically subscribe to the child's pubsub channel — the discovery push trigger is the active half of RIMPL-05 in Phase 5 scope.

Output: `GetRegistrationsForMain` API at both TransactionManager and GeniusNode layers (RIMPL-06); CID notification callback registered on the `reg/` namespace that triggers `AddListenTopic(child_addr)` when the registration names the local node (RIMPL-05 reception side). The broadcast half of RIMPL-05 is already satisfied by Phase 4's `RegistrationTransaction::GetTopics()` including `main_address_`.
</objective>

    ```
    void TransactionManager::RegElementCallback( crdt::CRDTCallbackManager::NewDataPair new_data, std::string cid )
    {
        // Deserialize the element value to check main_address
        auto maybe_tx = DeSerializeTransaction( new_data.second );
        if ( maybe_tx.has_error() || maybe_tx.value()->GetType() != "registration" )
        {
            return;
        }
        auto reg_tx = std::dynamic_pointer_cast<RegistrationTransaction>( maybe_tx.value() );
        if ( !reg_tx )
        {
            return;
        }

        // D-49: if this registration names the local node as main, follow the child
        if ( reg_tx->GetMainAddress() == account_m->GetAddress() )
        {
            m_logger->info( "Discovered new child registration: child={}, main={}, following child channel",
                            reg_tx->GetSrcAddress().substr(0, 16),
                            reg_tx->GetMainAddress().substr(0, 16) );
            globaldb_m->AddListenTopic( reg_tx->GetSrcAddress() );
        }
    }
    ```

    - The callback uses `new_data.second` (the value buffer from NewDataPair) which contains the full protobuf bytes — CRDT already resolved the CID to content before firing the callback

    - No error return needed — callback is void; failures in deserialization or cast are silently skipped (element already passed FilterRegistration)
    - The callback does NOT need to re-validate the signature — FilterRegistration already rejected invalid elements; surviving elements are pre-validated

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| CRDT reg/ scan → caller | GetRegistrationsForMain reads from CRDT (which may contain data from any peer) and returns discovery entries to the caller |
| reg/ NewElementCallback → AddListenTopic | The CID handler trusts a FilterRegistration-accepted element's main_address field — an attacker who crafts a valid RegistrationTx naming a victim's main could cause the victim to waste resources following a bogus child channel |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-07 | Spoofing | GetRegistrationsForMain results | mitigate | Data sourced from CRDT, which is gated by FilterRegistration (signature + sequence checks). Results reflect only filter-validated registrations |
| T-05-08 | Tampering | reg/ value during CRDT scan | mitigate | Deserialization + type check + dynamic_pointer_cast failures in GetRegistrationsForMain skip corrupted entries silently |
| T-05-09 | Information Disclosure | GetRegistrationsForMain output | accept | RegistrationDiscoveryEntry contains only public addresses and metadata — no private keys or credentials |
| T-05-10 | Denial of Service | AddListenTopic following bogus children | mitigate | CID handler only follows after FilterRegistration validation (signature must be valid against a real keypair). Creating many valid keypairs to spam-follow is expensive (key generation + registration cost). Consensus authority gate (deferred) would further mitigate by requiring parent-child authority proof |
| T-05-11 | Elevation of Privilege | RegElementCallback triggers AddListenTopic without authority check | accept | v2.0 scope: consensus authority gate (CheckParentChildAuthority) is deferred. Any filter-validated registration triggers follow. Accepted risk for this milestone per ROADMAP/REQUIREMENTS.md "Out of Scope" |
</threat_model>
