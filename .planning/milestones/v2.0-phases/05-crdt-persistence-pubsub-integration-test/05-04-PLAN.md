<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Test translation units → Production headers | `friend` declarations grant test code access to `protected:` members in production headers (`TransactionManager.hpp`, `GeniusNode.hpp`). The friend classes (`RegTestAccess`, `ChildRegistrationIntegrationTest`) exist ONLY in test `.cpp` files under `SuperGenius/test/` — they are never compiled into production binaries. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-01 | Elevation of Privilege | TransactionManager.hpp:319 (`friend class RegTestAccess;`) | accept | RegTestAccess is defined only in `SuperGenius/test/src/multiaccount/regtest/child_registration.cpp` — a test translation unit never linked into production binaries. The `friend` keyword is a compile-time access gate; at runtime there is no attack vector. An attacker would need source-level code injection into a production .cpp file to define a class named `RegTestAccess` — this requires compromising the build system, at which point they already own the binary. Production binaries compiled without test .cpp files have no `RegTestAccess` definition, making the friend declaration inert. |
| T-05-02 | Elevation of Privilege | GeniusNode.hpp:741 (`friend class ChildRegistrationIntegrationTest;`) | accept | Same rationale as T-05-01. The `account_` member holds the GeniusAccount (including private key). In production, no translation unit defines `ChildRegistrationIntegrationTest`, so the friend declaration is inert. The existing `friend class MultiAccountTestAccess;` (line 740) already has the same access to `account_` and has shipped safely for years — this follows the identical pattern. |
| T-05-03 | Tampering | registration_transaction_test.cpp, child_registration.cpp — proto-level signature tampering | mitigate | The WR-02/WR-03 fix changes signature-invalidation from raw byte-offset (`serialized[size-5] ^= 0xFF`) to proto-level DAG signature modification (`dag_mutable->signature()[last_byte] ^= 0xFF`). This improves determinism: the byte flip is guaranteed to land inside the signature field rather than an arbitrary protobuf field. If the protobuf re-serialization fails, `ASSERT_TRUE(SerializeToArray(...))` catches it. The tampered bytes are confined to test-only CRDT element injection — no production code path is affected. |
| T-05-SC | Tampering | npm/pip/cargo installs | accept | No package manager operations in this plan — C++ source changes only. No new dependencies. |

## Security Summary

The two friend declarations are additive, compile-time-only access grants following the identical pattern as the 5 existing friend declarations in TransactionManager.hpp (lines 314-318) and 2 existing in GeniusNode.hpp (lines 739-740). They carry no runtime risk. The signature tampering fix improves test determinism and eliminates a flaky test that could mask a real FilterRegistration regression.
