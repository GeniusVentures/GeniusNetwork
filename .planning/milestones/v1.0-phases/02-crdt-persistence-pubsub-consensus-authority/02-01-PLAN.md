**Section 6 — Certified Status Flag Design (~60-80 lines):**
- State D-26: The reg/ CRDT filter accepts pre-certificate (optimistic storage), but a certified status flag marks consensus-confirmed records. Main wallet only acts on certified registrations.
- Document the three implementation options from RESEARCH.md lines 281-295 (and PATTERNS.md lines 283-295):
  - **Option A (separate CRDT key):** Key `/bc-{net}/reg-cert/{child_addr}` with value = certificate CID. Durable across restarts. Needs cleanup on detach (Phase 3 LIFE-04).

- State the **recommendation** (RESEARCH.md open question 1): Use **Option C augmented with Option A** — the in-memory `tx_processed_m` map with status=CONFIRMED is the primary authoritative source (matches existing `ChangeTransactionState` pattern at `TransactionManager.cpp:5110-5184`).     2. Call `ChangeTransactionState(reg_tx, TransactionStatus::CONFIRMED)` — same path as all other tx types

- State the core tension: CRDT is eventually consistent (different peers see different states at different times), but authority decisions must be totally ordered and fork-free.

  - **Tier 1 — Nonce chain (consensus ordering):** RegistrationTx carries `DAGStruct.nonce` (field 4 in DAGStruct). The nonce chain (`sgns.nonce.v1`) prevents two transactions at the same nonce from both being certified. First-to-consensus wins.
  - **Tier 2 — Sequence (registration lineage):** RegistrationTx carries `sequence` (field 3 in RegistrationTx per `docs/registration-protocol.md` §2). The reg/ CRDT filter rejects lower-or-equal sequences as best-effort optimization. Sequence monotonicity is enforced at consensus level by the nonce chain — you can't get two competing sequences certified at the same nonce.
- Document the tie-break semantics for competing registrations:
  - Two RegistrationTx with the same `sequence` but different `nonce` values → first to receive a consensus certificate at its nonce is authoritative
  - The nonce chain inherently prevents both from being certified (single nonce slot per account)
  - The reg/ filter then rejects any subsequent attempt with the same sequence (seq not strictly higher per D-13 gate 3)
  - Result: deterministic winner — the one that reached consensus first. No ambiguous state.
  - This is NOT a "first-to-CRDT wins" model — consensus ordering, not CRDT arrival order, determines the winner.
- Document the two-tier separation (D-26 restatement):
  - **CRDT tier:** Optimistic storage. FilterRegistration accepts well-formed registrations immediately. Data propagates via DAG sync to all peers. This is EVENTUAL consistency.
  - **Consensus tier:** Authoritative ordering. The nonce chain certifies exactly one RegistrationTx per nonce slot. `OnConsensusCertificate` marks it CONFIRMED. Downstream authority rules only read certified state. This is TOTAL ordering.
  - This cleanly resolves the tension: CRDT handles data propagation and availability; consensus handles authority and fork prevention.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Child node → CRDT | RegistrationTx protobuf enters CRDT storage through FilterRegistration. Malformed or malicious payloads must be rejected at this boundary; filter MUST validate signature, sequence monotonicity, and well-formedness before accepting. |
| Child node → PubSub | Child publishes RegistrationTx CID on main's pubsub topic. Any peer can publish on any topic; the main MUST NOT trust topic membership. CID resolution + certification check is the authoritative validation. |
| PubSub → Main node | Main receives untrusted CID notification. The CID must be resolved from CRDT (content-addressed — cannot produce wrong content for a given CID). The resolved registration must be checked for consensus certification before the main acts. |
| CRDT → Consensus validator | RegistrationTx proposer submits to `sgns.nonce.v1` subject. The nonce chain provides total ordering; validators independently verify the tx via `HandleNonceConsensusSubject` → `ValidateTransactionForConsensus`. A validator's local CRDT may have stale state (see Pitfall 1). |
