**Subsection 5.2: The Child-Signed-Only Model**
- "The child wallet constructs a RegistrationTx, calls `tx.FillHash()` to compute the data_hash, then calls `tx.MakeSignature(*child_account)` to produce a secp256k1 ECDSA signature over the data_hash using the child's own private key. Consensus validates the signature via `GeniusAccount::VerifySignature(child_address, sig, data)`. The main wallet performs NO cryptographic operation during registration."
- "The main wallet's public key (`main_address` field) is supplied to the child process via the connect flow (see §5.3). It is data in the child-signed tx — consensus does NOT verify that the main wallet signed this tx or that the named main consented to the registration."

**Subsection 5.3: Security Impact Analysis (per D-05)**
Document the three-part security analysis explicitly:

1. **Any child can claim any main:** "Because there is no main signature, consensus cannot cryptographically verify that the named main wallet actually consented to the registration. A malicious child could construct a RegistrationTx claiming any main wallet address as its `main_address`."

2. **Impact is bounded to discovery spam:** "This is acceptable because registration grants the child ZERO authority over the main wallet. The child cannot spend the main's funds (requires main's signature — Phase 2 CONS-01), cannot recover assets to any address other than the registered main (Phase 2 CONS-02), and cannot modify consensus rules. The only practical impact is discovery-view spam: a main wallet might see unsolicited 'claimed child' entries when listing its registered children."

3. **v2 hardening path:** "If discovery spam becomes a real problem in production, an optional main acceptance signature can be added as a v2 upgrade: the main wallet submits a signed `RegistrationAcceptance` message that moves a pending registration to confirmed state. This is deferred — not designed in Phase 1."

**Subsection 5.4: Why NOT Dual-Signature (Rationale)**
- "Dual-signature would require the main wallet to be online and sign during the registration flow, adding UX friction (the user must approve a signing request in the GNUS Wallet app). It would also require the main's private key to be accessible during a game session or child-app initialization. The child-signed-only model eliminates this friction and keeps the main's private key entirely out of the game/child process."

**Subsection 5.5: Connect Flow — Main Pubkey Delivery (REG-04)**
- Per D-10: "The connect flow (GNUS Wallet app / 'Connect GNUS Wallet' UI) delivers ONLY the main wallet's public key to the child app. The main performs NO signing during registration."
- Specify the transport-agnostic handshake: (1) child app initiates "connect to main wallet" flow, (2) user approves in GNUS Wallet app, (3) GNUS Wallet app returns the main wallet's public key (128-hex, no prefix) to the child app, (4) child app uses this public key as `main_address` in the RegistrationTx it constructs and signs.
- "The concrete 'Connect GNUS Wallet' platform UI flows (Android, iOS, Windows, macOS, Linux) are out of scope for Phase 1 (deferred to v2 / PLAT-01, PLAT-02). This document specifies the transport-agnostic handshake only: the child receives the main's public key via an out-of-process channel."
- Per REG-04: "The main private key never enters the game/child process — satisfied trivially because the main performs zero cryptographic operations during registration."

**Section 6: Sequence Numbering & Replay Protection (REG-05)**

- **Subsection 6.1: Dual Counter Design (per D-09)**
  - "RegistrationTx carries TWO counters, serving different purposes:
    - `DAGStruct.nonce` (uint64): Per-account transaction ordering. Every transaction (transfer, registration, escrow) from the child account consumes a nonce. This drives the existing TransactionManager nonce validation and prevents replay of any transaction from the same account.
    - `sequence` (uint64): Per-child registration lineage. Scoped exclusively to registration events for this child. The first registration = 1; replacements increment the sequence to 2, 3, etc. This separates registration lineage from account tx ordering."
  - Explain why both are needed (Pitfall 2): "If RegistrationTx used only `DAGStruct.nonce`, a child's normal transfer transactions could 'push out' a registration — the nonce is consumed by a transfer, and the registration can't reuse it. If only `sequence` was used without `nonce`, the registration would bypass the standard per-account tx ordering that TransactionManager expects. Two counters = two independent ordering domains."

- **Subsection 6.2: Authoritative Registration Selection (Phase 2 Hand-off)**
  - "Consensus selects the highest valid `sequence` as the authoritative registration for a child. If two registrations arrive with equal `sequence` values, a tie-break rule is needed. The tie-break rule and the exact consensus-ordering mechanism are designed in Phase 2 (SYNC-01, CONS-01)."
  - "This document defines that the `sequence` field exists, is uint64, is monotonic per-child, and that consensus selects the highest valid sequence as authoritative. The field is set by the child wallet when constructing the RegistrationTx (sequentially incrementing from its last used sequence)."

- **Subsection 6.3: Replay Protection**
  - "Consensus rejects RegistrationTx where `DAGStruct.nonce ≤ confirmed_nonce` (existing TransactionManager nonce validation). This prevents replay of the exact same RegistrationTx."
  - "Consensus rejects RegistrationTx where `sequence ≤ last_confirmed_sequence` for the same child (Phase 2 consensus logic, derived from CRDT registration state). This prevents replay of an old registration after a newer registration with a higher sequence is already confirmed."
  - "The combination of nonce-based account ordering and sequence-based registration lineage provides defense-in-depth against replay attacks."
  - Traceability: REG-05 satisfied by this section.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Child process → RegistrationTx | The child constructs and signs the RegistrationTx. The child process is untrusted — it may contain a compromised game. The registration MUST NOT grant any authority over the main wallet. |
| Connect flow → main_address field | The main wallet's public key crosses from the GNUS Wallet app (trusted) into the child/game process (untrusted). The pubkey is data only; the main's private key NEVER crosses this boundary. |
| RegistrationTx → Consensus | The child-signed RegistrationTx enters the consensus validation path. Consensus verifies the child's signature but does NOT verify main consent (per D-04/D-05). The bounded impact (discovery spam only) relies on Phase 2 consensus authority rules. |
| Proto wire format → Deserializer | Malformed proto wire data arrives at `RegistrationTransaction::DeSerializeByteVector`. Protobuf `ParseFromArray` returns false on malformed data — no crash, no OOB, no state corruption. |
