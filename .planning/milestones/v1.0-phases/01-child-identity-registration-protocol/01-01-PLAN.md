## Phase Goal

**As a** SuperGenius developer, **I want to** understand the child-wallet identity model — how child wallets are created, how they hold keys, how they own UTXOs, and how their identity is derived from consensus-visible state rather than creation-time metadata — **so that** I can implement child wallets in the SuperGenius node without ambiguity about what makes an account a child.

**Section 4: Nonce Tracking**
- State: "A child wallet tracks its own per-account nonce independently of any other wallet. Because the child is a separate GeniusAccount, its nonce counter (`GetProposedNonce`, `ReserveNextNonce`, `confirmed_nonces_` map) is naturally distinct from the main wallet's nonce."
- Per D-03, IDENT-02: "No new nonce machinery is needed. The child wallet reuses the existing per-account nonce system in GeniusAccount. When a child creates a transaction (transfer, registration, escrow), it calls `ReserveNextNonce()` to obtain the next nonce, embeds it in `DAGStruct.nonce`, and the transaction flows through the standard nonce validation in TransactionManager."
- Document the nonce lifecycle: (1) child calls `GetProposedNonce()` to preview the next nonce without reserving, (2) child calls `ReserveNextNonce()` to atomically claim the next nonce, (3) nonce is embedded in `DAGStruct.nonce` when constructing any transaction, (4) after consensus confirms the transaction, `confirmed_nonces_` is updated, (5) if a transaction is rejected or abandoned, `ReleaseNonce(nonce)` returns the nonce to the pool.
- Explicitly state: "The child's nonce is scoped to the child account only. A child's nonce=7 and a main's nonce=7 are unrelated counters in separate GeniusAccount instances. Registration transactions consume a child nonce just like any other transaction, but also carry a dedicated `sequence` field for registration lineage (see registration protocol design doc, REG-05)."
- Traceability: IDENT-02 satisfied by this section.

**Section 5: UTXO Ownership**
- State: "A child wallet owns UTXOs via the standard `UTXOEntryRecord.owner_address` field (SGTransaction.proto:57). The child's address (128-hex, derived from its independent secp256k1 public key) is set as the `owner_address` when UTXOs are created for that child."
- Per D-02: "No new UTXO ownership scheme is needed. Child-owned assets are distinguishable by owner_address alone — querying `UTXOEntryRecord` where `owner_address == child_address` returns all child-owned UTXOs. This works identically to any other wallet."
- Document the flow: (1) child wallet receives funds (transfer tx credits UTXOs to child's address), (2) child wallet creates a transaction referencing its owned UTXOs as inputs (standard GeniusUTXO input selection by owner), (3) consensus validates that the child's signature authorizes spending those UTXOs (standard cryptographic ownership check), (4) output UTXOs from child transactions have `owner_address` set to the destination addresses (which may be the child itself, the main, an external address, or a developer wallet).
- Explicitly state: "`GeniusUTXO.hpp` and `UTXOStructs.hpp` are NOT modified. Child UTXO ownership uses the existing owner_address mechanism that all wallets use today. The only difference is semantic: for child wallets, the `owner_address` happens to be a child's address rather than a main wallet's address — but the UTXO layer does not distinguish."
- Traceability: IDENT-04 satisfied by this section.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Key generation (EthereumKeyGenerator) | Child keypair is generated within the child process; compromise of the child process compromises the child keypair, but NOT the main keypair (independent keypair per IDENT-01) |
| Address derivation | Child address derived from its own secp256k1 public key; no cryptographic linkage to main wallet address |
| UTXO ownership (owner_address) | UTXOs are owned by address; a child-owned UTXO has the child's address in owner_address — no authority inheritance from parent |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-01 | Spoofing | Child identity (creation path) | mitigate | The identity model MUST document that a child wallet's authority is bounded to its own keypair — a child key cannot sign as a main wallet. Independent secp256k1 keypair (IDENT-01) ensures no cross-account impersonation. |
| T-01-02 | Tampering | Nonce counter (GeniusAccount) | mitigate | Per-account nonce machinery (`ReserveNextNonce`, `confirmed_nonces_`) is existing, battle-tested infrastructure. Child reuses it unchanged (D-03). Nonce replay protection is inherited from TransactionManager validation. |
| T-01-03 | Information Disclosure | Key derivation (EthereumKeyGenerator) | mitigate | The identity model MUST explicitly state that child keypair is NOT HD-derived from main seed. Compromise of child reveals nothing about main. This is a design constraint, not a runtime check — the model must be clear enough that implementers cannot accidentally derive child keys from main seed. |
| T-01-04 | Elevation of Privilege | Emergent identity (registration-based) | accept | The design states "child-ness is emergent from a consensus-visible registration record" — no creation-time permission enforcement. This is acceptable because Phase 1 defines identity only; Phase 2 consensus authority rules (CONS-01..06) enforce that a child registration grants ZERO authority over main funds. The identity model document MUST flag this deferred authority as a Phase 2 hand-off. |
| T-01-SC | Tampering | npm/pip/cargo installs | accept | No new packages installed — design-documentation phase. |
</threat_model>
