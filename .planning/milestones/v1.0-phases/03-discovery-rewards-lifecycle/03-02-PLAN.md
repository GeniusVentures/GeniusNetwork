**Section 6: Lifecycle State Machine (LIFE-01)**
- Per D-34: "The lifecycle state machine has four states. States are derived from the `reg/{child_addr}` CRDT record's fields — no separate state-machine engine is needed."
- Document the four states:

| State | CRDT Condition | Description |
|-------|---------------|-------------|
| **Unregistered (standalone)** | No `reg/{child_addr}` record exists | Child operates independently. Reward policy from SDK DevConfig (D-30). Can receive, hold, transfer assets. |
| **Registered** | `reg/{child_addr}` exists with non-empty `main_address` AND `detach_flag == false` | Main has recovery authority (CONS-02). Child broadcast is active (D-15/D-16). Reward policy from RegistrationMetadata (or DevConfig fallback for pre-certification escrows). |
| **Detached** | `reg/{child_addr}` exists with `detach_flag == true` AND initiator was the child (child-signed RegistrationTx with detach_flag) | Main has read-only visibility (inspect history/balance), zero recovery authority. Child retains all UTXOs. |
| **Revoked** | `reg/{child_addr}` exists with `detach_flag == true` AND initiator was the main (main-signed RevokeTx) | Same CRDT outcome as Detached (same flag), different initiator. Main has read-only visibility, zero recovery authority. |

- Per D-34: "There is no 'registration-pending' state — with child-signed-only (D-04), registration is immediate upon certification; there's no main-consent gate. There is no 'closed' state — child wallets are accounts with keypairs; they don't 'close.'"
- Document all valid transitions in a table:

| From | To | Initiator | Mechanism | D-# |
|------|----|-----------|-----------|-----|
| Unregistered | Registered | Child | Child signs RegistrationTx; CRDT writes to reg/{child_addr}; consensus certifies (D-06, D-26) | D-34 |
| Registered | Detached | Child | Child signs new RegistrationTx with higher sequence, detach_flag=true, supersedes_sequence=current.sequence (D-35) | D-38 |
| Registered | Revoked | Main | Main signs RevokeTx; consensus validates main sig + main_address match + Registered state (D-36) | D-36 |
| Detached | Registered | Child | Child signs new RegistrationTx with higher sequence, new/updated main_address, supersedes_sequence=current.sequence (re-registration, D-39) | D-38 |

**Section 7: Detach Flow — Child-Initiated (LIFE-01, LIFE-02)**
- Per D-35: "The child issues a new `RegistrationTx` with a higher `sequence` number and a `detach_flag = true`. The `reg/` CRDT record is updated in-place."
- Document the detach flow:
  1. Child constructs `RegistrationTx` with: `main_address` cleared (or set to zero-address), `sequence = current.sequence + 1`, `detach_flag = true`, `supersedes_sequence = current.sequence`, remaining `RegistrationMetadata` fields retained.
  2. Child signs with its own keypair (D-04/D-05).
  3. `FilterRegistration` validates: child signature (gate 2), `sequence > current.sequence` (gate 3), `supersedes_sequence == current.sequence` (gate 3b — D-38). On success: CRDT updates `reg/{child_addr}` in-place.
  4. Nonce chain (`sgns.nonce.v1`) prevents double-detach at same nonce.
  5. Post-detach: child retains all UTXOs, can transact independently. Former main has read-only visibility (inspect history), zero recovery authority.
- Reference: TransactionManager.cpp:2984-3039 (FilterTransaction template), Consensus.hpp:37 (NONCE_SUBJECT_TYPE).

**Section 8: Revoke Flow — Main-Initiated (LIFE-01, LIFE-02)**
- Per D-36: "The main issues a main-signed consensus transaction that targets the child's `reg/` record and sets the `detach_flag`."
- Document the revoke flow with the research-recommended first-class `RevokeTx` approach (per RESEARCH.md Open Question #3):
  1. `RevokeTx` proto message in `SGTransaction.proto`: `DAGStruct dag_struct = 1`, `bytes child_address = 2`, `uint64 registration_sequence = 3`. New `EmbeddedTransaction` oneof arm `revoke = 9` in `Consensus.proto`.
  2. `RevokeTx` as a new `GeniusTransaction` subclass following the `RegistrationTx` (Phase 1 D-06) and `EscrowTx` patterns — has its own `CheckTransactionAuthorization`, `CheckTransactionWellFormed`, `CheckTransactionTypeRules` overrides.
  3. Consensus validation pipeline (ValidateTransactionForConsensus, TransactionManager.cpp:4234-4304):
     - Gate 2 (CheckTransactionAuthorization, line 4361): validates main's signature.

Rationale: keeps authority actions separate from value transfers; provides cleaner audit trail; avoids overloading the transfer type with lifecycle semantics. **Section 9: Replace Main + Policy Fork Decision (LIFE-02, LIFE-03)**
- Per D-37 (LIFE-03 fork decision): "Main replacement is child-only — no consent signature is required from the old main."
- Document the replacement flow:
  1. Child constructs `RegistrationTx` with: new `main_address` (different from current), `sequence = current.sequence + 1`, `detach_flag = false`, `supersedes_sequence = current.sequence`.
  2. Child signs with its own keypair.
  3. `FilterRegistration` validates: child signature, sequence > current, supersedes_sequence == current.sequence.
  4. Old main loses recovery rights over future balances; new main gains recovery rights going forward.
- Document the rationale for child-only replacement (D-37): "Requiring old-main consent would create a deadlock if the old main's key is lost — the child would be permanently bound to an unreachable main. Child-only replacement is consistent with the child-owned identity model (D-04/D-05): registration is child-signed-only and grants the main zero authority over the child's UTXOs."
- Per D-38 (supersedes_sequence): "Every lifecycle-change RegistrationTx (replace main, detach) carries a `supersedes_sequence` field referencing the `sequence` of the registration it replaces. This creates an explicit chain-of-custody."
- Document the conflict resolution mechanism in detail:
  - **CRDT Filter Gate 3b (FilterRegistration extension):** When `RegistrationTx.supersedes_sequence != 0`, the filter rejects the update unless `supersedes_sequence == current_registration.sequence()`. This prevents race-condition forks where two competing updates both try to replace the same base registration.
  - **Nonce Chain Total Ordering (sgns.nonce.v1):** RegistrationTx flows through `HandleNonceConsensusSubject` (TransactionManager.cpp:149-159). The nonce chain allows only one transaction per nonce slot. Two RegistrationTx updates at different nonces but the same `supersedes_sequence` cannot both be certified — the first to reach consensus at its nonce wins; the second fails at the CRDT filter because the current `sequence` has already been bumped by the first.
  - Result: "Deterministic first-to-consensus-wins — NOT first-to-CRDT-wins. Consensus ordering, not CRDT arrival order, determines the winner."
- Reference: TransactionManager.cpp:2984-3039 (FilterTransaction template), Consensus.hpp:37 (NONCE_SUBJECT_TYPE), TransactionManager.cpp:149-159 (nonce handler registration), RESEARCH.md §Nonce Chain Consensus Ordering (lines 432-432), PATTERNS.md §5 Analog 5c (supersedes_sequence gate).
- Traceability: LIFE-02, LIFE-03.

**Section 10: Detach Semantics (LIFE-04)**
- Per D-39: "Detaching (or being revoked) leaves the child wallet as a valid standalone wallet. The child's UTXOs, keypair, and nonce are unaffected — only the `reg/` record's status changes."
- Explicitly state:
  - "The child's address, keypair (`eth_keypair_` in GeniusAccount), and nonce counter (`confirmed_nonces_`, `GetProposedNonce`, `ReserveNextNonce`) are completely unaffected by detach or revoke."
  - "All UTXOs remain owned by the child's address (`UTXOEntryRecord.owner_address == child_address`) — no UTXO transfer or burn occurs during detach/revoke."
  - "The child can continue creating transfers, receiving funds, and earning processing rewards independently."
  - "If the child later re-registers (to the same or a different main), the lifecycle continues from the current registration's `sequence` — the `reg/` record is updated in-place, not deleted and recreated."
  - "Detach/revoke does NOT destroy the child wallet — it only severs the parent-child authority relationship."
  - "The detached/revoked `reg/` record serves as an audit trail: it preserves the history of the parent-child relationship, including the original registration timestamp and all lifecycle transitions."

|----------|-------------|
| GeniusNode → TransactionManager (HoldEscrow) | Policy source selection happens at GeniusNode level — if the child's `reg/` CRDT record is read from an untrusted CRDT delta, an attacker could inject a false dev_wallet. Mitigated by CRDT filter validation + certified status check. |
